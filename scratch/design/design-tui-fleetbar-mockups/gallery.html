FleetBar + Viewport Feedback — Three Agent Concepts

Press a button.
Fleet handles it.

Three independent design concepts for the same idea: your always-on Port Daddy daemon as the control center for your agent fleet — no hanging chat session, no terminal, no bootstrapping. Ask Spider a question. Mark a bug in the browser. Review what Cartographer found. All from buttons that are always there.

Daemon-backed No persistent chat FleetBar UI Browser Extension Async agents
01 Ask a Fleet Agent FleetBar

Menu bar dropdown. Pick an agent, ask a question, the daemon spawns it and brings back the answer. Spider, Cartographer, QA, Gardener, Spark — each with their own last response and idle/running status.

Design notes

Agent roster as horizontal tiles — fits 5 without scrolling at 380px. Selecting an agent swaps the reply pane and quick-prompt chips in place. Quick prompts are agent-specific: Spider gets "Scan last commit", Cartographer gets "What touched auth this week?"

Dispatch overlay inside the reply pane (not a modal) keeps the compose area accessible. ⌘↵ sends. Empty submit flashes red border for 600ms.

02 Viewport Feedback Chrome Extension

Activate feedback mode, drag a rectangle over the broken thing, annotate it. The daemon receives the event, a fleet agent inspects the DOM, finds the source file, fixes it, writes a Playwright test, replies. No terminal touch.

Design notes

Three-panel walkthrough: idle popup → selection mode → annotation panel. Dark curtains surround the live selection (not a canvas overlay) so the target stays at full opacity. Yellow corner handles are the only interactive affordances in selection mode — everything else dims.

Category pills use Port Daddy coordination colors: bug → cinnabar, nit → amber, feedback → cobalt. DOM selector strip shows the agent's resolved target before you hit send.

03 Fleet Activity Feed FleetBar

What your agents found while you were working. Spider's security flag with the code block, Cartographer's live index scan, the feedback handler's diff and passing test count. Outcomes, not events.

Design notes

3px left-border accent stripe per agent — color-codes at a glance before you read the text. Spider's security finding expands inline to show the TypeScript with the injected variable underlined (wavy red). Running Cartographer shows a scanline animation on the card itself, not just a spinner.

Older items collapse behind a disclosure button — present but not competing. This is an outcomes feed, not a notification feed: Spider fired once, one card, one finding, one set of actions.

The architecture underneath

Daemon as the always-on listener

All three concepts run on the same infrastructure: the Port Daddy daemon runs pd watch on fleet channels. No agent needs to be pre-started. No chat session needs to be open. The daemon is the "hanging-out" process — the UI is just buttons.

What's built vs. what's missing

Three UI surfaces to build

pd watch, fleet trigger:, and pd spawn are all shipped. The gap is entirely in FleetBar: the Ask panel, the activity feed, and the extension↔daemon bridge. The infrastructure is waiting.

Build order

Extension first, FleetBar panels second

The browser extension (Concept 02) is independently shippable — it talks to the existing POST /publish API. FleetBar panels (01 + 03) are additive to an existing app. Start with the extension, validate the feedback loop, then surface results in FleetBar.
