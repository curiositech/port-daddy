% Figure IV.14 --- Harbor Sovereignty as a fence (S2.1, def:fh-sovereignty):
% five exclusive powers inside, downstream effects at other harbors
% explicitly drawn outside.
%
% Reader question: what exactly can only D_A decide about harbor A, and
%   what can it not touch?
% Claim: sovereignty is a narrow fence around exactly five decisions; an
%   A-side agent acting at a B-hosted database sits outside the fence by
%   definition, not by omission.
% Evidence: def:fh-sovereignty's own five-item list (issuance, attenuation,
%   revocation, acceptance, evidence binding) and S2.1's own
%   counterexample (an A-side agent operating against a B-hosted database).
% Must distinguish: the five powers inside the fence from the one named
%   thing the text is explicit is outside it -- drawing only the five
%   powers would silently relitigate the scope question the text answers.
% Grammar chosen: containment (a trust boundary fence, pd trust boundary)
%   with five named ports inside and one named thing outside. Grammar
%   rejected: a Venn diagram of two circles would suggest overlap or
%   degree; the text's claim is a hard boundary, all-or-nothing per power,
%   which a fence with ports states more literally.
% Five-second test: is "what a B-hosted database does with an A-issued
%   card" inside or outside the fence?

\caption{\textbf{Five powers inside the fence, everything downstream outside it.} Definition~\ref{def:fh-sovereignty} gives $D_A$ exclusive authority over exactly five things: issuance, attenuation, revocation, acceptance, and evidence binding. What an $A$-side agent does at a $B$-hosted database sits outside the fence by definition -- $B$'s policy applies there, not $D_A$'s, which is exactly why the transfer ceremony (\S\ref{sec:fh-xfer}) cannot require $B$ to verify under $D_A$'s key in its hot path without violating $B$'s own sovereignty.
