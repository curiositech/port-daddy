% sequence over the message-ladder idiom (templates/tpl-message-ladder.tex):
% one lifeline per harbor, badges numbered and forward-sloped, a ruled
% legend of what each one binds.
%
% Reader question: how do all four governing protocols (transfer,
%   revocation, settlement, admission) actually compose in one concrete
%   incident?
% Claim: the four primitives fire in exactly one order against one shared
%   incident -- transfer, then a two-hour-later damage discovery, then
%   settlement, then revocation -- and each is doing its own narrow job, not
%   improvising.
% Evidence: the chapter's own names and numbers from S:fh-ex-setup through
%   S:fh-ex-revocation -- Controller-7, harbors A/S/B, att_A ("controller
%   schema, 9am-5pm, human approval within 30 min"), att_S ("controller
%   schema, after a snapshot, no other migration in flight"), the float32 vs
%   float64 schema mismatch, bond B_alpha at 24h TTL, and the ~3-round
%   ($\log_2 8$) gossip estimate for an 8-harbor federation.
% Must distinguish: which events are local to one harbor (deliver, damage
%   detected, revoke) from which cross a boundary (offer, claim, clear), and
%   the two-hour real-time gap between transfer and damage discovery.
% Grammar chosen: message-ladder (tpl-message-ladder.tex) extended to three
%   lifelines with phase dividers, drawn full width (6.0in) because a
%   four-phase, six-message incident does not fit the 4.5in column without
%   crowding -- declared here per S1. Grammar rejected: a generic swimlane
%   Gantt (tpl-swimlane-gantt.tex) would show concurrency/duration, which
%   this incident does not turn on; every step here is a discrete event in a
%   strict order, which the ladder's numbered, forward-sloped arrows carry
%   directly.
% Five-second test: which harbor discovers the damage, and how long after
%   the transfer does it happen?
