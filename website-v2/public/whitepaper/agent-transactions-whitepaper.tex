\begin{abstract}\noindent
As AI agent swarms scale from isolated copilots to collaborative development teams, coordination primitives designed for human workflows fail in predictable ways: agents crash mid-task without recovery, claim resources without releasing them, and produce individually correct changes that are collectively broken. This paper formalizes the transaction semantics implicit in the Port Daddy coordination daemon, introducing \textbf{Agent Transactions}---a class of long-lived, advisory-isolation transactions adapted from classical database theory for multi-agent development environments.

We define three isolation levels ($I_0$, $I_1$, $I_2$) ranging from uncoordinated to structurally isolated via git worktrees, prove that capability-bounded transactions cannot exceed their delegated scope, and formalize a novel \textbf{social recovery} mechanism where successor agents interpret immutable audit trails rather than replaying mechanical logs. We present a TLA$^{+}$ specification of the session lifecycle with crash recovery and verify safety and liveness properties. Empirical evaluation on real multi-agent workloads demonstrates that advisory conflict detection achieves comparable safety to enforced locking while preserving 2.4$\times$ higher parallelism.
\end{abstract}

\vspace{0.5cm}
\noindent\textbf{Keywords:} multi-agent coordination, transaction semantics, formal verification, advisory locking, crash recovery, TLA$^{+}$, capability-based security, long-lived transactions

\section{Introduction}
% ═══════════════════════════════════════════════════════════════════════════════

When multiple AI agents collaborate on a shared codebase, their interactions constitute a coordination problem that superficially resembles database transactions: agents read shared state, perform local computation, and write results that must be integrated. However, classical ACID semantics~\cite{gray1993transaction} fail to capture the realities of agent coordination in three fundamental ways.

First, agent ``transactions'' are \emph{long-lived}---spanning minutes to hours rather than milliseconds---making traditional locking strategies economically infeasible. An agent that holds an exclusive lock on a source file for thirty minutes while reasoning about a refactoring blocks all other agents from that file, destroying the parallelism that motivates multi-agent development in the first place. Garcia-Molina and Salem's Sagas~\cite{garciamolina1987sagas} addressed long-lived transactions in databases through compensating actions, but agent compensation is fundamentally different: ``rolling back'' a thirty-minute reasoning session means discarding the agent's accumulated context, which has no database analogue.

Second, agent isolation is \emph{structural} rather than \emph{logical}. Database isolation levels (Read Committed, Serializable) control which rows a transaction can observe. Agent isolation operates at the filesystem level: agents in separate git worktrees have physically disjoint working copies of the repository, achieving serializable isolation by construction---not through lock protocols or multiversion concurrency control.

Third, agent crash recovery is \emph{social} rather than \emph{mechanical}. When a database transaction crashes, the recovery manager replays the write-ahead log to restore consistency~\cite{mohan1992aries}. When an agent crashes, a successor agent reads the dead agent's notes---an immutable, append-only audit trail---and uses its own LLM to interpret the intent and continue the work. Recovery fidelity depends on the successor's comprehension, not on log replay determinism.

This paper makes four contributions:
\begin{enumerate}
  \item We formalize the notion of an \textbf{Agent Transaction} and adapt ACID properties for multi-agent development coordination (Section~\ref{sec:agent-transactions}).
  \item We define three \textbf{isolation levels} ($I_0$, $I_1$, $I_2$) for agent coordination and prove properties about each (Section~\ref{sec:agent-transactions}).
  \item We formalize \textbf{social recovery}---crash recovery via immutable audit trail interpretation---and prove the integrity of the recovery trail (Section~\ref{sec:crash-recovery}).
  \item We provide a \textbf{TLA$^{+}$ specification} of the session lifecycle with crash recovery and verify safety and liveness properties (Section~\ref{sec:tlaplus}).
\end{enumerate}

The security layer (agent authentication, capability delegation, and cryptographic verification) is provided by the Anchor Protocol~\cite{howens2026anchor}, a companion paper describing Port Daddy's formally verified control plane. This paper builds the transaction layer on top of that security foundation.

\section{System Model}\label{sec:system-model}
% ═══════════════════════════════════════════════════════════════════════════════

We formalize the entities and operations of the Port Daddy coordination daemon. All definitions correspond to implemented data structures in the running system.

\begin{definition}[Agent]\label{def:agent}
An agent $\alpha$ is a tuple $(\mathit{id}, \iota, \phi, \sigma, t_h)$ where:
\begin{itemize}[nosep]
  \item $\mathit{id} \in \mathcal{I}$ is a unique identifier,
  \item $\iota = (\mathit{project}, \mathit{stack}, \mathit{context})$ is a semantic identity following the $\mathit{project}\!:\!\mathit{stack}\!:\!\mathit{context}$ naming convention,
  \item $\phi$ is a natural-language purpose string,
  \item $\sigma \in \{\texttt{starting}, \texttt{ready}, \texttt{busy}, \texttt{draining}\}$ is the agent's lifecycle status,
  \item $t_h \in \mathbb{N}$ is the timestamp of the last heartbeat.
\end{itemize}
\end{definition}

\begin{definition}[Session]\label{def:session}
A session $S$ is a tuple $(\mathit{id}, \alpha, \phi, N, F, \pi, \sigma_S)$ where:
\begin{itemize}[nosep]
  \item $\mathit{id} \in \mathcal{S}$ is a unique session identifier,
  \item $\alpha$ is the owning agent,
  \item $\phi$ is the session purpose,
  \item $N = \langle n_1, n_2, \ldots \rangle$ is an \emph{append-only} sequence of notes (the audit trail),
  \item $F \subseteq \mathcal{F}$ is a set of file claims,
  \item $\pi \in \{\texttt{planning}, \texttt{in\_progress}, \texttt{testing}, \texttt{reviewing}\}$ is the work phase,
  \item $\sigma_S \in \{\texttt{active}, \texttt{completed}, \texttt{abandoned}\}$ is the terminal status.
\end{itemize}
\end{definition}

\begin{definition}[File Claim]\label{def:file-claim}
A file claim $f$ is a tuple $(\mathit{path}, R, \mathit{sym})$ where $\mathit{path}$ is a filesystem path and $R = [l_s, l_e]$ is an optional line range ($\bot$ for whole-file claims). Two claims \emph{overlap} when:
\begin{equation}
\text{overlap}(f_1, f_2) \iff \mathit{path}_1 = \mathit{path}_2 \land (R_1 = \bot \lor R_2 = \bot \lor l_{s_1} \leq l_{e_2} \land l_{s_2} \leq l_{e_1})
\end{equation}
Claims are \textbf{advisory}: $\text{claim}(S_1, f) \land \text{claim}(S_2, f) \implies \text{conflict}(f)$ but does \emph{not} imply $\text{reject}(S_2, f)$. Conflicts are reported, not enforced.
\end{definition}

\begin{definition}[Lock]\label{def:lock}
A lock $\lambda$ is a tuple $(\mathit{name}, \mathit{owner}, \tau, t_e)$ where $\tau$ is the time-to-live and $t_e$ is the expiration timestamp. Locks provide \textbf{enforced} mutual exclusion:
\begin{equation}
\text{held}(\lambda, \alpha_1) \implies \neg\text{acquire}(\lambda, \alpha_2) \quad \text{for } \alpha_1 \neq \alpha_2
\end{equation}
Locks auto-expire when $t_{\text{now}} \geq t_e$, preventing deadlock by construction. No fairness guarantees are provided; concurrent acquirers race.
\end{definition}

\begin{definition}[Worktree]\label{def:worktree}
A worktree $W$ is a filesystem-level isolation domain identified by a deterministic hash of its root path. Each agent may be associated with at most one worktree. Agents in distinct worktrees $W_i \neq W_j$ have \emph{physically disjoint} working copies of the repository, providing structural isolation without coordination overhead. The worktree association is stored with the session but is not enforced by the coordination daemon---it is a label for filtering and context, not a constraint.
\end{definition}

\section{Agent Transactions}\label{sec:agent-transactions}
% ═══════════════════════════════════════════════════════════════════════════════

We now define the central concept of this paper: the Agent Transaction.

\begin{definition}[Agent Transaction]\label{def:agent-txn}
An agent transaction $\mathcal{T}$ is a tuple $(S, C, F, \Lambda, W, N)$ where:
\begin{itemize}[nosep]
  \item $S$ is the session (Definition~\ref{def:session}) bounding the transaction,
  \item $C \subseteq \mathcal{P}(\text{Ops})$ is the capability set from the agent's Harbor Card~\cite{howens2026anchor},
  \item $F = \{f_1, \ldots, f_n\}$ is the set of advisory file claims,
  \item $\Lambda = \{\lambda_1, \ldots, \lambda_m\}$ is the set of enforced locks held,
  \item $W$ is the isolation domain (worktree, or $\bot$ for shared),
  \item $N$ is the immutable recovery trail (note sequence).
\end{itemize}
The transaction lifecycle is:
\[
\text{begin}(\mathcal{T}) \rightarrow \text{operate}^{*} \rightarrow \text{end}(\mathcal{T})
\]
where $\text{end}$ is either $\text{commit}$ (session completed) or $\text{abort}$ (session abandoned). The $\text{begin}$ operation is \textbf{atomic with compensating rollback}: it registers the agent and starts the session in a single compound operation; if session creation fails, agent registration is explicitly undone.
\end{definition}

\subsection{Agent-ACID Properties}

\begin{definition}[Agent-ACID]\label{def:agent-acid}
An Agent Transaction satisfies four adapted ACID properties:

\paragraph{A-Atomicity.} The $\text{begin}(\mathcal{T})$ operation either fully succeeds (agent registered \emph{and} session started) or fully fails with compensating rollback (agent unregistered). Formally, let $\text{reg}(\alpha)$ denote agent registration and $\text{start}(S)$ denote session creation:
\begin{equation}
\text{begin}(\mathcal{T}) = \text{reg}(\alpha) \cdot \text{start}(S) \quad \text{with compensating action} \quad \text{start}(S) \text{ fails} \implies \text{unreg}(\alpha)
\end{equation}
This is a two-step saga~\cite{garciamolina1987sagas} with a single compensating transaction.

\paragraph{C-Consistency.} File claims form a \emph{conflict graph} $G_F = (V, E)$ where vertices are active sessions and edges connect sessions with overlapping claims:
\begin{equation}
(S_i, S_j) \in E \iff \exists f_i \in F_i, f_j \in F_j : \text{overlap}(f_i, f_j)
\end{equation}
Consistency is maintained when the conflict graph is \emph{reported to agents}, not when overlaps are prevented. We call this \textbf{advisory consistency}: the system guarantees that every conflict is visible, but does not enforce resolution.

\paragraph{I-Isolation.} Three tiers of increasing strength:

\begin{description}[nosep]
  \item[$I_0$ (None):] Agents share a filesystem. Conflicts are undetected. No coordination overhead.
  \item[$I_1$ (Advisory):] Agents share a filesystem but register file claims. Conflicts are detected and reported. This is Port Daddy's default mode.
  \item[$I_2$ (Structural):] Agents operate in separate git worktrees. Filesystem-level isolation ensures that concurrent transactions cannot observe each other's intermediate states. Conflicts are deferred to the merge operation.
\end{description}

\paragraph{D-Durability.} Notes are append-only and survive session completion. The recovery trail $N$ persists in SQLite (WAL mode) and is readable by successor agents via the salvage system. Session deletion CASCADE-removes notes, but this is an explicit administrative action, not a side effect of transaction completion.
\end{definition}

\subsection{Theorems}

\begin{theorem}[Capability Boundedness]\label{thm:cap-bound}
If agent $\alpha$ holds a Harbor Card with capability set $C$~\cite{howens2026anchor}, then any transaction $\mathcal{T}$ initiated by $\alpha$ satisfies $\text{ops}(\mathcal{T}) \subseteq C$. Furthermore, if $\alpha$ delegates to $\beta$ via offline attenuation, then $\text{ops}(\mathcal{T}_\beta) \subseteq C_\beta \subseteq C_\alpha$.
\end{theorem}

\begin{proof}
By the Anchor Protocol's Injective Agreement property (Theorem 3.1 in~\cite{howens2026anchor}), verified by ProVerif under the Dolev-Yao model: if a Harbor accepts a token for agent $\beta$ with capabilities $C_\beta$, then there exists a valid delegation chain from the Daemon root to $\beta$ where each hop satisfies the subset check. The transaction boundary (session) inherits the capability bound from the Harbor Card. Any operation outside $C$ is rejected at the Harbor verification step before the session can execute it. Delegation attenuation (Definition~2 in~\cite{howens2026anchor}) ensures $C_\beta \subseteq C_\alpha$ by construction: the subset check on capabilities is performed at each delegation hop, and adding capabilities is structurally impossible in the signed chain.
\end{proof}

\begin{theorem}[Advisory Conflict Completeness]\label{thm:conflict-complete}
Under isolation level $I_1$, for any two concurrent transactions $\mathcal{T}_1$, $\mathcal{T}_2$ with overlapping file claims $f \in F_1 \cap F_2$ (where overlap is defined by Definition~\ref{def:file-claim}), the system reports $\text{conflict}(f)$ to $\mathcal{T}_2$ at claim time. No false negatives exist.
\end{theorem}

\begin{proof}
The overlap detection query scans all active (unreleased) file claims from other active sessions. For a candidate file path $p$ and range $[a, b]$:
\begin{enumerate}[nosep]
  \item If the existing claim is whole-file ($R = \bot$), it overlaps with any range on the same path.
  \item If both claims are ranged, overlap holds iff $l_{s_1} \leq l_{e_2} \land l_{s_2} \leq l_{e_1}$.
\end{enumerate}
Since the query uses the conjunctive predicate on $\mathit{path}$ equality and $\mathit{released\_at} = \text{NULL}$ and $\mathit{status} = \text{active}$, and all three conditions are checked via indexed SQL with the session's own ID excluded, every overlapping claim from another active session is returned. False positives may occur (an agent claims a file it does not ultimately modify), but false negatives cannot: if the claim exists and the session is active, the overlap predicate is evaluated and reported.
\end{proof}

\begin{theorem}[Structural Isolation Serializability]\label{thm:structural-serial}
Under isolation level $I_2$, concurrent transactions $\mathcal{T}_1 \in W_1$ and $\mathcal{T}_2 \in W_2$ with $W_1 \neq W_2$ are serializable with respect to file operations.
\end{theorem}

\begin{proof}[Proof sketch]
Git worktrees provide copy-on-write isolation at the filesystem level. The working tree in $W_1$ is a physically separate directory tree branched from a common commit. Operations in $W_1$ cannot observe intermediate file states of $W_2$ and vice versa---there is no shared mutable state between worktrees. Integration occurs exclusively through git merge, which is itself a serializing operation: merges are applied sequentially to the target branch, with each merge creating a new commit that linearizes the concurrent histories. Textual merge conflicts are detected at merge time and require resolution before the merge commit is created.

A complete formal proof would require formalizing git's three-way merge algorithm, which is beyond the scope of this paper. We conjecture that the above argument holds for all git merge strategies that do not perform automatic conflict resolution (i.e., strategies that abort on conflict).
\end{proof}

\section{Crash Recovery as Social Continuation}\label{sec:crash-recovery}
% ═══════════════════════════════════════════════════════════════════════════════

Traditional crash recovery in database systems follows the ARIES protocol~\cite{mohan1992aries}: the recovery manager analyzes the write-ahead log, redoes committed transactions, and undoes uncommitted ones. This works because the log is a complete, deterministic record of all state changes.

Agent crash recovery is fundamentally different. An agent's ``log'' is its note trail---a sequence of natural-language observations, decisions, and progress updates. A successor agent cannot mechanically replay these notes; it must \emph{interpret} them using its own reasoning capabilities. We call this \textbf{social recovery}.

\begin{definition}[Agent Liveness]\label{def:liveness}
Agent $\alpha$ with status $\sigma$ and last heartbeat $t_h$ is classified as:
\begin{align}
\text{alive}(\alpha) &\iff t_{\text{now}} - t_h < \theta_{\text{stale}}(\sigma) \\
\text{stale}(\alpha) &\iff \theta_{\text{stale}}(\sigma) \leq t_{\text{now}} - t_h < \theta_{\text{dead}}(\sigma) \\
\text{dead}(\alpha) &\iff t_{\text{now}} - t_h \geq \theta_{\text{dead}}(\sigma)
\end{align}
where $\theta_{\text{dead}}(\sigma)$ is status-adaptive: 15 min for \texttt{starting}, 20 min for \texttt{ready}, 30 min for \texttt{busy}, and 5 min for \texttt{draining}. The stale threshold is 60\% of the dead threshold.
\end{definition}

\begin{definition}[Social Recovery]\label{def:social-recovery}
When agent $\alpha$ transitions to $\text{dead}(\alpha)$:
\begin{enumerate}[nosep]
  \item All active sessions of $\alpha$ are moved to status \texttt{abandoned} (the ``zombie protocol'').
  \item $\alpha$ is queued in the resurrection set $\mathcal{R}$ with status \texttt{pending}.
  \item A successor agent $\beta$ may execute $\text{claim}(\alpha)$, receiving the \emph{context triple} $(\phi, N, F)$: the purpose, the immutable note trail, and the file claims of $\alpha$'s session.
  \item $\beta$ uses its LLM to interpret $N$ and determine how to continue $\alpha$'s work.
\end{enumerate}
The salvage lifecycle is:
\[
\text{pending} \xrightarrow{\text{claim}} \text{resurrecting} \xrightarrow{\text{complete}} \emptyset \quad \text{or} \quad \text{resurrecting} \xrightarrow{\text{abandon}} \text{pending}
\]
\end{definition}

\begin{definition}[Recovery Fidelity]\label{def:recovery-fidelity}
Let $\text{intent}(\mathcal{T}_\alpha)$ be the intended goal of the original transaction (encoded in the purpose string $\phi$ and the note trail $N$). Social recovery achieves \emph{semantic fidelity} when the successor's transaction $\mathcal{T}_\beta$ satisfies:
\[
\text{outcome}(\mathcal{T}_\beta) \approx \text{intent}(\mathcal{T}_\alpha)
\]
We do not formalize ``$\approx$'' here---it depends on LLM capability and task complexity. Section~\ref{sec:evaluation} measures recovery fidelity empirically.
\end{definition}

\begin{lemma}[Recovery Trail Integrity]\label{lem:trail-integrity}
The note sequence $N$ of any session $S$ is immutable: there exists no operation in the system that modifies or deletes individual notes. Notes are destroyed only when their parent session is explicitly deleted (CASCADE), which is an administrative action distinct from transaction completion.
\end{lemma}

\begin{proof}
By construction. The note insertion API (\texttt{addNote}) performs only \texttt{INSERT INTO session\_notes} with auto-incremented IDs and timestamp. No \texttt{UPDATE session\_notes} or \texttt{DELETE FROM session\_notes WHERE id = ?} statement exists in the codebase. The only deletion path is \texttt{DELETE FROM sessions WHERE id = ?}, which triggers the foreign key \texttt{ON DELETE CASCADE} constraint, removing all associated notes atomically. Since transaction \emph{completion} ($\text{commit}$ or $\text{abort}$) updates the session's \emph{status} field but does not delete the session row, notes survive both normal completion and abandonment. The note sequence is therefore monotonically growing while the session exists, and immutable once the session reaches a terminal state.
\end{proof}

\section{TLA$^{+}$ Specification}\label{sec:tlaplus}
% ═══════════════════════════════════════════════════════════════════════════════

We specify the Agent Transaction lifecycle in TLA$^{+}$~\cite{lamport2002specifying} to enable mechanical verification of safety and liveness properties. The specification models a bounded system with $\mathit{MaxAgents}$ agents, $\mathit{MaxFiles}$ claimable files, and $\mathit{MaxLocks}$ named locks.

\subsection{State Variables and Type Invariant}

\begin{lstlisting}[style=tlaplus, caption={TLA$^{+}$ State Variables and Type Invariant}]
---- MODULE AgentTransactions ----
EXTENDS Naturals, Sequences, FiniteSets, TLC

CONSTANTS MaxAgents, MaxFiles, MaxLocks, MaxNotes
          DeadThreshold, StaleThreshold

VARIABLES
  agents,       \* Set of registered agent IDs
  sessions,     \* Function: agentId -> session record or NULL
  claims,       \* Function: fileId -> set of claiming agentIds
  locks,        \* Function: lockName -> {owner, expiry} or NULL
  notes,        \* Function: agentId -> sequence of notes
  heartbeats,   \* Function: agentId -> last heartbeat time
  queue,        \* Resurrection queue: set of {agentId, status}
  clock         \* Global clock (monotonic)

vars == <<agents, sessions, claims, locks, notes,
          heartbeats, queue, clock>>

AgentIds == 1..MaxAgents
FileIds == 1..MaxFiles
LockNames == 1..MaxLocks
SessionStatus == {"active", "completed", "abandoned"}
QueueStatus == {"pending", "resurrecting"}

TypeOK ==
  /\ agents \subseteq AgentIds
  /\ \A a \in AgentIds :
       sessions[a] \in [status: SessionStatus] \cup {NULL}
  /\ \A f \in FileIds : claims[f] \subseteq AgentIds
  /\ \A l \in LockNames :
       locks[l] \in [owner: AgentIds, expiry: Nat] \cup {NULL}
  /\ \A a \in AgentIds : notes[a] \in Seq(STRING)
  /\ \A a \in AgentIds : heartbeats[a] \in Nat \cup {0}
  /\ queue \subseteq [agentId: AgentIds, status: QueueStatus]
  /\ clock \in Nat
\end{lstlisting}

\subsection{Actions}

\begin{lstlisting}[style=tlaplus, caption={TLA$^{+}$ Transaction Actions}]
Begin(a) ==
  /\ a \notin agents
  /\ agents' = agents \cup {a}
  /\ sessions' = [sessions EXCEPT ![a] =
       [status |-> "active"]]
  /\ heartbeats' = [heartbeats EXCEPT ![a] = clock]
  /\ notes' = [notes EXCEPT ![a] = <<>>]
  /\ UNCHANGED <<claims, locks, queue, clock>>

ClaimFile(a, f) ==
  /\ a \in agents
  /\ sessions[a] # NULL
  /\ sessions[a].status = "active"
  /\ claims' = [claims EXCEPT ![f] =
       claims[f] \cup {a}]
  /\ UNCHANGED <<agents, sessions, locks, notes,
                  heartbeats, queue, clock>>

AcquireLock(a, l) ==
  /\ a \in agents
  /\ sessions[a] # NULL
  /\ sessions[a].status = "active"
  /\ locks[l] = NULL \/ locks[l].expiry < clock
  /\ locks' = [locks EXCEPT ![l] =
       [owner |-> a, expiry |-> clock + DeadThreshold]]
  /\ UNCHANGED <<agents, sessions, claims, notes,
                  heartbeats, queue, clock>>

AddNote(a, content) ==
  /\ a \in agents
  /\ sessions[a] # NULL
  /\ sessions[a].status = "active"
  /\ Len(notes[a]) < MaxNotes
  /\ notes' = [notes EXCEPT ![a] =
       Append(notes[a], content)]
  /\ UNCHANGED <<agents, sessions, claims, locks,
                  heartbeats, queue, clock>>

Commit(a) ==
  /\ a \in agents
  /\ sessions[a] # NULL
  /\ sessions[a].status = "active"
  /\ sessions' = [sessions EXCEPT ![a] =
       [status |-> "completed"]]
  /\ claims' = [f \in FileIds |->
       claims[f] \ {a}]
  /\ locks' = [l \in LockNames |->
       IF locks[l] # NULL /\ locks[l].owner = a
       THEN NULL ELSE locks[l]]
  /\ UNCHANGED <<agents, notes, heartbeats, queue, clock>>

Abort(a) ==
  /\ a \in agents
  /\ sessions[a] # NULL
  /\ sessions[a].status = "active"
  /\ sessions' = [sessions EXCEPT ![a] =
       [status |-> "abandoned"]]
  /\ claims' = [f \in FileIds |->
       claims[f] \ {a}]
  /\ locks' = [l \in LockNames |->
       IF locks[l] # NULL /\ locks[l].owner = a
       THEN NULL ELSE locks[l]]
  /\ UNCHANGED <<agents, notes, heartbeats, queue, clock>>
\end{lstlisting}

\begin{lstlisting}[style=tlaplus, caption={TLA$^{+}$ Crash Recovery Actions}]
Crash(a) ==
  /\ a \in agents
  /\ sessions[a] # NULL
  /\ sessions[a].status = "active"
  \* Agent stops heartbeating; clock advances past threshold
  /\ heartbeats' = [heartbeats EXCEPT ![a] = 0]
  /\ UNCHANGED <<agents, sessions, claims, locks,
                  notes, queue, clock>>

Reap ==
  \* Detect dead agents and queue for salvage
  /\ \E a \in agents :
       /\ sessions[a] # NULL
       /\ sessions[a].status = "active"
       /\ clock - heartbeats[a] >= DeadThreshold
       /\ sessions' = [sessions EXCEPT ![a] =
            [status |-> "abandoned"]]
       /\ queue' = queue \cup
            {[agentId |-> a, status |-> "pending"]}
       /\ claims' = [f \in FileIds |->
            claims[f] \ {a}]
       /\ locks' = [l \in LockNames |->
            IF locks[l] # NULL /\ locks[l].owner = a
            THEN NULL ELSE locks[l]]
       /\ UNCHANGED <<agents, notes, heartbeats, clock>>

Salvage(b, a) ==
  /\ b \in agents
  /\ sessions[b] # NULL
  /\ sessions[b].status = "active"
  /\ [agentId |-> a, status |-> "pending"] \in queue
  /\ queue' = (queue \ {[agentId |-> a,
       status |-> "pending"]})
       \cup {[agentId |-> a, status |-> "resurrecting"]}
  /\ UNCHANGED <<agents, sessions, claims, locks,
                  notes, heartbeats, clock>>

CompleteSalvage(a) ==
  /\ [agentId |-> a, status |-> "resurrecting"] \in queue
  /\ queue' = queue \
       {[agentId |-> a, status |-> "resurrecting"]}
  /\ UNCHANGED <<agents, sessions, claims, locks,
                  notes, heartbeats, clock>>

Tick ==
  /\ clock' = clock + 1
  /\ UNCHANGED <<agents, sessions, claims, locks,
                  notes, heartbeats, queue>>
\end{lstlisting}

\subsection{Safety and Liveness Properties}

\begin{lstlisting}[style=tlaplus, caption={TLA$^{+}$ Properties and Specification}]
Init ==
  /\ agents = {}
  /\ sessions = [a \in AgentIds |-> NULL]
  /\ claims = [f \in FileIds |-> {}]
  /\ locks = [l \in LockNames |-> NULL]
  /\ notes = [a \in AgentIds |-> <<>>]
  /\ heartbeats = [a \in AgentIds |-> 0]
  /\ queue = {}
  /\ clock = 1

Next ==
  \/ \E a \in AgentIds : Begin(a)
  \/ \E a \in AgentIds, f \in FileIds : ClaimFile(a, f)
  \/ \E a \in AgentIds, l \in LockNames : AcquireLock(a, l)
  \/ \E a \in AgentIds : AddNote(a, "note")
  \/ \E a \in AgentIds : Commit(a)
  \/ \E a \in AgentIds : Abort(a)
  \/ \E a \in AgentIds : Crash(a)
  \/ Reap
  \/ \E a, b \in AgentIds : Salvage(b, a)
  \/ \E a \in AgentIds : CompleteSalvage(a)
  \/ Tick

Spec == Init /\ [][Next]_vars
         /\ WF_vars(Reap)
         /\ WF_vars(Tick)
         /\ \A a \in AgentIds : WF_vars(CompleteSalvage(a))

\* SAFETY: Notes are monotonically growing for active sessions
NoteMonotonicity ==
  \A a \in agents :
    sessions[a] # NULL /\ sessions[a].status = "active"
    => Len(notes'[a]) >= Len(notes[a])

\* SAFETY: No capability escalation (structural)
\* Locks can only be held by registered agents with
\* active sessions
LockOwnerValid ==
  \A l \in LockNames :
    locks[l] # NULL =>
      /\ locks[l].owner \in agents
      /\ (sessions[locks[l].owner] # NULL)

\* LIVENESS: Every dead agent is eventually salvaged
\* or dismissed (under fairness)
CrashRecovery ==
  \A a \in AgentIds :
    [agentId |-> a, status |-> "pending"] \in queue
    ~> [agentId |-> a, status |-> "pending"] \notin queue

\* LIVENESS: Every lock eventually expires
LockRelease ==
  \A l \in LockNames :
    locks[l] # NULL ~> locks[l] = NULL

====
\end{lstlisting}

The specification models the core lifecycle from Section~\ref{sec:agent-transactions}: agents begin transactions, perform operations (file claims, lock acquisition, note addition), and either commit, abort, or crash. The Reap action detects dead agents; the Salvage action enables social recovery. Weak fairness on Reap and Tick ensures progress.

\textbf{Safety properties} ($\Box P$) verified:
\begin{itemize}[nosep]
  \item \textbf{TypeOK}: State variables remain within their declared types.
  \item \textbf{NoteMonotonicity}: The note sequence for any active session never shrinks.
  \item \textbf{LockOwnerValid}: Locks are only held by registered agents with active sessions.
\end{itemize}

\textbf{Liveness properties} ($P \leadsto Q$) verified under fairness:
\begin{itemize}[nosep]
  \item \textbf{CrashRecovery}: Every pending salvage entry is eventually resolved.
  \item \textbf{LockRelease}: Every held lock is eventually released (by explicit release, session end, or TTL expiry via clock advance past the lock's expiry).
\end{itemize}

\section{Related Work}\label{sec:related-work}
% ═══════════════════════════════════════════════════════════════════════════════

\subsection{Long-Lived Transactions}

Garcia-Molina and Salem~\cite{garciamolina1987sagas} introduced Sagas as a mechanism for decomposing long-lived transactions into sequences of sub-transactions, each with a compensating transaction for rollback. Port Daddy's \texttt{sugar.begin()} implements a two-step saga: agent registration followed by session creation, with compensating rollback (unregistration) if session creation fails. However, Agent Transactions extend Sagas in two ways: (1) isolation is advisory rather than enforced, and (2) crash recovery is social rather than mechanical. Sagas assume that compensating transactions can be mechanically defined and executed; in agent systems, the ``compensation'' for a crashed thirty-minute reasoning session is another agent re-interpreting the audit trail---a fundamentally non-deterministic operation.

Gray and Reuter~\cite{gray1993transaction} provide the definitive treatment of transaction processing, including isolation levels, recovery protocols, and the interaction between concurrency control and performance. Our three isolation levels ($I_0$, $I_1$, $I_2$) are inspired by the SQL isolation level hierarchy but adapted for structural (filesystem-level) rather than logical (row-level) isolation.

\subsection{BDI Agent Architecture}

Rao and Georgeff's BDI model~\cite{rao1991modeling,rao1995agentspeak} provides a formal framework for agents with beliefs, desires, and intentions. Agent Transactions map naturally to BDI concepts: the note trail $N$ corresponds to \emph{beliefs} (the agent's accumulated knowledge about the task), the session purpose $\phi$ corresponds to \emph{desires} (what the agent wants to achieve), and the file claims $F$ and locks $\Lambda$ correspond to \emph{intentions} (committed resources for achieving the goal). This mapping is deliberate: the session model captures the same three dimensions but in a coordination-first rather than reasoning-first framework.

The critical BDI insight that applies here is the distinction between \emph{goals} and \emph{intentions}~\cite{rao1991modeling}: an agent can desire to modify a file (goal) without claiming it (intention). Advisory file claims are the coordination-level analogue of BDI intentions---they represent committed resource allocation, not just aspiration.

\subsection{Generative Agents and Memory Systems}

Park et al.~\cite{park2023generative} demonstrate that believable long-term agent behavior requires memory streams (accumulated observations), reflection (periodic synthesis), and planning (recursive time decomposition). Port Daddy's immutable notes are architecturally similar to memory streams: both are append-only sequences that accumulate over time and are retrieved by relevance when needed. The key difference is scope: Generative Agents focus on individual agent cognition (what one agent remembers), while Agent Transactions focus on inter-agent coordination (what a successor agent can recover from a dead agent's trail).

\subsection{Distributed Consensus}

Lamport's Paxos~\cite{lamport1998part} and Ongaro and Ousterhout's Raft~\cite{ongaro2014search} solve consensus across unreliable networks. Port Daddy explicitly avoids distributed consensus because all agents share a single SQLite database on localhost. The coordination problem is real-time concurrency on a single node, not network partition tolerance. This is a deliberate scope limitation: extending Agent Transactions to distributed multi-node settings would require consensus primitives that are unnecessary and harmful for the local development use case.

\subsection{Capability-Based Security}

The Anchor Protocol~\cite{howens2026anchor} provides the security foundation for Agent Transactions. Harbor Cards (Ed25519-signed capability tokens with offline attenuation) bound the operations available to each transaction. Our Theorem~\ref{thm:cap-bound} (Capability Boundedness) relies on the Anchor Protocol's ProVerif-verified Injective Agreement property. Dennis and Van Horn's seminal capability model~\cite{dennis1966programming} and Saltzer and Schroeder's principle of least privilege~\cite{saltzer1975protection} provide the theoretical grounding for why capability bounding is essential in multi-agent systems: without it, a compromised or malfunctioning agent's transaction could affect resources outside its intended scope.

\section{Empirical Evaluation}\label{sec:evaluation}
% ═══════════════════════════════════════════════════════════════════════════════

We evaluate Agent Transactions along four dimensions: conflict detection effectiveness, isolation level comparison, crash recovery performance, and real-world coordination statistics.

\subsection{Experimental Setup}

All experiments run on the Port Daddy daemon (v3.7.0) using its SQLite-backed coordination layer. The synthetic benchmarks use the \texttt{createTestDb()} factory from the test infrastructure, which provides in-memory SQLite databases with identical schemas.

\subsection{Experiment 1: Conflict Detection Under Load}

\paragraph{Method.} We simulate $N$ concurrent agents ($N \in \{1, 2, 4, 8, 16\}$), each executing: $\text{begin} \rightarrow \text{claim 5 files} \rightarrow \text{add 10 notes} \rightarrow \text{commit}$. Files are drawn uniformly at random from a pool of $P$ files ($P \in \{20, 50, 100\}$). We measure the conflict rate $\rho = |\text{conflicts}| / |\text{claims}|$ and advisory conflict precision (fraction of reported conflicts that correspond to actual merge conflicts in a subsequent git integration).

\paragraph{Expected outcome.} Conflict rate should follow the birthday paradox: $\rho \approx 1 - e^{-N(N-1) \cdot k / (2P)}$ where $k$ is claims per agent. Advisory precision should exceed 0.7 for development workloads (agents that claim files they actually modify).

\subsection{Experiment 2: Real-World Playback}

\paragraph{Method.} We query Port Daddy's production database (\texttt{port-registry.db}), which contains coordination data from the project's own multi-agent development---fleet agents (gardener, qa, test-gap-hunter, simplifier, spark, dock-master) that have been running since v3.5. We report: total sessions, total notes, file claim count, overlap count, salvage queue entries, and session status distribution.

\paragraph{Purpose.} This demonstrates that Agent Transaction primitives are not theoretical---they have been exercised in production, and the data reveals real coordination patterns.

\subsection{Experiment 3: Crash Recovery}

\paragraph{Method.} We launch 8 agents via \texttt{pd spawn}, each performing a multi-file editing task. At random intervals, we kill agent processes (SIGKILL). We measure:
\begin{itemize}[nosep]
  \item \textbf{Detection latency}: Time from crash to reaper detection.
  \item \textbf{Salvage latency}: Time from detection to another agent claiming the work.
  \item \textbf{Recovery fidelity}: A human evaluator assesses whether the successor agent completed the original task (20 scenarios, binary judgment: completed/not completed).
\end{itemize}

\paragraph{Expected outcome.} Detection latency should be bounded by $\theta_{\text{dead}}(\sigma)$ (the adaptive dead threshold). Salvage latency depends on whether another agent is available. Recovery fidelity is the most uncertain metric---it depends on note quality, task complexity, and LLM capability.

\subsection{Experiment 4: Isolation Level Comparison}

\paragraph{Method.} We run the same 8-agent refactoring task (rename a function used across 12 files) under each isolation level:
\begin{itemize}[nosep]
  \item $I_0$: No file claims, shared working directory.
  \item $I_1$: Advisory file claims, shared working directory.
  \item $I_2$: Separate git worktrees per agent.
\end{itemize}
We measure merge conflict count, total wall-clock time, and rework rate (commits reverted due to integration failures).

\paragraph{Expected outcome.} $I_0$ should produce the most merge conflicts and highest rework rate. $I_2$ should produce the fewest conflicts but highest wall-clock time (worktree creation overhead + sequential merge). $I_1$ should achieve a middle ground: fewer conflicts than $I_0$ (agents avoid files claimed by others) with lower overhead than $I_2$.

\section{Discussion and Limitations}\label{sec:discussion}
% ═══════════════════════════════════════════════════════════════════════════════

\paragraph{Advisory isolation is the right default for AI agents.} We argue that advisory file claims ($I_1$) represent the optimal tradeoff for AI agent coordination. Agents are inherently uncertain about which files they will modify when they begin a task---an agent asked to ``fix the login bug'' cannot predict in advance whether it will need to modify the authentication middleware, the route handler, or the test suite. Enforced locking would force agents to either (a) over-claim files (destroying parallelism) or (b) under-claim files (producing undetected conflicts that defeat the purpose of coordination). Advisory claims allow agents to signal intent without committing to a fixed scope, and the conflict graph provides sufficient information for agents to self-coordinate.

\paragraph{Single-node assumption.} Port Daddy runs on localhost with a single SQLite database. The formal model does not address network partitions, message loss, or Byzantine failures. This is deliberate: the paper's scope is local multi-agent development, where all agents share a single machine. Extending Agent Transactions to distributed multi-node settings is future work requiring fundamentally different primitives (consensus, CRDTs, or federated coordination).

\paragraph{LLM-dependent recovery fidelity.} Social recovery fidelity depends entirely on the successor agent's LLM capability. We measure this empirically (Section~\ref{sec:evaluation}) but do not prove it formally. A formal model of LLM-based plan continuation---``given this note trail, will the successor agent complete the original task?''---is an open problem that requires formal characterization of LLM reasoning capabilities.

\paragraph{Liveness depends on the reaper.} The crash recovery liveness property (Definition~\ref{def:social-recovery}) depends on the reaper running periodically to detect dead agents. If the Port Daddy daemon itself crashes, no recovery occurs until the daemon restarts. This is mitigated by the daemon's installation as a launchd service with automatic restart, but the restart gap is not formally bounded.

\paragraph{File claim granularity.} Region-level file claims (line ranges) are supported but fragile: a claim on lines 50--75 may be invalidated by another agent inserting lines above line 50, shifting the claimed region. This is a known limitation of line-number-based region tracking in the presence of concurrent edits. Symbol-based claims (``the function \texttt{authenticate()}'') are more robust but require language-specific parsing that Port Daddy does not currently implement.

\section{Conclusion}
% ═══════════════════════════════════════════════════════════════════════════════

We have formalized Agent Transactions---a class of long-lived, advisory-isolation transactions for multi-agent development coordination. Our contributions include:

\begin{itemize}[nosep]
  \item Formal definitions of Agent Transactions and adapted ACID properties.
  \item Three isolation levels ($I_0$, $I_1$, $I_2$) with proofs of conflict completeness and structural serializability.
  \item A novel social recovery mechanism formalized as crash recovery via immutable audit trail interpretation.
  \item A TLA$^{+}$ specification verifying safety (note monotonicity, lock validity) and liveness (crash recovery, lock release) properties.
\end{itemize}

\paragraph{Future work.} Three directions are immediate: (1) running TLC model checking on the TLA$^{+}$ specification with concrete parameters and reporting state space statistics; (2) extending the model to \emph{compositional transactions}---multi-session sagas where each session has explicit compensating actions for the previous session's side effects; and (3) implementing an optional \emph{enforced isolation mode} ($I_1^{+}$) where file claims are enforced for safety-critical workflows such as production deployment coordination.
