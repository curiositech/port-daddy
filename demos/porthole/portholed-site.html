why this exists

We audited our own demo GIFs. It went badly.

Before building Porthole we read all 47 terminal recordings on our own site, byte by byte. The pipeline truncated every command at 18 lines. Errors shipped on camera and nobody noticed, because nobody reviews pixels. A recording that is text gets reviewed like text — in the PR diff.

the loop

Record. Test. Share. One cast, three jobs.

Record

One command, real PTY, open asciicast format. Colors, timing, spinners, full-screen TUIs — vim and tmux replay faithfully. Input is never captured.

$ porthole rec -c "pd status"
recorded 14.1s → pd-status.cast
$ porthole open pd-status.cast
local player → http://localhost:4310

Test — demos that can’t rot

Scenarios in porthole.yml re-record in CI and diff the settled transcript against a committed golden. Your demos are now snapshot tests. They cannot rot.

$ porthole test
quickstart ✓  transcript matches golden
salvage    ✗  line 12: "Unknown command"
→ diff: .porthole/salvage.diff.html

Share

A hosted, scrubbable link that deep-links to any line — cite line 482 of an incident the way you cite a stack frame. Secret scrub runs before anything leaves your machine.

$ porthole share pd-status.cast
scrub: 0 findings · 14s · public
→ portholed.com/p/x7Qk2 (copied)
flight recorder

The bug happened an hour ago. The replay still exists.

With the shell hook enabled, Porthole keeps the last 15 minutes of your terminal in a local ring buffer — never uploaded, input never captured. When something breaks, porthole save-last 10m turns hindsight into a cast. Attach it to the issue and the maintainer watches the failure happen: the exact flags, the 40-second hang, the error that flashed past. “Steps to reproduce” becomes a link. CLI authors can embed the same ring buffer in-process and offer a replay on crash — session replay for terminals.

yours, not ours

Reskin it with CSS variables. Nothing else.

The player is headless-core + tokens: every color is a documented --ph-* custom property, state is exposed as data-* attributes, and the default skin is one plain stylesheet you can skip. The ◐ toggle above is the token system working — your site’s dark-mode switch drives every embed the same way.

honest answers

The questions you’d ask next.

Does it capture full-screen TUIs — vim, htop, tmux?
Capture: always — a PTY recorder gets every byte. Replay: TUIs render in a faithful fixed grid (never wrapped), and their final frame stays in the transcript when they exit. The TUI (vim) tab above is a live example.
What about secrets?
Keystrokes are never recorded. Before any share, a scrubber scans the reconstructed transcript for paths, tokens, and emails and makes you look at what it found. Local files never leave your machine without an explicit share.
Can I put one in a GitHub README?
GitHub strips scripts, so the embed kit generates an SVG poster of your payoff frame — still real text in the SVG — linking to the live player.
Isn’t this asciinema?
asciinema is excellent and Porthole speaks its format natively. The difference is what happens after capture: terminal players — asciinema’s included — replay a fixed viewport, so anything that scrolls off the top is gone. Porthole keeps the whole session, adds the flight recorder, and turns recordings into CI assertions. Your existing .cast files work here unchanged.
What format is a recording?
asciicast — the open NDJSON format from asciinema. No lock-in: your casts play in any asciicast tool, and Porthole plays any asciicast you already have.
Self-host?
porthole export --html emits a single self-contained file — player, cast, themes, zero dependencies. Host it anywhere. This page’s player is exactly that file.
