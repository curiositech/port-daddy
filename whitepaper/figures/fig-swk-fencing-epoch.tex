% Brief (tikz-diagram-craft). Register row ch1-14 [should].
% Reader question: how does a holder who is asleep past reassignment get
%   blocked from acting?
% Claim: the epoch, not the lock, rejects the stale holder: A's late
%   effect still names a real lease it once held, but it presents the
%   epoch that lease had when A held it, and the effect broker rejects
%   anything below the resource's current epoch.
% Evidence: whitepaper/single-writer-kernel.tex thm:exclusion (every
%   granted lease carries a strictly monotonic fencing epoch; downstream
%   effect brokers reject any operation bearing an expired epoch); the
%   work-unit machine's guard 1 (admit-effect: current epoch only),
%   shortest crime: propose-authorize, start_exec, reassign_role,
%   admit_effect(STALE), 4 steps.
% Must distinguish: the epoch increments on reassignment, not on every
%   write; the rejection compares the effect's carried epoch to the
%   resource's current epoch, not to a wall-clock deadline.
% Grammar: a four-step spine, epoch value named at each step, the stale
%   effect crossing in from the side. Rejected: the full work-unit machine
%   (536 states), which would bury this one guard in the machine it
%   belongs to; this figure isolates the guard as a 3-actor sequence.
% Five-second test: "epoch ticks 0 to 1 at reassignment; A's effect still
%   says 0 and is rejected".
