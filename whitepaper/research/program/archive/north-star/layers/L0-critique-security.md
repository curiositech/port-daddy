I now have the ground truth. The dossier's pragma claims (I1, I4) are accurate. But the security posture claims — the keychain migration, the plaintext-key-at-rest framing, and especially the Arbiter's regimentation — are materially mis-stated in a way that matters for a security reviewer. I have enough to write the review.

## Steelman (security / OS-sandboxing framing)

At its strongest, L0 is a **textbook reference monitor instantiated as a single-writer transactional kernel**, and the dossier earns that framing honestly. Read through Anderson (1972) / Lampson's three reference-monitor properties — *always invoked (complete mediation), tamper-evident, small enough to verify* — the design is coherent:

- **Complete mediation by construction, not by vigilance.** The single-writer invariant (§1.1) is the load-bearing security claim, and the dossier is right that it's the cleanest thing here. Because all contended state lives behind one SQLite file lock + `busy_timeout=5000` (verified in `db.ts:398`), the kernel does not need application-level concurrency control to mediate access — the OS filesystem lock *is* the mediation primitive. This is Saltzer & Schroeder's "economy of mechanism" done correctly: one serialization point instead of N hand-rolled critical sections.
- **Fail-safe defaults, applied in the right places.** `assertNotProdInTest` (`db.ts:51`, a genuine Rails-`ProtectedEnvironment` analogue) and the `0600` DB perms are exactly Saltzer & Schroeder fail-safe-default and least-privilege. The refuse-to-serve-on-CRITICAL boot gate (`pd attest`) is the correct posture for a TCB: when integrity is unknown, deny.
- **Tamper-evidence with the right pedigree.** Citing Haber & Stornetta (1991) *before* Merkle for the hash-chained audit log is the correct lineage — append-only tamper-evident logs predate blockchain, and that's the honest citation. The activity log → Arbiter → Merkle chain is a clean audit-organ design.
- **It refuses to grow into the wrong threat model.** Invoking FLP (1985) to justify "no consensus at L0" is the strongest move in the document. A security reviewer's chief fear is scope creep in the TCB; the dossier *shrinks* the TCB deliberately and names the exact boundary (a second daemon → L3). That is disciplined kernel design.
- **It self-reports its own enforcement coverage** (`enforced | degraded | stubbed`). A monitor that lies about whether it's running is worse than no monitor; the `ArbiterStatus` honesty is a real security property, not decoration.

This is a competent, security-literate design with the right citations in the right places. I want to be clear about that before I take it apart.

## Gaps & inconsistencies (prioritized)

**1. (CRITICAL) The Arbiter is not a reference monitor — it is a post-hoc auditor, and the dossier's own honesty discipline is too generous about this.** The single most important security claim in the document is that the Arbiter "makes a small set of forbidden coordination states physically unreachable." I checked the code: `arbiter.ts:328` does `activityLog.subscribe((entry) => {...})`. The Arbiter is a **subscriber to an append-only event stream that has already committed**. By the time it sees `security.violation`, the forbidding write is durable in WAL. Even in strictMode, the response (line 594) is `man-overboard salvage` — a *compensating transaction*, not prevention.

This violates the reference-monitor property the dossier claims (Anderson's "always invoked" means invoked **before** the operation, on the request path). What L0 has built is closer to a **runtime verifier / security automaton in the Schneider (2000) sense operating in detect-and-recover mode** — and Schneider's own result is the relevant hammer here: an EM (execution monitor) can only enforce **safety properties by truncating the execution before the bad state**. A monitor that observes *after* commit cannot enforce *any* safety property; it can only alert and compensate. The dossier cites Schneider for OP-2 but does not apply Schneider's conclusion to its own headline claim. I8's label ("BUILT-WEAK in observe mode") undersells the problem: it is architecturally observe-only for *every* rule, because subscription is downstream of commit. strictMode changes the *reaction*, not the *interception point*.

The fix the dossier needs: either (a) demote the headline from "physically unreachable" to "detected-and-compensated, with a bounded detection-to-reaction window" everywhere, or (b) identify which rules can be moved to an inline `BEFORE INSERT` trigger / pre-commit hook (PID_SQUATTING and double-claim genuinely can — they're already PK constraints; that's I2's mechanism, not the Arbiter's). Right now the dossier double-counts: I2 says mutual exclusion is enforced by PK constraint (true, inline, real regimentation), then §1.5 credits the Arbiter with making double-claim "unreachable" (false — the PK does that; the Arbiter just notices afterward).

**2. (HIGH) The "plaintext signing key at rest" claim is stale, and it poisons OP-9, I12, and the §6 threat model.** The dossier states as settled BUILT fact: "the DB carries the Ed25519 Harbor-Card signing key in plaintext — a same-machine secret," and builds OP-9 ("DB is 0600 but plaintext") and the §5 assumptions on it. The code says otherwise. `lib/keychain.ts` is a shipped OS-keychain accessor; `coordination-crypto.ts:166` *refuses* to derive in plaintext storage when the keychain is unavailable; `harbor-tokens.ts:42-44,297-325` shows an **active phase-1→phase-2 migration that moves the key out of the DB column into the keychain and blanks the DB row**. So the real state is "BUILT-WEAK, mid-migration, keychain-primary with legacy-plaintext fallback," not "plaintext, full stop." For a security dossier this is the difference between "we have a secret-at-rest vulnerability" and "we have a partially-completed remediation with a documented fallback." A reviewer demands the *current* state and the *fallback conditions* (what platforms still hit the plaintext path? what happens on keychain-unavailable?). OP-9 as written proposes the solution that is already half-built.

**3. (HIGH) The threat model is gestured at, never stated — and a kernel paper lives or dies on its threat model.** §6/OP-9 mention "same-user process adversary explicitly out of threat model" in passing. That is not a threat model; it is a single exclusion. A security expert demands the STRIDE/Saltzer-Schroeder-grade table the rest of the dossier's rigor implies: *who is the adversary* (a buggy cooperating agent? a malicious agent inside the swarm? a compromised dependency? a same-user process? a different uid?), *what are the trust boundaries* (the Unix socket, the FFI .node boundary, the keychain ACL, the DB file), and *what is in vs. out of the TCB*. The peer-cred auth detail I verified (`ipc-auth.ts:8`: "Node.js doesn't expose SO_PEERCRED natively, we use a two-phase auth") is a real trust-boundary weakness the dossier *omits entirely* while claiming "peer-credential auth" as a BUILT bullet — the actual implementation is a software-handshake workaround, not kernel-enforced peer credentials, which on macOS notably *cannot* get the peer PID without `lsof`/`/proc`. That is a meaningful authentication gap on the kernel's own IPC boundary, and it's in code, not in the dossier.

**4. (HIGH) Self-asserted identity (I12=DESIGNED) silently invalidates the security weight of I7, I8, I9, and every Arbiter rule.** The dossier correctly flags I12 as the keystone, but does not propagate the consequence: **every other invariant that names an `owner_actor_id` is unforgeable only up to identity spoofing.** LOCK_OWNER_VALID, CAP_ESCALATION, NOTE_MONOTONICITY, owner-scoped release — all key off self-asserted identity. A malicious agent simply claims to be another actor. So I8 ("forbidden-state unreachability") is not merely "observe-mode-weak"; it is *bypassable by impersonation* until ADR-0040 gates writes. The Arbiter's CAP_ESCALATION rule being Rust-FFI-enforced is security theater if the *capability set it checks against* is attached to a forgeable identity. This dependency (I12 ⇒ soundness of I7/I8/I9) must be stated as a hard precondition, not left to the reader.

**5. (MEDIUM) Merkle tamper-evidence is non-load-bearing and the dossier nearly admits it but stops short.** I9 is labeled BUILT-WEAK, "not yet gating reads everywhere." A security reviewer must be blunter: **tamper-evidence that nothing verifies is not a security control, it is a data structure.** Worse — the attacker who can edit the audit log (a same-user process, which is *out of scope per OP-9*) can also recompute the chain, because the chain's integrity ultimately roots in either the plaintext/keychain key (see gap #2) or nothing. So I9's threat model and OP-9's exclusion are in tension: the only adversary Merkle defends against is exactly the adversary the threat model excludes. Either the chain is anchored to an external/append-only sink (then say where) or it defends against nothing the model admits.

**6. (MEDIUM) FFI is named as a security boundary but its integrity story is unverified and the dossier over-claims it.** The dossier says CAP_ESCALATION is enforced by a "Rust FFI core with checksum-verified embedding" and OP-9 notes "the FFI enforcer is materialized to a temp file." My grep for the FFI/harbor materialization, checksum, and temp-file handling in `arbiter.ts` found *nothing* — no `writeFileSync`, no checksum, no `dlopen`, no `libharbor` reference in that file. The mechanism may live elsewhere, but the dossier cites it as a concrete L0 enforcement guarantee without a code anchor, while *every other* claim is anchored to `lib/*.ts`. A temp-file-materialized native lib is itself a TOCTOU + supply-chain surface (who can write the temp dir? is the checksum verified before or after load? — classic time-of-check/time-of-use). For the one rule the dossier elevates to "real regimentation," this is the weakest-evidenced claim in the document.

**7. (LOW/consistency) The dual-runtime substrate (I11) is correctly flagged as a soundness hazard but never framed as a security one.** Two SQLite bindings means two implementations of the serialization the entire mutual-exclusion guarantee (I2) rests on. If `bun:sqlite` and `better-sqlite3` differ in busy-timeout/lock semantics, I2 — your one inline, real regimentation — could hold under test and fail in prod. The dossier treats this as a correctness/CI issue. It is also a *security* issue: a mutual-exclusion bypass under the production runtime is a privilege/isolation failure, not just a 500.

## What an expert would add

- **A real threat model table** (adversary × asset × trust boundary × control × residual risk), with the TCB drawn explicitly. The dossier has the citations (Saltzer-Schroeder, Anderson, Schneider) to do this in its sleep; not doing it is the conspicuous omission.
- **Schneider (2000) applied to the dossier's own claims**, not just OP-2: a per-rule classification into *safety property enforceable inline (truncate before bad state)* vs. *only detectable post-hoc*. Subscription-based monitoring puts almost everything in the second bucket today; the paper should own that and propose which rules move to `sqlite3_update_hook`/pre-commit triggers.
- **Engage the sandboxing literature the title invokes.** The review lens is "Arbiter jail, tool-allowlist, scoped-FS" — but the dossier contains *no* OS-sandboxing mechanism at all. There is no seccomp-bpf, no `pledge`/`unveil` (OpenBSD), no macOS Seatbelt/App Sandbox, no Landlock (Linux LSM, the modern scoped-FS primitive), no capsicum. The "scoped-FS claim" is just `session_files` claims — which are **advisory coordination locks between cooperating agents, not OS-enforced filesystem isolation.** A malicious agent ignores a `session_files` row and writes the file anyway. The dossier should either (a) build the scoped-FS claim on a real OS primitive (Landlock/unveil) and cite it, or (b) state loudly that L0 provides *advisory* coordination, and OS-level sandboxing of agent processes is out of scope / delegated upward. Conflating advisory file-claims with sandboxing is the central category error for *this* reviewer's lens.
- **Capability model rigor.** "permission is a recorded capability" (§1.5) needs the object-capability literature (Miller, *Robust Composition*, 2006; Dennis & Van Horn, 1966) if it's going to call these capabilities. Right now capabilities are forgeable rows keyed on forgeable identity — that is an ACL with extra steps, not a capability system. Name it honestly.
- **TOCTOU analysis of the OS-bind port check.** `isPortAvailable()` (bind-test) then claim-the-port is a classic check-then-act race against any other process on the machine. The dossier lists it as BUILT with no caveat.

## Verdict

**Not yet paper-ready as a security artifact, though structurally close.** It is COMPLETE as an *inventory* of L0's organs and unusually honest about its build state — the ADR-0045 labeling discipline is genuinely good and rare. But it is **not CONSISTENT on its single most important security claim**, and it **misuses two of my field's core concepts**:

1. It calls the Arbiter a regimentation mechanism that makes states "physically unreachable." The code (`arbiter.ts:328`) shows a post-commit log subscriber whose strongest action is a compensating salvage. By Schneider's own theorem — which the dossier cites — a post-hoc monitor enforces no safety property. This must be reframed throughout, and the real inline regimentation (PK constraints, fail-closed boot gate) credited to the right mechanism.
2. It presents advisory inter-agent file-claims as "scoped-FS / sandboxing." For a security reviewer that is the headline category error: advisory coordination locks are not isolation. Either ground it in Landlock/unveil/Seatbelt or state plainly that OS sandboxing is not an L0 control.

**Must change before paper-ready:** (1) a stated threat model with the TCB drawn; (2) correct the Arbiter regimentation-vs-detection claim everywhere, applying Schneider; (3) update the stale plaintext-key claim to reflect the keychain migration in `harbor-tokens.ts`; (4) propagate I12 (forgeable identity) as a hard precondition that bounds the soundness of I7/I8/I9; (5) anchor or retract the FFI/temp-file enforcement claim and analyze its TOCTOU/supply-chain surface; (6) either build or explicitly disclaim OS-level sandboxing, and stop calling `session_files` a scoped-FS control.

The honest closing sentence the dossier *wants* to write — "solid where local, provisional where it must become cryptographic and continuous" — is true and well-earned for durability and mutual exclusion. It is **not** yet true for enforcement and identity, and a security reviewer cannot let those ride under the same sentence.
