- **The relay now routes HPKE-wrapped channel keys between a harbor's members' devices (WS-B slice B3, relay half; ADR-0123 §1-3).** Two new D1 tables (`migrations/2026-08-26-b3-device-keys.sql`): `device_keys`, one row per (account, device) registering that device's X25519 wrapping pubkey — account-scoped, not harbor-scoped, mirroring `apns_device_tokens`' `(user_id, device_id)` PK plus a global-unique index on the bare id, so a device resolves to its owning account with one indexed lookup; and `harbor_key_wraps`, one row per HPKE-wrapped envelope, whose composite primary key (`harbor_id, authority_epoch, recipient_device_id, key_purpose, key_id`) mirrors `lib/pd-vault-ts.ts`'s `KeyWrapAad` field-for-field — the vault's own `unambiguousEncoding` already treats those seven fields as a wrap's identity, so the relay's row identity matches it exactly. A new `src/device-keys.ts` (following the `src/invites.ts` precedent of a standalone file, not an addition to `harbors.ts`) adds five routes: `POST`/`GET /v1/devices/keys` (register/rotate/list my own devices, account-scoped like `/v1/push/apns/devices`), `GET /v1/harbors/:ns/:name/devices/:deviceId/key` (a peer's pubkey, member-gated), and `POST`/`GET /v1/harbors/:ns/:name/wraps` (post/fetch opaque wrapped envelopes). The relay never decodes `enc`/`ciphertext` — it only verifies routing metadata: a wrap POST's `recipientDeviceId` is resolved to its owning account server-side (never trusted from the request body) and checked against the harbor's membership before the row lands, and a wrap GET stacks harbor-membership *and* device-ownership gates so one member can never read another member's device's wraps even inside a harbor they both belong to. Any harbor member may post a wrap (the relay enforces no writer-vs-member distinction, matching `invites.ts`'s identical reasoning for minting); a same-coordinate repost is idempotent when byte-identical and `409 CONFLICT` when not. No consumption/ack bookkeeping ships in this slice — `GET .../wraps` is a pure, idempotent read.
