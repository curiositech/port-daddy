- **`pd-vault` can now wrap a channel key to a specific device (WS-A slice A4 / WS-B slice B3, ADR-0123 §1).** RFC 9180 HPKE base mode (DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM), implemented from the spec directly in both the Rust kernel crate (`core/kernel/pd-vault/src/hpke.rs`) and its pure-TS reference twin (`lib/pd-vault-ts.ts`) — no HPKE framework dependency in either language, matching the crate's existing house style. `wrap_channel_key_for_device`/`unwrap_channel_key_for_device` seal a `ChannelKey`'s bytes to a recipient device's X25519 public key, with the wrap context (account, harbor, authority epoch, recipient device, grant, key purpose, key id) bound into both the HPKE `info` and the AEAD `aad`, so the relay can route on that metadata without being able to swap any field in transit. The custody law holds: no new public accessor for raw key bytes exists in either implementation, only complete sealed envelopes. Verified against RFC 9180's own official CFRG test vectors (a real X25519 ECDH, not a stand-in) by three independent implementations across two languages plus a from-scratch third check; the wrap-level known-answer vector is a shared fixture (`tests/fixtures/pd-vault-parity-vectors.json`) asserted by both suites per ADR-0120. `grant`/`key_purpose` are opaque authenticated strings in both languages — the vault does not enforce the ADR-0042 ladder, matching ADR-0123 §2's "vault stays small" doctrine.
