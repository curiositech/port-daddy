type: security

- **A retired identity can no longer be flipped back to active by any code path; the database refuses it.** `actor_souls` gains `retired_at` / `retired_reason` / `retired_by` and `resurrection_receipt` / `resurrected_at` / `resurrected_by` (additive, PRAGMA-guarded, migrates on first boot), plus three SQLite triggers: clearing `retired_at` aborts unless the same `UPDATE` sets a fresh, table-unique receipt; a retired row's credential, operator trust, clean-exit count and identity key are frozen; and a retired row cannot be deleted, so its `(harbor, actor_id)` key cannot be re-minted. A retired soul's credential stops verifying, `POST /actors/register` answers `IDENTITY_RETIRED` (403), and it resolves as `unknown` (pool floor). The durable agent roster gets the same wall in ledger form: `PATCH /durable-agents/:id` can no longer move `retired` to `ready` (409 `DURABLE_AGENT_RETIRED`), and a `harbor_events` trigger aborts any `agent-node` fact that reactivates a retired agent without a receipt the previous fact did not carry. The only way back is `souls.resurrect` / `POST /actors/souls/:id/resurrect` (operator token) and `POST /durable-agents/:id/resurrect` (loopback), which mint a receipt and write `IDENTITY_RETIRED` / `IDENTITY_RESURRECTED` entries to the ADR-0089 forensics journal. ADR-0137; `tests/unit/identity-retirement-keystone.test.ts` reproduces the incidental reactivation paths and proves they are refused.
