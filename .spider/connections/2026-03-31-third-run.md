## S19. Agent Inbox `onMessage` Callback + IPC `sendTo` → Zero-Poll Inbox Delivery

**PREMISE A:** `lib/agent-inbox.ts` (line 51) accepts an optional `onMessage?: (agentId, message) => void` callback at construction time. When `send()` deposits a message, it calls `onMessage(agentId, msg)` synchronously — a side-channel hook for real-time notification that is currently wired to nothing. The callback fires on every send but nobody listens.

**PREMISE B:** The IPC server (`lib/ipc-server.ts`) exposes a `sendTo(agentId, frame)` method (from S6/ipc-era, harbor multicast) that finds the connection for a registered agent and writes a frame directly. Latency: ~50µs.

**THEREFORE:** Wire `agentInbox`'s `onMessage` callback to `ipcServer.sendTo(agentId, INFORM { type: 'inbox_message', message })`. When any caller deposits an inbox message — the salvage system (S2, 2026-03-27), the daemon itself, another agent — the target agent receives an `INFORM` push over IPC with zero polling. The `onMessage` hook has been unused since inbox shipped. Connecting it to `sendTo` is a 5-line change in `server.ts` at construction time — the most egregious untapped two-system connection in the codebase.

**CONFIDENCE:** high
**EFFORT:** trivial
**SKETCH:** In `server.ts`, when constructing `agentInbox`:

```typescript
const agentInbox = createAgentInbox(db, (agentId, message) => {
  // Push to IPC if the agent has a live connection
  ipcServer.sendTo(agentId, encodeFrame({
    type: Performative.INFORM,
    conv_id: FIRE_AND_FORGET,
    payload: { topic: 'inbox', message }
  }));
});
```

`ipcServer.sendTo` already handles the case where the agent has no IPC connection (returns false silently). The IPC client SDK gets `client.on('inbox', handler)`. Done. Total: ~10 lines including the SDK stub.

## S20. Barnacle Watchdog + Merge Queue → Pre-Mortem Merge Checkpoint

**PREMISE A:** The Barnacle watchdog (`lib/barnacle-client.ts`) implements the Ouroboros Architecture — it pings the daemon's `/health` endpoint and triggers a recovery callback if the daemon becomes unresponsive. The `createBarnacleWatcher()` factory accepts a logger but has no production callback wired for "daemon about to die."

**PREMISE B:** The merge queue (`lib/merge-queue.ts`) maintains in-progress merge entries with `status: 'merging' | 'inspecting'`. If the daemon crashes while a merge is executing, these entries are stuck at their last status. On restart, `cleanup(olderThanMs)` would delete them after the retention window — losing the merge context entirely.

**THEREFORE:** When Barnacle detects daemon failure, it serializes all non-terminal merge queue entries (`listPending()` + entries with status `merging` or `inspecting`) to `~/.port-daddy/merge-checkpoint.json` before the process collapses. On daemon startup, if the checkpoint file exists, `createMergeQueue()` re-inserts the entries with `status: 'pending'` (rewinding in-flight merges to pending). The merge queue survives daemon restarts with no data loss, and each restored entry carries the original `agentId` so the orchestrator can attribute the resumed work correctly.

**CONFIDENCE:** medium
**EFFORT:** session
**SKETCH:** In `lib/barnacle-client.ts`, the health-failure path calls a new `onPreMortem()` hook injected at construction. In `server.ts`, wire `mergeQueue.checkpoint('~/.port-daddy/merge-checkpoint.json')` as the pre-mortem hook. Add `checkpoint(path)` to `createMergeQueue()` — writes `JSON.stringify(mergeQueue.listPending())` to disk. In `createMergeQueue()` initialization, check for the checkpoint file and call `submit()` for each entry with `{ resume: true }` to bypass duplicate detection. Delete the checkpoint after successful restore. The fleet checkpoint (S8, first run) and the merge checkpoint share the same lifecycle; they can be written in one pre-mortem pass.

## S21. `pd scan` + Symbol Index → Eager Symbol Population at Project Registration

**PREMISE A:** `lib/projects.ts`'s `register()` stores project root, type, config, services, and tags in SQLite. `POST /scan` calls `detectFramework()` and `register()` but never touches the symbol index. The project is known to Port Daddy but its code is invisible to the graph.

**PREMISE B:** The symbol index (`lib/symbol-index.ts`) caches per-file SHA-256 hashes — scanning an already-parsed file is a single hash comparison (~1ms). The expensive parse only runs when the hash changes. `parseDirectory(root)` recursively parses all TypeScript/JavaScript/Python files in a directory tree.

**THEREFORE:** `POST /scan` can trigger `symbolIndex.parseDirectory(root)` as a background job after `register()` completes. The response to the client is unchanged (immediate). Within seconds, the symbol graph for the project is pre-populated — ready for conflict prediction, topological merge ordering (S14, first run), and function-level file claims (S3, ipc-era) — without any agent ever manually calling `POST /symbols/parse`. Phase 1C ("lazy code promotion") becomes "eager batch promotion on project registration." The graph exists before the first agent touches a file.

**CONFIDENCE:** high
**EFFORT:** small
**SKETCH:** In `routes/projects.ts` (the `/scan` handler), after `projects.register()` returns, call `setImmediate(() => symbolIndex.parseDirectory(root))` — fire and forget, non-blocking. Add a `GET /symbols/stats` response field `projects_scanned: N` (already in the stats endpoint per features manifest). The `/scan` response gains an optional `symbols_queued: true` field. No schema changes. Handles the case where `symbolIndex` is not yet wired by checking `if (deps.symbolIndex)`. This is the zero-friction path to getting the symbol graph populated in real projects without requiring agents to explicitly parse files.

The briefing becomes a forward-looking as well as backward-looking document.

## S23. Harbor Token `lhb` + Tuple TTL → Liveness-Anchored Tuple Expiration

**PREMISE A:** Harbor tokens (`lib/harbor-tokens.ts`) carry an `lhb` (last-heartbeat) timestamp claim (per arXiv 2509.13597). The `verify()` function checks `lhb` freshness — if the token's `lhb` is older than the heartbeat threshold, the token is stale (zombie detection). This freshness signal is computed from the JWT but not exposed to other systems.

**PREMISE B:** The tuple space (`lib/tuples.ts`) accepts a per-tuple `ttl` in milliseconds. Tuples expire at `created_at + ttl`. If an agent writes a capability tuple declaring `['capability', 'typescript', agentId, 0.9]` with a 5-minute TTL, the tuple outlives the agent if the agent dies 10 seconds after writing it — creating ghost capability signals.

**THEREFORE:** When an agent writes a tuple and presents a harbor token, the daemon can cap the tuple's effective TTL to `min(requested_ttl, harborToken.lhb_threshold - now)`. A tuple from a healthy agent (fresh `lhb`) gets its full requested TTL. A tuple from a stale agent (old `lhb`) gets a shortened TTL proportional to how stale the agent is. Ghost capability signals can no longer outlast the agent's last confirmed liveness. The tuple space becomes cryptographically freshness-aware without the tuple writer needing to manage their own TTL.

**CONFIDENCE:** medium
**EFFORT:** small
**SKETCH:** In `routes/tuples.ts`, the `POST /tuples` handler: if request headers include `Authorization: Bearer <harbor-token>`, call `harborTokens.verify(token)` and extract `lhb`. Compute `remainingLiveness = lhb + LHB_THRESHOLD - Date.now()`. Set effective TTL to `Math.min(body.ttl ?? DEFAULT_TTL, remainingLiveness)`. If `remainingLiveness <= 0`, reject with 403 (zombie agent). Add `harborTokens` to tuple route deps. This is 15 lines in the route handler and requires no schema changes.

## S24. DNS Module + Harbor Capabilities → Capability-Gated DNS Exposure

**PREMISE A:** The DNS module (`lib/dns.ts`) creates `.local` hostname records for services — `POST /dns/:id` binds a semantic identity like `myapp:api:main` to a hostname like `myapp-api.local`. Currently, any agent that knows the service ID can create a DNS record. There is no capability check.

**PREMISE B:** Harbor tokens carry a `capabilities` array declared in the token JWT. The tokens are already verified in the HTTP layer for harbor-protected endpoints. A harbor card declaring `capabilities: ['dns:expose']` means the agent has been granted external visibility permissions.

**THEREFORE:** DNS record creation becomes capability-gated: `POST /dns/:id` returns 403 unless the caller presents a harbor token containing `dns:expose` in its capabilities. This prevents a rogue fleet agent (e.g., the gardener) from accidentally exposing a service externally. The capability namespace already exists in `harbor-tokens.ts` — this is the first concrete use of a domain-specific capability (not just `merge:submit`). Combine with the tunnel module: `dns:expose` also gates `POST /tunnel/:id`. One capability claim → one permission boundary across two related systems.

**CONFIDENCE:** medium
**EFFORT:** small
**SKETCH:** In `routes/dns.ts`, add a middleware check before `POST /dns/:id`: extract `Authorization: Bearer` header, call `harborTokens.verify(token)`, check `payload.capabilities.includes('dns:expose')`. If the request has no harbor token, apply the existing open behavior (backward compat for non-harbor agents). Same pattern in `routes/tunnel.ts` for `POST /tunnel/:id`. Add `dns:expose` and `tunnel:expose` as documented capability strings in the harbor token documentation section of README.md. ~30 lines across two route files.

## S25. Activity Log + Tuple `out()` → Immutable Audit Shadow for Ephemeral Signals

**PREMISE A:** The tuple space (`lib/tuples.ts`) is intentionally ephemeral: tuples expire after TTL, `in()` destroys them, cleanup pruning removes old entries. There is no history of what tuples existed — the design choice is correct for coordination, but forensically opaque.

**PREMISE B:** The activity log (`lib/activity.ts`) is an append-only audit trail. Every call to `activityLog.log()` creates an immutable record with `type`, `details`, and `metadata` JSON. The log already captures claims, releases, sessions, notes, agents, and webhooks. It can be queried by time range, type, and summary.

**THEREFORE:** `tuples.out()`, `tuples.in()`, and `tuples.in()` that returns empty can each emit `activityLog.log('tuple.out' | 'tuple.in' | 'tuple.miss', { details: template, metadata: { harbor, agentId, matched: true/false } })`. The tuple space retains its ephemeral semantics — the tuple table is still transient — but the *fact that coordination happened* is preserved in the audit log forever. After an incident, engineers can reconstruct "who declared what capability, when, and who consumed which work items" from the activity log, even though the tuples themselves are long gone. This is the audit shadow pattern: ephemeral state with permanent event log.

**CONFIDENCE:** high
**EFFORT:** trivial
**SKETCH:** `lib/tuples.ts`'s `createTupleSpace(db)` already accepts a db. Add optional `activityLog?: ActivityLog` to its factory deps (same optional pattern as DNS module). In `out()`, after the INSERT, call `activityLog?.log('tuple.out', { details: JSON.stringify(template.slice(0,3)), metadata: { harbor, agentId } })`. In `in()`, log `tuple.in` on match, `tuple.miss` on no match. Wire `activityLog` into the tuple space factory in `server.ts`. The `GET /activity` endpoint immediately surfaces tuple coordination history. Zero schema changes; the activity table already exists.

## S26. Changelog + IPC Subscription → Push-Based Feature Notifications to Fleet Agents

**PREMISE A:** The changelog module (`lib/changelog.ts`) accumulates hierarchical, identity-scoped entries. Entries are currently only readable via `GET /changelog` polling. There is no notification mechanism — fleet agents that depend on shipped feature availability (e.g., "only use the new tuple space if it's been released") must poll.

**PREMISE B:** The IPC subscription mechanism (`lib/ipc-router.ts`, `IpcAction.SUBSCRIBE`) maintains persistent callbacks that fire when named events occur. The `messaging.subscribe(channel, callback)` path is already the backbone of IPC pub/sub. A named channel `pd:changelog` could carry entry payloads.

**THEREFORE:** When `changelog.add(entry)` is called, publish to a dedicated `pd:changelog` pub/sub channel (`messaging.publish('pd:changelog', entry)`). IPC-connected agents that subscribed to `pd:changelog` receive push notifications of new changelog entries as `INFORM` frames. A fleet agent implementing conditional capability detection — "use pheromone-weighted merges only after the 'pheromone orchestrator plugin' changelog entry ships" — can wire this as a runtime feature flag without polling. The changelog becomes an event stream. Agents can react to feature availability rather than polling for it.

**CONFIDENCE:** high
**EFFORT:** trivial
**SKETCH:** In `lib/changelog.ts`, inject `messaging?: ReturnType<typeof createMessaging>` as an optional dep. In `add(entry)`, after the INSERT, call `messaging?.publish('pd:changelog', entry)`. Wire `messaging` into the changelog factory in `server.ts` (it's already instantiated before changelog). IPC clients subscribe with `client.subscribe('pd:changelog', handler)` — the standard IPC channel subscription path. Add `pd:changelog` as a documented reserved channel name. Total: ~8 lines.
