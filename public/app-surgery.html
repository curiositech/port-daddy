App Surgery Map

Port Daddy has one daemon, but too many shells around it.

This report maps the Mac menu bar surfaces, legacy HTML dashboards, and the newer React fleet editor. The repo currently has overlapping interfaces, duplicated polling logic, hardcoded ports, and partially abandoned experiments.

The good news: there is a clean merge path. Keep one native menu bar app as the user-facing information layer, keep one web editor as the topology surgery layer, and aggressively mine the older HTML surfaces for the parts that still feel alive.

Status as of 2026-04-06: the FleetBar native window now targets the real /fleet-ui/ control plane instead of a separate shadow dashboard. The remaining gap is pulling the older activity density and live-feed character into that unified surface.

Keep `apps/FleetBar` as native shell Keep `fleet-config-ui` as editable control plane Merge activity / stories / radio feel from old HTML Retire duplicate Swift prototypes Standardize user-facing daemon on `9876`

Immediate Read

  • Best native base: `apps/FleetBar` already speaks fleet status, daemon lifecycle, and cost telemetry.
  • Best editor base: `fleet-config-ui` already has multi-project support, daemon selection, YAML/config editing, DM, sorties, and activity panels.
  • Lost soul: `public/fleet-live.html` and `public/fleet-config.html` have the richer motion, activity density, and “story” feeling the newer UI partially lost.
  • Main duplication bug: multiple apps independently read the port file, poll or SSE the daemon, and assume `localhost:9876` in different ways.
  • Canonical split to aim for: menu bar for awareness and suggestions; web app for graph editing and topology surgery.

Where The Duplication Is Hurting

  • Port assumptions: multiple apps hardcode `http://localhost:9876`, while others read the daemon port file. This is why one UI can look “right” while another looks disconnected.
  • Polling duplicated everywhere: menu bar prototypes, old HTML, and new React each do their own fetch/SSE logic instead of sharing one coherent client contract.
  • Information split: cost lives in one Swift store, action-heavy stories live in old HTML, graph editing lives in React, and the daemon hints live in `/launch-hints` with no canonical home in the UI.
  • Product identity split: the repo simultaneously thinks of the user-facing surface as “dashboard,” “fleet live,” “fleet config,” and “FleetBar.”

Recommendation: The New Split

Keep `apps/FleetBar` as the daemon companion. It should launch when the daemon starts, read one shared daemon preference, show connection errors, budget pressure, fleet failures, salvage alerts, and “should we initialize this project?” suggestions.
Keep `fleet-config-ui` as the deep editing plane. This is where incoming/outgoing edge editing, finite initiations, spawn ceilings, per-project budgets, and graph validation should live.
Mine `public/fleet-live.html` and `public/fleet-config.html` for personality and feed density. Bring back the story log, live activity compression, channel vividness, and obvious causality trails.
Retire `fleet-live-app` and `fleet-bar-app` after harvesting anything unique. They are architectural forks, not durable surfaces.

Suggested Menubar Responsibilities

  • Daemon health: offline, degraded, wrong port, reconnecting, or auth/API failure.
  • Fleet health: active/idle/failed agents, fleets needing attention, stale queues, watchdog findings.
  • Cost and limits: spend today, burn rate, spawn ceiling pressure, per-project budget warnings.
  • Actionable suggestions: new project detected, `pd init` suggestion, missing `pd-fleet.yml`, broken channel topology, invalid edges, fleet config drift.
  • Briefings: “Spark has 3 ideas,” “QA found 2 regressions,” “Spider has 8 connection notes,” “Cartographer wants a merge.”

Suggested Web Control Plane Responsibilities

  • Graph surgery: add/remove incoming and outgoing edges with validation.
  • Execution boundaries: finite steps per initiation, explicit stop conditions, retry behavior.
  • Budget controls: per-agent model selection, caps, max concurrent spawns, per-hour quotas.
  • Inbox and channel debugging: direct agent inbox, channel publish, subscriptions, last delivered payload.
  • YAML truth: round-trip config editing with immediate topology validation and daemon reload.

Port Decision

User-facing Port Daddy should standardize on `9876` as the stable daemon. The reason is not that `9876` is intrinsically better; it is because the historical HTML, the native wrappers, and most assumptions in the repo already orbit that port. Let dev instances float elsewhere, but the user-facing daemon, menubar, and browser surfaces should all agree that the canonical local daemon is `9876` unless explicitly overridden.

Path Recommendation Reason
Stable daemon Use `9876` Matches existing public HTML and historical native wrappers.
Dev daemon Use override ports like `9877` / `9878` Fine for parallel sessions, but not as the default mental model.
Menu bar app Read shared daemon preference, default to port file / `9876` Ambient tool must follow the daemon the user considers canonical.
Web UI Keep explicit daemon chooser Useful for debugging and multi-daemon development.

Concrete Surgery Order

  1. 1. Declare `apps/FleetBar` the only native menu bar app that survives.
  2. 2. Add shared settings for daemon URL + “launch menubar with daemon” + suggestion visibility.
  3. 3. Teach the daemon start path to launch FleetBar when that setting is enabled.
  4. 4. Port activity/stories/briefing density from `public/fleet-live.html` into FleetBar and the React activity panel.
  5. 5. Port the stronger agent/channel/config affordances from `public/fleet-config.html` into `fleet-config-ui`.
  6. 6. Delete or archive `fleet-live-app` and `fleet-bar-app` once the harvested pieces land.
