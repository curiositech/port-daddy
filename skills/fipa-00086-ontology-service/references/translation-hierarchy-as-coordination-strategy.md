# Translation as a task-bounded claim

## Choose a route, not a rank

Ask first whether B directly supports O1: request its service using O1; `not-understood` means this direct route failed. Then choose one §5.3 route: ask DF for an O1 provider; ask an OA for a differently named Identical/Equivalent ontology or usable sub-ontology; or ask DF for a translation service and use it as proxy. These are options, not one compulsory protocol.

Relationships may be manually asserted because determining them can be hard or undecidable. Treat a service listing as a candidate capability, not proof that all terms translate.

## Worked hand check

For `source -> target`, select one source expression with an essential axiom and one with a target-missing term. Accept the first only if a returned target expression satisfies the local fixture. Retain the second as loss or an implementation/application outcome; reserve `nil` for C's example where an OA cannot provide any translation between the ontology pair. A successful route never proves a return route or universal translation.
Assess mappings against the task-essential concepts, direction, and expected information loss. Do not label a mapping lossless/equivalent from surface vocabulary alone. If a required term is unknown, ambiguous, or loses prohibited detail, retain that outcome and escalate/renegotiate rather than silently translate.
