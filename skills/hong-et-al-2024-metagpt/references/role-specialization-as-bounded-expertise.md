# Roles as interface boundaries

Use a role card with responsibility, accepted input, action, produced output, constraints/tool access, and acceptance evidence. For example, an Architect consumes a PRD, decides file layout/data/interface boundaries, publishes a design, and leaves open requirements visible; a Project Manager consumes that design, assigns dependency-bearing tasks, and checks that each task names its owner and inputs. Optional parallel work begins only after the dependency graph shows independent work products and joins when their named prerequisites are both available. This is a local scheduling technique; the paper's described software SOP is not evidence for a particular parallel schedule.

Specialization can make ownership and reviews clearer; it does not formally bound expertise, guarantee fewer errors, or require one artifact per role. The paper’s ablations are task/metric-specific and do not justify compounding-error arithmetic. In v0.8.1, a Role watches action causes and buffers messages; this implementation detail is not a quality guarantee.
