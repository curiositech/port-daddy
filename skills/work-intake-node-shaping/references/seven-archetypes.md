# Seven local topology contrasts

The seven labels are first-party planning choices. The six signals are definitions to discuss, not a scored universal classifier.

| Signal | Meaning to record |
|---|---|
| coupling | how strongly outputs or edits constrain each other |
| context pressure | how much shared state must remain coherent |
| skill boundary | whether one, a few, or many distinct capabilities are needed |
| review independence | whether the review can be meaningfully separated from production |
| budget | local planning constraint, not a calibrated price prediction |
| operator burden | expected steering/approval load on the named operator |

| Shape | Conditional choice | Difficult boundary / failure |
|---|---|---|
| node | one coherent deliverable and acceptance trace | shared file does not prove no approval is needed |
| scout | an unknown blocks a contract | do not turn research into an unbounded task |
| chain | each output is a concrete input to the next | a numbered list without contracts is not a chain |
| dag-workgroup | interfaces and independent validation are documented | shared input alone does not establish parallel safety |
| tournament | independently comparable alternatives and an evaluator exist | do not rank unequal contracts or self-reported confidence |
| ambient-watcher | recurring observation has a named change condition | observation does not authorize an intervention |
| human-gate | a named action is structurally blocked pending approval | a selected human-gate still needs approval declaration and authority/resources before admission |

## Five pairwise disambiguation recipes

| Pair | Ask | Worked distinction |
| --- | --- | --- |
| node / scout | Is the follow-on contract and done condition already known? | A one-file fix with a verifier is node; an investigation to learn which subsystem owns the failure is scout. |
| chain / dag-workgroup | Does every next output require the preceding output, or are real interfaces independently ready? | Fetch → parse → report is chain; independent parser and policy-review branches with a documented merge are DAG-workgroup. |
| dag-workgroup / tournament | Are nodes producing complementary artifacts, or comparable alternatives to the same contract? | API, UI, and tests with a merge contract form a DAG; three independent implementation proposals evaluated by one rubric form a tournament. |
| ambient-watcher / others | Is recurring observation with a named change condition the product of the work? | A monitor that reports a version change is a watcher; a one-time upgrade analysis is scout or node. |
| human-gate / node | Is a named action structurally blocked on approval? | A deployment whose approval is required is human-gate even if one node prepared it; ordinary review does not by itself change a node into a gate. |

Record a runner-up and why it lost. If no distinction is defensible, hold or select scout for clarification rather than inventing a shape. These are local policy comparisons, not a deterministic score or generic invariant.
