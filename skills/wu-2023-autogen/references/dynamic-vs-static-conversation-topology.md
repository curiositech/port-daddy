# Fixed, nested, function-routed, and managed topology

Use fixed direct Assistant ↔ UserProxy exchange when the next stage is known: proposal → execution/human reply → result/error → repair or terminal predicate. A custom `generate_reply` or `register_reply` path can hold that main conversation while a nested conversation consults another participant and returns a result. Function calls are another paper-described route into code that can message an additional participant. These are distinct patterns; list allowed participants and record the actual route.

Use `GroupChatManager` when a group should select the next speaker from context. The paper's manager loop is: select speaker, collect its response, broadcast it to the group, and repeat (A5). This is managed control, not decentralized pairwise auto-reply. In AutoGen 0.2, `GroupChat` has `max_round` and speaker-selection configuration; configure and test group boundaries independently from a direct participant's consecutive-auto-reply bound.

**Selection rule.** Prefer a fixed sequence when its stages are known and inspectable. Consider nested/function/manager routing when intermediate content determines the next needed capability, then test irrelevant speaker selection, allowed-transition behavior if configured, terminal predicate, and `max_round`. No topology is universally scalable or correct.
