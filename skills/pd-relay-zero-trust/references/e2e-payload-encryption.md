# End-to-End Payload Encryption

**Load when**: specifying the E2E envelope; reusing the existing note-encryption design; arguing why the relay never sees plaintext.

## Posture

The relay routes ciphertext. It cannot decrypt. This is not a feature toggle; it is invariant **I1** (see `threat-model.md`).

## Reuse, don't reinvent

We already have `lib/note-encryption.ts` (AES-256-GCM, per-session key wrapped under master). The same envelope shape applies to events with two changes:

1. The wrapping key is **per-channel**, not per-session.
2. The wrap key is wrapped under the **harbor key**, so all members of the harbor can unwrap.

```
event_envelope.ciphertext = {
  alg: "AES-256-GCM",
  iv: <96-bit IV>,
  ct: <ciphertext>,
  tag: <128-bit GCM tag>,
  wrap: <per-channel symmetric key wrapped under harbor key>
}
```

## Key hierarchy

```
harbor_key (Ed25519 sign + X25519 encrypt) — out-of-band exchanged among harbor members
  └── per-channel symmetric key (256-bit) — generated by first publisher, wrapped under harbor X25519 to all members
        └── per-event AES-GCM with random IV
```

The harbor key has both Ed25519 (for signing) and X25519 (for ECDH) halves. Standard X25519 ECDH-1PU or HPKE for wrapping.

## HPKE (RFC 9180) as the wrap

Use HPKE (Hybrid Public Key Encryption) to wrap the per-channel key under each member's X25519 key. HPKE is the modern replacement for ad-hoc ECDH-then-AES.

Algorithm choice (HPKE suite):
- KEM: `DHKEM(X25519, HKDF-SHA256)`
- KDF: `HKDF-SHA256`
- AEAD: `ChaCha20Poly1305` for the wrap (small payload, no AES-NI assumption); AES-256-GCM for the event payload (bulk, AES-NI usually present)

We keep AES-256-GCM for the event payload because:
- Hardware acceleration on most x86_64 / ARM64 deployments
- Already in our code (note-encryption.ts)
- 96-bit IV with random selection is safe up to 2^32 events per key (we rotate channel keys before then)

## Channel key rotation

Triggers:
- Every 24 hours
- On harbor member removal (re-key to exclude departed member)
- On 2^32 events (forced by IV space)
- On suspected compromise

Rotation is published as a special event:
```
channel: <channel>
type: "channel_key_rotation"
prev_key_id: <old_kid>
new_key_id: <new_kid>
new_wrapped_keys: [{member_x25519_pk, hpke_ciphertext}, ...]
```

Subscribers see the rotation event, unwrap the new key, switch over for subsequent events.

## Forward secrecy considerations

Per-event AES-GCM is **not** forward-secret on its own. If the channel key is compromised, all past events encrypted under it are readable.

Two levels of mitigation:

1. **Channel key rotation** (above): bounds the window of compromise to one rotation period (24h default).
2. **Per-epoch keys with KDF chains**: every N events, derive next key via HKDF and discard prior. Strong forward secrecy at cost of complexity. Optional, for harbors that opt in.

For v0: rotation only. KDF chains are an opt-in add later.

## Authentication of plaintext

GCM tag authenticates ciphertext + IV under the channel key. But **anyone with the channel key can forge events under any sender's name as far as decryption goes**. The Ed25519 publisher signature on the envelope (in the chain) provides the publisher-binding that GCM alone doesn't.

Verification order at subscriber:
1. Verify Ed25519 sig on `this_hash` (publisher binding)
2. Verify chain continuity (`prev_hash`)
3. Decrypt ciphertext with channel key
4. If tag fails, surface as crypto error AND chain integrity violation (would imply ciphertext tampering despite valid sig — should be impossible without sig key compromise)

## Headers vs payload

What's in the header (visible to relay):
- sender, channel, seq, prev_hash, this_hash, iat, sig, kid, card

What's in the payload (E2E encrypted):
- application data
- optional metadata extensions (correlation IDs, custom fields)

The split reveals routing/audit data while protecting application content. Document this clearly in the public spec — users will assume otherwise unless told.

## When the relay needs to peek

Some operational features want to read payload (e.g., "filter events by content"). We refuse:
- Filter by header fields only (sender, channel, sizes, time)
- For content-based subscription, subscribers do their own filtering after decrypt
- Never add a "trusted relay" mode that breaks I1

## Testing

- **Round-trip property test**: random plaintext + key → encrypt → decrypt → equal
- **Tamper test**: mutate any byte of ciphertext or tag → decryption fails
- **Replay test**: same plaintext under same key+IV → must never happen (IV uniqueness)
- **Multi-recipient HPKE test**: wrap key for N members, each can unwrap independently
- **Cross-implementation vectors**: 50+ golden vectors so our Node, Python, Go SDKs agree
- **Forward-secrecy boundary test**: simulate key compromise; confirm prior epochs unrecoverable

## Library choices

- **TypeScript/Node**: `@noble/ciphers` for AES-GCM, `@noble/curves` for X25519, `@noble/hashes` for HKDF, `hpke-js` for HPKE
- **Python**: `cryptography` (Hazmat layer), `pyhpke`
- **Go**: standard `crypto/cipher` + `golang.org/x/crypto/hpke` once stable
- **Rust**: `aes-gcm`, `x25519-dalek`, `hpke` crate

All should produce byte-identical output given the same inputs (verified by golden vectors).

## Performance

AES-256-GCM with hardware acceleration: ~1 GB/s per core. Negligible for our payloads (typical event < 4KB).
HPKE wrap is per-channel-key per-member, not per-event. Amortized to nothing.

## Anti-patterns

- **Sending plaintext "for debug"** — configurable plaintext mode is a footgun. No plaintext path exists.
- **Reusing IVs** — random 96-bit IVs are safe up to ~2^32 events per key. We rotate before then.
- **Padding to fixed size** for traffic analysis defense — overengineered for v0; revisit if metadata leakage becomes a threat.
- **Encrypting headers** — defeats relay's routing function. Headers are intentionally cleartext.
- **Using GCM keys for HPKE wrap** — different role, different key.
- **Letting HPKE failures fail-soft** — wrap-failure → drop, don't fall back to plaintext.
