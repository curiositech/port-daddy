\subsection{Build the layer: a gate the worker cannot influence}
\label{sec:sealed-gate}

\noindent\emph{Express lane: this section builds the room's gate three
times. The first version applies the declared function to whatever value
the worker submits, so a worker that submits half the record leaks a bit
the contract never released. The second version reads the committed record
and releases when the worker asks. The value is now correct, but the
worker chooses the time of the release, and the time carries a message.
The third version computes the value itself and releases it at a fixed
deadline. An exhaustive test of two rooms run side by side finds no state,
out of 1,870, in which Erin can distinguish two records with the same
parity. A worker that could cause 9 different outputs under the first
version can cause only 1.}

The boundary above ends on a gap. In the checked model, \texttt{submit}
carries no payload, so no mutation of that model can launder a secret, and
Figure~\ref{fig:sealed-laundering-fork} is arithmetic that was never run.
\pdkernelname{} builds the missing piece here: a gate that receives a
value from the worker and has to decide what to release, and when.

A \emph{room} holds one record. Derek commits it. A worker inside the room
reads it and submits values to the gate. Erin sees what the gate releases,
and the time on the room's clock when it was released. The work order
gives the room one \emph{slot}, which says how many of the record's low
bits are released and when (Listing~\ref{alg:sealed-gate-slot}). One low
bit is the parity $g(s)=s\bmod 2$ of
Property~\ref{thm:sealed-noninterference}.

\pdlistingroom{22}
\pdexcerpt[caption={A slot, and what the decision core is shown of a
room.},label={alg:sealed-gate-slot}]{ch03-slot}

Every run below is one room in two worlds, printed side by side. Derek's
record is 0 in one world and 2 in the other, the pair from the example
above. The slot releases their parity, which is 0 in both, so Erin must
see the same thing in both columns.

\subsubsection{Naive: apply the function to the submitted value}

The obvious gate does what the contract says. The worker computes a result
and submits it. The gate applies the declared function to that value and
releases the result through the slot, once
(Listing~\ref{alg:sealed-gate-handed}).

\pdlistingroom{9}
\pdexcerpt[caption={The first version. \texttt{low} keeps the low bits that
the slot declares.},label={alg:sealed-gate-handed}]{ch03-submitted}

This gate is not careless. It uses its slot only once, and it never
releases more bits than the slot declares. With a worker that submits the
record, it is correct (Listing~\ref{alg:sealed-gate-run-honest}).

\pdlistingroom{15}
\pdrun[caption={A worker that submits the record, at the first gate. The
word at the left of each step says who acts. The gate does not check
it.},label={alg:sealed-gate-run-honest}]{honest-submitted}

Erin sees 0 in both worlds. A test with an honest worker would pass this
gate.

\subsubsection{Break: submit half the record}

The worker is Erin's agent, and nothing forces it to submit the record. It
can submit any value it can compute from the record.
Figure~\ref{fig:sealed-laundering-fork} proposed $t=\lfloor s/2\rfloor$
(Listing~\ref{alg:sealed-gate-run-launder}).

\pdlistingroom{16}
\pdrun[caption={The break. The gate applies the parity function to half the
record.},label={alg:sealed-gate-run-launder}]{launder-submitted}

Half of 0 is 0, and half of 2 is 1. The gate took the parity of each, as it
was written to do, and released 0 in one world and 1 in the other. Erin now
knows the record's second bit, which the contract never released. The gate
limited the release to one bit, but the worker chose which bit. This is
the laundering attack of the boundary above, as a recorded run.

\subsubsection{Break again: the right value at a time the worker chooses}

The property's hypothesis says what to fix: the gate should read the
record that Derek committed. A submission from the worker then becomes
only a request to release (Listing~\ref{alg:sealed-gate-prompt}).

\pdlistingroom{11}
\pdexcerpt[caption={The second version. The value comes from the committed
record, and the worker chooses when it is
released.},label={alg:sealed-gate-prompt}]{ch03-on-request}

The worker that submits half the record now achieves nothing
(Listing~\ref{alg:sealed-gate-run-launder-prompt}).

\pdlistingroom{6}
\pdrunlines[caption={The first break, fixed. The submitted value no longer
reaches Erin.},label={alg:sealed-gate-run-launder-prompt}]{launder-on-request}{1,5,8-9,14-15}{1, 5, 8\textendash 9 and 14\textendash 15}

The gate still releases whenever the worker asks. A worker that has read
the record can ask immediately in one world and one tick later in the
other (Listing~\ref{alg:sealed-gate-run-timing}).

\pdlistingroom{18}
\pdrun[caption={The second break. The value is the same in both worlds, and
the time is not.},label={alg:sealed-gate-run-timing}]{timing-on-request}

Erin sees 0 in both worlds, and it is the correct value. It was released
at time 0 in one world and at time 1 in the other, so she learns the
record's second bit from the timing. Section~\ref{sec:sealed-budget}
measures this channel: a release that can happen at one of $w$ times
carries $\log_2 w$ bits beyond its payload. The property above left timing
out of its model. This gate satisfies that property's hypothesis and still
leaks.

\subsubsection{Fix: the gate computes the value, and the deadline sets the time}

Both breaks have the same cause. The worker controls something that Erin
can see: the value under the first gate, and the time under the second.
\pdkernelname{} removes both controls. The decision is made in the
decision core (\weld{prereq:sec:prereq-build}{decision core}), and the
core makes it only when the clock ticks. \texttt{tick} is given the room
and the current time. It releases something only if \texttt{due} finds
that the slot's deadline has arrived and \texttt{spent} finds that the
slot has not been used. The value comes from \texttt{source} and
\texttt{declared} (Listing~\ref{alg:sealed-gate-tick}).

\pdlistingroom{16}
\pdexcerpt[caption={The decision the core makes on each tick of the
clock.},label={alg:sealed-gate-tick}]{ch03-tick}

Those four functions are the gate's guards, in two pairs. One pair deals
with the first break (Listing~\ref{alg:sealed-gate-what}).
\texttt{source} reads the record its owner committed, and \texttt{declared}
keeps only the bits the slot declares. The worker can still submit values.
The core stores the latest one, and neither guard reads it. The other pair
deals with the second break (Listing~\ref{alg:sealed-gate-when}).
\texttt{due} compares the current time with the slot's deadline, and does
not look at anything the worker did. \texttt{spent} allows the slot to be
used once.

\pdlistingroom{17}
\pdexcerpt[caption={The guards on the value released. A line marked

that guard removed. The verification below runs each of those
builds.},label={alg:sealed-gate-what}]{ch03-what}

\pdlistingroom{16}
\pdexcerpt[caption={The guards on the time of the
release.},label={alg:sealed-gate-when}]{ch03-when}

A worker that submits half the record changes nothing
(Listing~\ref{alg:sealed-gate-run-launder-core}). A worker that asks early
in one world and late in the other gets its release at the same time in
both (Listing~\ref{alg:sealed-gate-run-timing-core}).

\pdlistingroom{14}
\pdrun[caption={The first break, at the kernel's
gate.},label={alg:sealed-gate-run-launder-core}]{launder-core}

\pdlistingroom{16}
\pdrun[caption={The second break, at the kernel's
gate.},label={alg:sealed-gate-run-timing-core}]{timing-core}

Nothing is released when the worker submits a value. The parity is
released when the clock reaches time 2, in both worlds.

\keyidea[Remove the worker's choice]{Anything a worker can choose and a
recipient can see is a channel. It can be a value, and it can be the time
at which a value arrives. Limiting the choice makes the channel smaller.
Removing the choice closes it: the gate computes the value from what the
owner committed, and the deadline fixes the time.}

\subsubsection{Verify: two rooms run as one system}

\paragraph{Every pair of worlds.}
Property~\ref{thm:sealed-noninterference} is about pairs of runs, and its
proof idea sets two worlds side by side. The kernel's tests do the same
with the kernel's own gate. Two rooms with different records are run as
one system, and an exhaustive test visits every state the pair can reach.
Listing~\ref{alg:sealed-gate-pair} gives every move the pair can make
from one state.

\pdlistingroom{29}
\pdexcerpt[caption={Every move a pair of rooms can make. A worker that has
not read the record does the same thing in both
worlds.},label={alg:sealed-gate-pair}]{ch03-pair}

Derek's commit and the clock's ticks happen in both rooms together. So
does anything a worker does before it has read the record, because until
then it has nothing to base a choice on. After the read, the worker in
each world acts independently, and the test tries every way the two can
differ. In each state it asks one question about two records with the
same parity: has Erin seen the same thing in both rooms? Each room is also
compared with a reference model, written separately from the core, of
what Erin should have seen by each time: nothing until the slot's
deadline, and then the record's low bits, once.

The bounds are small. Records run from 0 to 3, and the slot releases one
bit at time 2. The clock runs to time 3, and each worker submits up to 2
values from 0 to 3. Two of the six pairs of records have the same parity,
as the example above counted (Listing~\ref{alg:sealed-gate-worlds}).

Under the first gate Erin has seen different things in 5,760 of 8,046
states. In 1,280 of those, both rooms released something at the same time
and the values differ, which is laundering. The second gate has no leak of
that kind, and all 4,800 of its leaks are in the timing. The kernel's gate
has no leak of either kind in 1,870 states, and in every state it had
released exactly what the reference model says.

\pdlistingroom{22}
\pdrun[caption={Every state of two rooms whose records have the same
parity, at each gate.},label={alg:sealed-gate-worlds}]{worlds}

\paragraph{Every output.}
A count of states shows that a gate leaks. It does not show how much. The
last column of the listing does. For one record, it counts the different
outputs a worker can cause by the time the clock stops, where an output
is everything Erin has seen (Figure~\ref{fig:sealed-views}).

\input{figures/fig-sealed-views}

Under the first gate the worker picks a bit and one of 4 times to release
it, or releases nothing. That is $2\times4+1=9$ outputs, whatever the
record is. Theorem~\ref{thm:sealed-capacity} gives one release of $b=1$
bit at one of $w=4$ times a capacity of $b+\log_2 w=3$ bits, which is 8
outputs. The ninth is no release at all. The theorem assumes that the
number of releases is fixed, and this gate lets the worker decide whether
there is one. Under the second gate the bit is the record's own, and the
worker still chooses among the 4 times and no release, which is 5
outputs. Under the kernel's gate there is 1, and a choice among 1 carries
no information.

\paragraph{Any record, any time.}
The exhaustive test stops at records of 2 bits and a clock that runs to 3.
Kani removes both bounds (\weld{anchor:sec:correct}{Kani}). It compiles
the core's own \texttt{tick} and has a solver consider every input at
once. A property of two runs needs two rooms in one harness. That is the
self-composition of the proof idea above, applied to the code
(Listing~\ref{alg:sealed-gate-kani-pair}).

\pdlistingroom{27}
\pdexcerpt[caption={Two rooms in one Kani harness. Their records are any 64
bits with the same declared
bits.},label={alg:sealed-gate-kani-pair}]{ch03-kani-pair}

\texttt{two\_rooms} builds any two rooms that Erin cannot distinguish so
far. They have the same slot, used in both or in neither. Their records
have the same declared bits. Records of 0 and 2 under a slot of 1
bit are one such pair, and the solver can pick any 64-bit records. It also
picks everything else, including the value each worker submitted. The
harness moves the clock to any time. Its 2 assertions say that both rooms
release the same thing, and that both slots are in the same state
afterwards. Its two \texttt{cover} lines make the solver find a case where
something is released from two rooms with different records, and a case
where the workers submitted different values. Without them the assertions
could pass just because no case reached them.

That is one step. A second harness shows that a commit and a submission
release nothing. Together these give an induction: two rooms that start
indistinguishable stay indistinguishable after any number of moves. Kani
checked the two premises. The induction itself is an argument, and no
tool checked it (Listing~\ref{alg:sealed-gate-kani}).

\pdlistingroom{11}
\pdrunlines[caption={Kani~0.68 on the core's
gate.},label={alg:sealed-gate-kani}]{kani-release}{1-11}{1\textendash 11}

The third result is a control. Its harness asserts the same one-step
property of a gate that computes the release from the value the worker
submitted. That assertion is false, and Kani reports the failure, which
is what a control is for.

\paragraph{Each guard removed.}
This build has four guards. The core can be compiled with any one of them
removed, and the checks should then fail. The exhaustive test is run on
each of those builds (Listing~\ref{alg:sealed-gate-guards-walk}), and so
are the harnesses (Listing~\ref{alg:sealed-gate-kani-guards}).

The first row is the first break, inside the core. The second build
releases the whole record. Erin can then distinguish the worlds without
any help from the worker, and that build still has 1 output for each
record. The third build releases early when the worker has asked, which
is the second break.

The last row is the important one. A core that releases the parity a
second time shows Erin the same thing in both worlds, in every one of
1,870 states, because both rooms repeat the release identically. The
two-room check cannot detect that this guard is missing. The comparison
with the reference model detects it in 1,080 states, and Kani detects it
too. Two rooms that are wrong in the same way look the same. A check that
compares two runs with each other needs a second check next to it, one
that compares a run with what should have happened.

\pdscope{The exhaustive test covers records of 2 bits and one slot of one
bit. Its clock runs for 3 ticks, and
Listing~\ref{alg:sealed-gate-worlds} prints its other bounds. It counts
states and says nothing about how likely a state is. The harnesses cover
one move of two rooms, with any 64-bit record and any slot. That
indistinguishable rooms stay indistinguishable over a whole run is an
argument built on two of those harnesses.}

\begin{pdboundary}
\setlength{\parskip}{4pt plus 1pt}
The gate does the work. The declared bits are something the gate can
compute from the record, so the worker adds nothing to what is released,
and a room with no worker releases the same parity. A room is rented for
work that the gate cannot redo. For that work the gate cannot check
whether an answer is the declared function of the committed record.
Section~\ref{sec:sealed-budget} limits how many bits such a room may
release instead, and that is this chapter's next build.

Time is a count of ticks that the room's host supplies. Nothing here says
how long a step takes, and a recipient with a finer clock than the gate's
is outside the model. A record that Derek commits after the slot's
deadline is released at the next tick, so the time of a release still
tells Erin when he committed.

Requests are not authenticated. Whoever reaches the core first commits
the record, and that can be the worker. The signed work order of
\S\ref{sec:sealed-design} is not built, and neither is its measured
hardware.

Only the gate is built, and for one kind of slot. A slot declares how
many of the record's low bits are released. A release of any other
function of the record, such as whether it exceeds a threshold, is not
built, and the checks above say nothing about one. A worker that sends what it read
through some other channel is a problem for the two fences, and no test
here runs one.
\end{pdboundary}
