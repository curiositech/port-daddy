# Agent Downtime R&D and Hackathons — a Self-Originated Extension to `pd dispatch`

Status: **Proposed** (not an ADR — pick a slot once direction is confirmed)
Author: RFC drafted 2026-07-23, following an operator design conversation

## Correction, from a dedicated audit run alongside this RFC

A memory/persistence-subsystem audit run the same day this RFC was opened claimed ADR-0040's actor-souls reputation ledger is read without real writers. A subsequent review caught that this was too broad, and re-checking `server.ts` directly (not the earlier grep-only pass) confirms a real write path does exist: `server.ts:655-665` runs `migrateActorSouls()` (`scripts/migrate-actor-souls.ts`) on **every daemon boot**, calling `actorSouls.mint()` directly to grandfather existing principals found in `budget_ledger`/`bond_escrow`/`agents` into real souls, before `budgetGuard` starts routing spend through them. The earlier audit missed this because it only grepped for callers of the HTTP route `POST /actors/register` and of `recordCleanExit()`, not for direct library calls to `souls.mint()` at boot.

What remains genuinely true, re-verified with the same grep repeated against current `main`: `POST /actors/register` (`routes/actors.ts:153`) and `recordCleanExit()` (`lib/actor-souls.ts:458`) still have zero callers anywhere in the live session lifecycle (`begin_session`, `pd begin`, `pd done`). The practical consequence is narrower than originally stated — an agent identity already known at the daemon's last boot gets a real soul; an identity that appears for the first time *between* boots stays `soulClass: 'unknown'` until the next restart's grandfather pass catches it retroactively, and a session's clean exit never graduates its soul in real time regardless. Design §4 and Phase 3 below originally assumed live, on-demand registration as a working substrate; the boot-time grandfather pass is a different, coarser mechanism than that, and Phase 3 is revised below accordingly.

## The pitch in one sentence

`pd dispatch` (the shipped successor to `pd nightshift`, `lib/dispatch/{queue,runner}.ts`) already lets an agent spend idle capacity on a bounded, budgeted, worktree-isolated task — but every dispatch today is seeded by a human-typed intent or an operator-tagged roadmap row. This proposal adds a third seed: an agent's **own read** of a codebase or skill corpus during genuine downtime, producing not just a draft PR but also pitches, prototypes, and refined docs/skills — plus a **hackathon mode** where several dispatch runs convene around a shared idea, using the existing Parley protocol as the convening mechanism and the existing actor-identity substrate to let one underlying agent stand in as several distinct, separately-accountable personas for the run.

## Problem

`pd nightshift`'s own "out of scope for first cut" section named this directly: *"Self-driven backlog scanning — for now, the operator types the intent. Auto-promotion from `feedback:dropped(severity=high)` is a future loop."* Roadmap-popper partially closed that loop, but only for rows a human already tagged. Nothing today lets an agent, in genuine idle time (not being used by the project or the operator), read a codebase or skill corpus, form its own view of what's wrong or worth trying, and act on it — the way a person browsing a backlog on a slow Friday afternoon might open a spike branch nobody asked for.

Separately, the operator wants something further: agents that can develop **standing opinions** across sessions ("their own forceful view of how things could be done"), and a **hackathon** format where several agent instances self-organize into ad-hoc teams, build something over a bounded window, and present it — with the twist that the same underlying agent can occupy more than one team and be experienced as a different "person" in each, because the split is a real accountability boundary (separate registered identities, separate outcome records), not just narrative flavor.

## Design

### 1. Self-originated dispatch intents

Add a third intent source alongside the two that exist today, `human-typed` and `roadmap-popper`: `agent-proposed`. (An earlier draft of this section also named `feedback:dropped` promotion as an existing dispatch source — checked against the real code for this revision: `feedback:dropped` tuples, emitted by `lib/feedback.ts`, are consumed only by `lib/roadmap-render.ts`, a roadmap *display* concern. Nothing in `lib/dispatch/*.ts` or `lib/roadmap-popper.ts` reads them. It does not seed dispatch today, so it is dropped from this list rather than miscounted.) A dispatch run, when it has idle capacity and no assigned task, may call a new `pd dispatch propose --self` that:

- requires a **grounding artifact**: the proposal must cite specific file:line evidence or a specific skill/ADR gap it read, not a vibe (the memory-store audit and CDM literature-survey patterns already in this repo are the right shape for "grounded, not vibes" — reuse that discipline, don't invent a new one).
- is capped by the same `daily_cap_usd` / one-at-a-time gates `pd nightshift` already specifies, plus a **new** cap specific to self-proposed work: no more than N self-proposed dispatches per week without at least one being operator-reviewed and closed out, so the queue can't silently grow unbounded busywork.
- outputs one of: a draft PR (existing), a **refined skill or doc** (new — a real PR against `skills/*/SKILL.md` or `docs/*`, same review gate), or a **pitch** (new — see below).

### 2. Pitches as a first-class dispatch output

Today `pd dispatch` only really has one shape of "done": a draft PR. Add `pitch` as a second output kind: a short structured artifact (problem, evidence, proposed direction, a working prototype link if one exists, an honest cost/risk section — matching this RFC's own shape) that lands in `pd morning`'s summary alongside PR-shaped completions, distinctly labeled so the operator isn't surprised to find opinion-shaped output next to code-shaped output. This is the concrete mechanism behind "shows up Monday morning with a presentation on an idea."

### 3. Hackathon mode — parley for opportunity, not just disagreement

`pd parley` today convenes only when disagreement's expected cost crosses `parleyCost` (ADR-0086). Add a second trigger shape, `parley --convene-kind opportunity`, gated by a *different* economic test (expected value of a coordinated attempt vs. N independent uncoordinated ones), that:

- invites K dispatch instances (self-proposed or operator-seeded) around one theme,
- runs a bounded number of rounds of the *same* typed exchange primitive (position → critique → revision → vote) parley already has, but scored on "what should we build" rather than "who's right,"
- ends with the existing durable-outcome mechanism, extended with a `built_artifact` field (a prototype, a demo, a joint pitch) instead of only a resolved position.

This is genuinely new economics on top of existing machinery, not a new coordination primitive — the reuse is the point, not a limitation.

### 4. One agent, several accountable personas

The "same agent, three teams, three people" idea is real and worth taking seriously, but it needs a hard rule to avoid becoming a reputation-laundering trick: **a persona is only legitimate if it is a genuinely separate, independently-scoped run** (its own dispatch id, its own worktree, its own token budget, its own registered actor-sub-identity per ADR-0040) that cannot see the other personas' in-progress state during the hackathon window — otherwise "three people" is theater, one agent negotiating with itself with full information, which produces convergence, not the productive friction three actual people would produce. Post-hackathon, all personas' outcomes roll up to the same base actor's reputation ledger (per `agent-identity-continuity-reputation`'s outcome-ledger design) — so a persona that pitched badly still costs the underlying agent's standing. That's what makes a "forceful view" earned rather than performed: it's a real bet, recorded, not a debate-team assignment.

**Naming, tied to the real Roster.** `lib/actor-roster.ts` is the canonical, already-shipped actor roster — `ActorDefinition` has `id` (a stable kebab-case identifier, e.g. `spark`, `cartographer`), `label`, `title`, `mission`, `owns`, `aliases`, `mailbox`. Hackathon personas should be a real, if ephemeral, extension of this same schema rather than a separate invented naming scheme, so the operator's "I'm hoping we persist some into the Roster system Beacon is building" is the actual mechanism, not a wish. Concretely: a persona gets `id: '<role>-<hackathon-slug>-<n>'` (stable, queryable, matches the existing kebab-case convention) and a `label`/`title` the persona itself proposes at spawn time (this is where "Sarah Redteamer" lives — as the `label`, not the `id`). A persona whose hackathon outcome earns it real, repeated recurrence (the same shape of contribution winning across multiple hackathons) is a candidate for **promotion**: its `label` and `mission` get folded into a durable, non-ephemeral roster entry the way any of today's named actors are — this is the actual persistence path, gated on recurrence the same way a mined eureka arc is (Section 1's grounding-artifact discipline, not a popularity vote after one good pitch).

**Hackathon budget, HITL-gated.** Reuses `apps/relay/src/interruptions.ts`'s already-shipped operator-interruption mechanism (`InterruptionRow`: `source_agent`, `title`, `body`, `urgency`, `state`, `answer`, with decay/nag/escalation if the operator doesn't respond) rather than inventing a second HITL primitive. A hackathon convene call creates one interruption per candidate project: `body` carries the pitch and its cost estimate, `urgency` scales with the cost, and the hackathon's actual budget is only committed once the operator's `answer` greenlights it — exactly "the operator calls for one, hears project pitches and their possible cost, then greenlights them." No hackathon work spends real budget before a real, recorded operator answer exists for that specific pitch.

**Fractional credit attribution across N personas of one role.** This is a genuinely different problem from a single agent's outcome ledger, and `agent-identity-continuity-reputation`'s own guidance names the right tool for it directly: pairwise/tournament signal among *individual* runs is Bradley-Terry/Elo, but **team games — where multiple parties jointly produce one outcome and credit must be distributed across teammates — are TrueSkill's actual design case** (its origin is Xbox Live team matchmaking). Applied here: one hackathon "team" of N personas sharing a role (four redteamers) is a TrueSkill team; the hackathon's outcome (won the greenlight, or didn't; pitch was later validated, or wasn't) updates each *persona's* individual skill estimate via TrueSkill's team-game update rule, which naturally does fractional attribution by construction — a persona whose skill estimate already has low uncertainty (a long track record) absorbs less of the update from one team outcome than a brand-new persona with wide uncertainty, so credit and blame are distributed by how *informative* this one result actually is about each individual, not split evenly by headcount. Each persona's updated skill estimate then rolls up into the base actor's reputation ledger per the existing outcome-ledger design, weighted by that persona's own current uncertainty the same way. This still needs the live actor-soul registration from Phase 3 to have anywhere real to write the update — named as a hard dependency, not assumed away.

## Phased plan

1. **Self-proposed intents + pitch output** (extends `lib/dispatch/queue.ts` with an `origin: 'agent-proposed'` field and `output_kind: 'pr' | 'skill-doc' | 'pitch'`; extends `pd morning` to render pitches distinctly). No new coordination primitive — pure extension of shipped infrastructure.
2. **Opportunity-parley trigger** (extends `lib/parley-trigger.ts` with the second convene-kind and its own economic gate). Composes with (1) — parley needs dispatch instances to convene, so this is naturally sequenced after.
3. **Per-persona sub-identity + reputation rollup** — the highest-risk, most novel piece, and now known to have a real prerequisite: the boot-time grandfather pass is not sufficient for a persona minted mid-hackathon, so live actor-soul registration (`POST /actors/register`) and clean-exit graduation (`recordCleanExit`) have to actually be wired into the live session lifecycle, since today nothing calls either. This phase is really two steps — (3a) wire live registration into `begin_session`/dispatch spawn for every agent, not just dispatch/hackathon personas, since that's a prerequisite improvement the whole fleet benefits from independent of this RFC; (3b) build the per-persona sub-identity scoping on top of a registration path that actually fires in real time, not just at the next restart. Also needs an explicit operator decision on the Sybil/whitewashing boundary (does a bad persona genuinely cost the base agent, every time, no exceptions?) before either step is built.

## Risks, named rather than hand-waved

- **Cost runaway with vibes-based justification.** Idle capacity is not free compute. Mitigation: the grounding-artifact requirement in (1), plus the existing `daily_cap_usd` and one-self-proposed-dispatch-open-at-a-time gate.
- **Reputation-laundering via personas.** Named directly in Design §4: no persona without a real accountability boundary and a real reputation rollup, full stop. This is the same failure mode `agent-identity-continuity-reputation` already catalogs (Sybil-reset, whitewashing) — this proposal must not reintroduce it under a friendlier name.
- **Performed forcefulness instead of earned forcefulness.** An LLM has no standing opinion across sessions unless something durable carries it forward. Without the reputation rollup actually wired (Phase 3, not Phase 1), "impassioned agents with their own view" degrades to confident tone with no track record behind it — worth saying plainly rather than presenting Phase 1 as if it already delivers this.
- **Hackathon personas with full mutual visibility collapse into one voice.** Named directly in Design §4 — enforce real isolation (separate worktrees, separate budgets, no shared in-progress state) or the format doesn't produce what it's for.
- **Building persona accountability on a ledger that only updates at boot.** Confirmed by the correction above: the reputation ledger this RFC's Phase 3 depends on has a real write path, but only a coarse, boot-time one — a persona minted mid-hackathon would resolve to `unknown` until the daemon's next restart. Building the persona layer without wiring live registration first would produce the exact reputation-laundering failure this RFC otherwise guards against — a freshly-minted persona would resolve to the same inert `unknown` state as an unaccountable one, making the "real accountability boundary" claim false in practice for exactly the personas that matter most (the ones created for this specific hackathon), even though it's true on paper for personas that already existed at last boot.

## Open questions for the operator

1. Cap on self-proposed dispatches per week, and the "must close one out before opening another" ratio — what numbers feel right to start conservative?
2. Should pitch-kind dispatches count against the same daily cost cap as code-kind dispatches, or get their own (smaller) budget, since a pitch is cheaper to produce than a working prototype?

Three questions raised in review are answered above rather than left open: persona naming is a real extension of `lib/actor-roster.ts`'s existing schema with promotion gated on recurrence (Design §4); hackathon budget approval reuses the shipped `apps/relay/src/interruptions.ts` HITL mechanism, no work spends before a real operator answer exists (Design §4); fractional credit across N personas of one role uses TrueSkill's team-game update rule, which was built for exactly this problem (Design §4).
