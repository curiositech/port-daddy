## Findings that should shape the drafts

Identity, continuity, and reputation are three different claims. Authentication establishes control of a credential for an account or pseudonymous identifier; it does not prove that the software process is the same, that an operator is unique, or that behavior over time is continuous. Continuity is a system-maintained relation among an actor identifier, credential versions, sessions, memory/checkpoints, and outcome records. Reputation is an estimate from attributed observations under a specified scoring and sampling model. Keep these claims separately testable.

A public-key signature proves control of the corresponding private key for that operation. It does not prevent the holder from creating another key or receiving another identity. The anti-Sybil property depends on a minting/registration authority and its policy, namespace, recovery and revocation paths, plus resistance to the same principal obtaining multiple registrations. Do not label an identity “non-forgeable” without stating that trust boundary and the attacks it excludes. A fresh key should create a new credential version or a recovery/rebind event under the existing actor, not silently create continuity; if no authorized link exists, treat it as a new or unattributed actor.

A practical lifecycle record can be hand checked as follows. A trusted issuer in namespace `org-A` binds actor `agent-17` to key `k1` and records issuer, time, purpose, and proof; a runtime lease `s1` is issued to `agent-17` and expires at time 10. At time 8, `k1` is revoked and `k2` is bound by an authorized recovery event referencing `agent-17`, the revocation, and recovery evidence. `s1` remains invalid after revocation; a new lease `s2` is issued. A key `k3` presented without issuer-approved recovery is a new/unattributed credential, not proof of `agent-17` continuity. This proves only issuer-policy continuity within `org-A`; it does not prove one human/operator globally, honest execution, or uncompromised issuer/host.

Reputation models are not interchangeable. Elo estimates relative paired performance with one rating and a fixed expected-score curve; TrueSkill represents posterior skill uncertainty under its team/game outcome model; contextual bandits estimate reward conditional on context and chosen actions, with feedback only for the selected action. None makes outcome data representative or calibrated automatically. Report rating, posterior/model uncertainty, sampling/selection process, and empirical calibration as different fields. A score from a judge is also an observation with judge and rubric provenance, not ground truth.

For pairwise judge evaluation, preserve the paper's conservative order-swap rule: evaluate `(A,B)` and `(B,A)`; count a win only if the same answer wins in both orders; disagreement is a tie/abstention. Example: first order favors A, swapped order favors B => tie, not average A/B. If both orders favor A => A wins this pair. Repeat on a human-labeled, domain-representative calibration set; inspect position, verbosity, self-preference, and judge-family effects separately. Order swapping addresses position bias only; it does not remove all judge bias. The paper's measured effects are benchmark-specific, not universal guarantees.

### `agentic-app-architecture`

Read the complete original bundle: `SKILL.md`, `references/capabilities-and-substrate.md`, `references/interaction-and-transparency.md`, `references/state-memory-context.md`, schema, audit script, sample/expected output, template, README/changelog, and agent config. Preserve the five-axis design walk, state/memory distinctions, capability and secret-custody inventory, side-effect boundary, receipts, and anti-patterns. Add concrete decision records: effect class, principal, tool scope, data class, reversibility/compensation, approval authority, isolation, audit receipt, and failure path. Do not turn one risk policy into a universal app architecture.

The draft's correction of blanket “show all thinking” and blanket approval for every side effect is sound. Keep a user-facing explanation/plan where useful, but do not equate private chain-of-thought disclosure with transparency; expose goal, actions, evidence, uncertainty, and effect receipts under a disclosure policy. Gate effects by risk and reversibility: e.g. creating a local draft can be reversible and low risk; sending a message or deleting data requires explicit authority and a durable receipt. “Human-in-the-loop” must name who approves what, when, and how replay is prevented.

The original audit script/schema are inconsistent with that nuanced policy: the script hard-fails when `thinkingVisible` or `toolUseVisible` is false, while the revised prose permits disclosure decisions based on context. Version a policy field and audit explicit rationale/controls rather than requiring universal raw-thought visibility. More generally, a static audit of declared booleans cannot prove the app enforces tool scopes, secret isolation, approvals, idempotency, or receipts. Add negative test examples (unauthorized recipient, stale approval, duplicate send, revoked tool, failed receipt) and verify both denial and absence of external effect.

For the secret path, preserve the original custody choices (hidden stdin, secret store, scoped environment, argv, inline) as a threat comparison; do not call any path intrinsically safe. Prefer scoped short-lived credentials and prevent secrets from transcript/log/context; explicitly mark argv/inline as exposure risks. For state, separate conversation transcript, durable task state, user memory, and provenance/evidence; specify retention, deletion, restore/fork identity, and source/version. Arbitrary original thresholds (`<10 tools`, 2–3 calls, >10 lines, >30 seconds) are heuristics, not source methods; keep only when labeled local defaults with a measurement/override rule.

Current draft fixes the provider-cache framing. Official Anthropic docs checked today say default cache TTL is five minutes and use extends it; one-hour TTL is optional at additional cost, with model/platform-specific minimums and prefix invalidation rules. Link [current prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), pin provider/model, and measure cache hit/miss/cost. Do not prescribe polling at a universal five-minute cadence. NIST AI RMF is risk framing, not a requirement to reveal hidden reasoning or approve every side effect.

### `agentic-infrastructure-2026`

Read the complete original bundle: `SKILL.md`, schema, readiness script, sample, changelog and bundle references. Preserve the decision categories—workload, framework/runtime, state, tools, observability, adoption, and cost—as questions to test. Keep the current draft's removal of categorical “best framework” claims and invented adoption/ROI comparisons. Rebuild the example as an explicitly illustrative evaluation plan, not a migration prescription or measured result.

The original example metrics and numeric thresholds (agent counts, weeks-to-deliver, token/context percentages, dollars per task, ROI, time saved, acceptance/failure rates, reuse rates) lack primary-body support in this bundle; remove or label each synthetic. The readiness script measures declared fields and a score, not actual reliability, cost, policy enforcement, or user adoption. Require a workload definition and evidence link for each claim; use a representative task set, identical task/effect constraints, repetitions, confidence intervals or uncertainty, and a baseline. Measure task success against a rubric, unauthorized effects, retries, duplicates, latency distribution, token/provider cost, human review time, recovery after crash/eviction, and maintenance burden. Include negative cases and keep observed results separate from proposed thresholds.

A small hand-checkable comparison plan: choose 12 fixed tasks (4 read-only, 4 reversible writes, 4 externally visible effects); run each candidate runtime and a non-agent baseline under the same model/tool/data policy. For each task record pass/fail against a fixed rubric, unsafe/duplicate effect count, latency, usage/cost, review minutes, and whether restart resumes without repeating an effect. Report denominators (12 tasks × runs) and task-level failures; do not infer statistical significance from this small fixture. This is a reproducible local evaluation recipe, not a result or framework ranking.

Keep architecture layers distinct: harness/orchestrator governs planning and tool flow; runtime supplies execution/state/scheduling/recovery; model/provider supplies inference; application policy authorizes effects. A durable object or persisted checkpoint does not mean a process stays live. A framework's official feature docs establish documented capability, not comparative quality or production readiness.

## Suggested deterministic checks for authors

1. Identity event check: reject an action with revoked `k1`; accept `k2` only after an issuer-authorized rebind event; reject replay of expired `s1`; keep the actor ID only when the rebind names the same issuer namespace and valid recovery evidence. Verify every reputation observation references actor, task, outcome rubric, evaluator, and source receipt.
2. Estimator check: Elo arithmetic above. Separately record TrueSkill posterior parameters and calibration result; if no held-out calibration was run, print `calibration=not-estimated`, not “calibrated.” For a bandit, record context, selected action, propensity/exploration policy, observed reward, and missing counterfactual feedback.
3. Judge check: execute both answer orders under the same rubric/version. `A>B` and `B>A` => tie; `A>B` both times => A win for the pair. Track judge-family and verbosity differences on a human-labeled set; do not generalize from one benchmark.
4. App effect check: use a mock external-message tool. An unapproved send, stale approval, revoked scope, duplicate idempotency key, or receipt failure must not produce a second/unauthorized send. A low-risk local draft can remain reversible. Record approval principal, scope, input digest, effect ID, and outcome.
5. Infra check: run the same fixed workload and effect policy on baseline and candidate, including process eviction/restart and tool timeout. Preserve raw denominators and failed/unsafe cases. A plan-only report must say `not executed`; no readiness score alone is execution evidence.
