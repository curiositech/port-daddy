## 1. `dag-chain-decomposition`

**Source and objective distinction.** The cited paper, “Minimum Path Cover in Parameterized Linear Time” ([arXiv:2211.09659](https://arxiv.org/abs/2211.09659), full HTML definitions and reduction sections opened), defines a path cover as paths such that every vertex appears in at least one path; paths can overlap. It explicitly distinguishes minimum path cover from minimum chain cover in the transitive closure (the latter uses vertex-disjoint chains). Therefore its broad “MPC = width” result is not the same as an edge-path cover that partitions vertices. Do not cite this paper as support for the direct-edge bipartite matching formula without qualifying the objective.

For a **vertex-disjoint path cover using original DAG edges**, make left/right copies of each vertex and include `u_L—v_R` exactly when the original graph has edge `u→v`. A matching with `m` edges selects at most one predecessor and successor per original vertex. Those selected edges form vertex-disjoint directed paths (and possibly cycles in a general digraph; acyclicity rules out cycles), with `|V|−m` path components. Conversely, every vertex-disjoint path cover with `k` paths supplies `|V|−k` such matching edges. Hence maximizing matching minimizes this specific cover objective. This is a short reduction/proof, not the result attributed to the overlapping-path paper. A **chain cover** instead uses reachability comparability (equivalently edges in the transitive closure) and has size equal to poset width by Dilworth; do not conflate with original-edge paths.

**Hand check.** In the bowtie `A→C, B→C, C→D, C→E`, overlapping paths `A→C→D` and `B→C→E` cover all vertices with 2 paths; this equals the reachability-poset width. A vertex-disjoint original-edge cover needs 3 paths: the bipartite matching can choose only one of `A_L—C_R` and `B_L—C_R`, and only one of `C_L—D_R` and `C_L—E_R`, for at most 2 matched edges; `5−2=3`. These are different valid answers to different objectives.

**Add to skill:** name the requested objective (overlapping path cover, chain cover under reachability, vertex-disjoint original-edge path cover, or schedule makespan) before choosing an algorithm; the last is not minimized by either cover count in general. State whether transitive closure is used and expose the reconstructed paths. **Reference proposal:** `references/path-cover-objectives-and-matching-reductions.md`, with the three definitions, proof above, worked bowtie, and counterexample to interpreting minimum path count as minimum makespan. Existing Chen stratification/virtual-node heuristics must be labeled separately from these exact definitions. **Diagram:** one bowtie shown as overlapping cover of 2 vs edge-disjoint cover of 3; original-edge bipartite matching and path reconstruction.

## 2. `dag-task-scheduler`

**Source and method.** Topcuoglu, Hariri & Wu, “Performance-Effective and Low-Complexity Task Scheduling for Heterogeneous Computing,” IEEE TPDS 13(3), 2002 ([author-hosted paper PDF](https://disco.ethz.ch/courses/fs14/seminar/paper/Jochen/4.pdf); paper body/algorithm inspected via PDF search result). HEFT computes an upward rank `rank_u(i)=avg(p_i)+max_{j∈succ(i)}(avg(c_ij)+rank_u(j))`; it schedules tasks in descending rank and assigns each to the processor yielding earliest finish time, inserting into the earliest idle gap where predecessors and transfer costs permit. It is a heuristic for a bounded heterogeneous processor set, not an optimal solver, and its averaged execution/communication estimates can mislead under highly variable LLM/agent durations.

**Hand check.** Suppose tasks `A→C`, `B→C`, two workers P1/P2, runtimes `A=(2,4)`, `B=(4,2)`, `C=(3,2)`, communication cost 1 only when predecessor and C use different workers. At time 0, schedule A on P1 and B on P2: both finish at 2; C on P2 must wait until B is done and A’s result transfers, so earliest C starts at 3 and finishes 5. Compare C on P1: A local, B transfer; earliest start 3, runtime 3, finish 6. HEFT’s assignment is C→P2 in this small scenario. If B is moved to P1, B takes 4 and C waits, finish at least 7. This is an illustrative deterministic instance, not an empirical benchmark.

**Add to skill:** distinguish ready-set generation from priority and placement; include communication, capacity reservations, deadlines, and uncertainty; describe how estimates update and when rescheduling is allowed. Replace arbitrary “2x wave overflow” rules with a policy objective and measured limits. **Reference proposal:** `references/heft-est-rank-and-insertion-scheduling.md`, including equations, hand trace, assumptions, and failure cases. **Diagram:** upward-rank calculation; earliest-gap placement with predecessor transfer.

## 3. `dag-cycle-analysis`

**Source and method.** Tarjan, “Depth-First Search and Linear Graph Algorithms,” SIAM Journal on Computing 1(2), 1972 ([SIAM article](https://epubs.siam.org/doi/abs/10.1137/0201010); abstract and metadata inspected; paper presents linear-time SCC algorithm). Use Tarjan SCCs in `O(V+E)` to diagnose a supposedly-DAG input: each SCC of size >1, or singleton with self-loop, is a cyclic component. Contract each SCC to one vertex; the condensation graph is a DAG. Preserve internal edges and node IDs so the condensation is a diagnostic projection, not a silent “repair.” The skill’s statement “DAG = undirected graph + directional metadata” is not generally a valid graph decomposition: a DAG may have an undirected cycle (diamond) yet its orientation remains acyclic, but direction is part of the graph data, not metadata that can be discarded without losing reachability.

**Hand check.** `A→B, B→A, B→C, C→D, D→C` produces SCCs `{A,B}` and `{C,D}`; condensation is `{A,B}→{C,D}`. A topological sort of the original graph fails, while the condensation succeeds. If the intent was a task DAG, stop and request a semantic repair of the two cycles; do not schedule the contracted components as though their internal work order were known.

**Add to skill:** separate DAG validation from the cited “cycle taxonomy” research and explain SCC condensation as diagnosis; identify edge direction semantics before transitive reduction. **Reference proposal:** `references/scc-diagnosis-and-condensation.md`, with iterative/recursive implementation notes and self-loop handling. **Diagram:** original cyclic graph to SCC condensation; true DAG diamond vs directed cycle.

## 4. `dag-confidence-scorer`

**Source and method.** Gneiting & Raftery, “Strictly Proper Scoring Rules, Prediction, and Estimation,” JASA 102(477), 2007 ([University of Washington technical record](https://stat.uw.edu/research/tech-reports/strictly-proper-scoring-rules-prediction-and-estimation); paper identity and abstract inspected). A probability forecast is evaluated against resolved outcomes with a proper score; for binary events the Brier loss is `(p−y)^2`, whose expected value is minimized by stating one’s actual probability under the assumed event distribution. This does not turn a rubric score or “reasoning depth” into calibrated probability. First define the forecast event (e.g. “will this output pass the specified verifier?”), collect outcomes, and assess proper score plus reliability by bins on a held-out time/task split. AUC/accuracy alone do not establish calibration.

**Hand check.** For forecasts `(0.8, 0.8, 0.2)` and outcomes `(1,0,0)`, losses are `0.04, 0.64, 0.04`; mean Brier loss is `0.24`. With only three observations, that is a worked calculation, not enough data to claim the “80%” bucket is calibrated. Keep “unknown/no comparable cohort” available.

**Add to skill:** remove fixed factor weights and accept/review thresholds unless validated on the target population; define event label, prediction time, resolution source, cohort and scoring window; calibrate separately by task family/model/evaluator and report uncertainty. **Reference proposal:** `references/confidence-as-forecast-calibration.md`, with proper-score equations, reliability table, and data requirements. **Diagram:** forecast→resolved outcome→calibration analysis; evidence factors versus independent validator/outcome.

## 5. `dag-dynamic-replanner`

**Source and method.** Temporal’s TypeScript workflow-versioning guide ([official docs](https://docs.temporal.io/develop/typescript/workflows/versioning), opened/read) explains deterministic workflow histories and the `patched`/deprecation pattern: preserve replay compatibility for histories created before a code change, then remove old branch only after no executions need it. Snakemake’s current CLI documentation describes rerun triggers for changed inputs, code, parameters, software environment, and timestamps, propagating reruns downstream ([official CLI](https://snakemake.readthedocs.io/en/stable/executing/cli.html), per parent’s live verification). These are distinct mechanisms: workflow-history compatibility vs dataflow invalidation. A replanner should version graph revisions and invalidate descendants whose declared inputs or assumptions changed, while retaining completed unaffected artifacts. Do not “retry with increased timeout” or “skip” by default: effects, idempotency and completion predicates decide.

**Hand check.** `fetch A→transform B→report C` and independent `fetch X→report D`. If A’s source revision changes, mark B and C stale and recompute; leave X and D valid. If only the report template changes, rerun C but keep A/B/X. A user-constraint change may instead alter the graph contract and require a new revision, not a cache invalidation.

**Add to skill:** define graph revision, input/code/config digests, affected-descendant calculation, checkpoint compatibility, effect boundary, and explicit disposition for old outputs. **Reference proposal:** `references/revisioned-replanning-and-invalidation.md`, with Temporal and Snakemake mechanisms contrasted and limits. **Diagram:** revision diff→affected descendants→new run; checkpoint reuse vs invalidate vs migration.

## 6. `dag-replay-debugger`

**Source and method.** Temporal’s versioning guide is primary implementation documentation (above); it establishes why deterministic workflow history must be replay-compatible across code changes. IPFS documentation explains content identifiers and Merkle DAGs: references identify encoded content, and changing a block changes the identifiers of ancestors ([content addressing](https://docs.ipfs.tech/concepts/content-addressing/), [Merkle DAG](https://docs.ipfs.tech/concepts/merkle-dag/), official docs opened/read). Combine these as a debugging protocol: freeze run ID, graph revision, code/prompt/model/tool configuration IDs, ordered event history, and content hashes for input/output artifacts; replay only deterministic orchestration decisions from that exact history. External effects should be mocked, denied, or reconciled; a content hash proves byte integrity under the chosen codec/hash, not authorship, truth, availability, or secrecy.

**Hand check.** An exact replay of `R1` uses the same workflow/code revision, recorded history, and the original recorded activity/tool results; it checks whether orchestration reconstructs the original decisions and outputs. It does not call the model again and generate a different response while still claiming to be the original replay. For a counterfactual, branch from R1’s checkpoint into new lineage `R1-CF`, change prompt `p1→p2`, and feed recorded or mocked tool/model responses under an explicit test harness; write new output `h(B2)` and compare with historical `h(B1)`. If a live model is called, label this as a new nondeterministic re-execution, not deterministic replay. Content hashes bind the artifacts in each lineage; they do not make the new branch historical truth.

**Add to skill:** separate historical inspection, deterministic workflow replay, counterfactual rerun, and live re-execution; include versioned provenance and effect policy. **Reference proposal:** `references/replay-manifest-and-content-addressed-artifacts.md`, with manifest fields and hash caveats. **Diagram:** event history plus artifact Merkle graph; replay lane with effect-denied tools and divergent result branch.

## 7. `dag-parallel-executor`

**Source and method.** Kotlin’s official coroutine guide states structured concurrency organizes child work in a parent/child tree: parent cancellation propagates to children; a lexical scope does not complete until children complete; child failure behavior depends on regular vs supervisor scope ([coroutines basics](https://kotlinlang.org/docs/coroutines-basics.html), [exception handling](https://kotlinlang.org/docs/exception-handling.html), official docs opened/read). This provides a useful lifecycle contract, not a direct prescription for Task-tool agents. The executor should create a scope per sealed wave, bind child attempts and cancellation tokens to it, gather every completion/cancellation/unknown state before closing, and distinguish fail-fast dependencies from independent children whose failures may be supervised. External side effects may outlive cooperative cancellation, so “cancelled” is not proof of effect rollback.

**Hand check.** Wave `{A,B}` feeds C. A fails; if A/B form a fail-fast atomic scope, request B cancellation, await terminal witnesses, then leave C blocked. If B is independent and useful, a supervisor policy may collect B’s successful artifact while still marking C blocked because A is required. Log the selected policy; do not infer cancellation from parent return.

**Add to skill:** replace model/time/token heuristics with capability and execution-policy rationale; define failure propagation, cancellation acknowledgment, join, timeout, and orphan handling. **Reference proposal:** `references/structured-wave-lifecycle-and-cancellation.md`, comparing fail-fast scope with supervisor scope and tool-backend constraints. **Diagram:** wave parent/children lifecycle; failure propagation tree vs supervised sibling.

## 8. `dag-hallucination-detector`

**Source and method.** FEVER (Thorne et al., NAACL-HLT 2018) defines claim labels `Supported`, `Refuted`, and `NotEnoughInfo`, requiring evidence for supported/refuted claims ([ACL Anthology](https://aclanthology.org/N18-1074/), paper record and abstract inspected). Its baseline pipelines retrieval, evidence selection, and claim verification; the authors report performance changes when correct evidence is required versus label-only, showing that verdicts without evidence can conceal retrieval failure. Use claim decomposition → source retrieval → minimal evidence set → entailment/contradiction/insufficient evidence. A 404 means the URL could not be retrieved now, not that the claim is hallucinated; a valid page likewise does not entail the claim. Numbers such as confidence 0.9 based on fetch success must be removed unless calibrated on labeled claims.

**Hand check.** Claim: “Version 2 launched before the migration completed.” Retrieved release note confirms launch date; migration status page says completion date after launch. Two dated sources jointly support the temporal relation. If the status page is absent, verdict is insufficient evidence, not false.

**Add to skill:** distinguish claim truth status from source retrievability, and separately report evidence coverage, source identity/date, entailment, contradiction, and unresolved/NEI. Evaluate evidence-set recall and verdict quality separately on a labeled set. **Reference proposal:** `references/claim-evidence-entailment-protocol.md`, with FEVER label distinctions, source-timestamp caveats, and a multi-hop example. **Diagram:** claim→evidence retrieval→evidence sufficiency→entail/contradict/NEI; citation resolution vs factual verification.

## 9. `dag-pattern-learner`

**Source and method.** Peters, Bühlmann & Meinshausen, “Causal Inference by using Invariant Prediction: Identification and Confidence Intervals,” JRSS-B 78(5), 2016 ([publisher article](https://academic.oup.com/jrsssb/article/78/5/947/7040653); article abstract/method description inspected). Invariant causal prediction tests whether a candidate conditional model for target Y remains stable across known environments; under the paper’s structural assumptions, invariant sets can identify direct causes and support error control. This does not validate causal conclusions from observational agent-run history with unobserved changes, selection, or dependent runs. For the skill’s pattern learning, make patterns predictive first; call them causal only after a designed intervention or defensible multi-environment invariance test.

**Hand check.** Historical logs show “parallel review” correlates with quality. Candidate confounder: parallel review was used only on high-risk tasks. Hold out a new project and stratify by risk; then randomly assign eligible comparable tasks to serial vs parallel review, fixing reviewer budget. If effect vanishes in holdout, store a risk-conditional association, not a universal “parallel improves quality” rule.

**Add to skill:** replace fixed recency/sample-count weights with outcome and population definitions; distinguish descriptive pattern, held-out prediction, and causal intervention; include negative results and environment/task stratification. **Reference proposal:** `references/held-out-pattern-and-causal-evaluation.md`, covering blocked temporal holdout, intervention design, and ICP assumptions. **Diagram:** execution log→candidate association→held-out prediction→optional intervention; environment-specific estimates and invariant intersection.

## 10. `dag-context-bridger`

**Source and method.** Cormack, Clarke & Büttcher, “Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods,” SIGIR 2009 ([Google Research publication record](https://research.google/pubs/reciprocal-rank-fusion-outperforms-condorcet-and-individual-rank-learning-methods/), bibliographic metadata and abstract-level claim inspected). RRF fuses ranked lists as `score(d)=Σ_i 1/(k+rank_i(d))`; it is a rank-fusion method, not calibrated relevance probability. Apply only after access/authority filtering and compatible dense-vector space validation. For bridging, use lexical, dense, and dependency/provenance rankings to produce candidate context, then preserve source/time/obligation labels and include omissions. Do not let compression erase a required counterexample or source qualification merely to hit token budget.

**Hand check.** Lexical ranks A=1, B=2; dense ranks B=1, C=2; with illustrative `k=60`, A gets 1/61≈.0164, B gets 1/62+1/61≈.0325, C gets 1/62≈.0161. B ranks first by cross-list support; this score is not a 3.25% or 97% confidence. If B is unauthorized, remove it before ranking and report the resulting gap.

**Add to skill:** replace token cutoffs and `>0.7` relevance with obligation coverage and task-specific budget; describe extractive preservation of quotes/constraints alongside generated summaries; mark excluded information. **Reference proposal:** `references/context-retrieval-fusion-and-loss-audit.md`, with RRF equation, filter ordering, compatibility, and summary-loss checks. **Diagram:** authority filter→multiple rankers→RRF→obligation coverage→compressed packet; original context fragments vs summary with traceable source links.

## 11. `dag-semantic-matcher`

**Source and method.** The same SIGIR 2009 RRF paper is exact primary support for rank fusion, not for arbitrary match-score cutoffs. Use a two-stage retriever: strict metadata/authority filtering first; parallel lexical and dense retrieval only within a compatible `spaceId`; fuse ranks with RRF; then rerank a bounded set against an explicit required-capability checklist and negative constraints. Output match evidence and gaps, not a single threshold presented as semantic certainty. Parent/root AGENTS policy makes this repository’s hybrid retrieval requirements local operator policy; that policy is not evidence that RRF alone is sufficient.

**Hand check.** Query asks “verify payment API signature and do not make a live request.” Skill X ranks 1 lexical and 6 dense; Skill Y ranks 4 lexical and 1 dense; RRF may rank Y higher overall, but a capability/effect check rejects Y if it permits live calls and has no verification procedure. Matching is about satisfiable constraints, not nearest wording.

**Add to skill:** remove adaptive numeric similarity thresholds; separate candidate recall, reranker precision, required capability coverage, exclusions, and abstention; use controlled test queries and human/ground-truth labels. **Reference proposal:** `references/authority-filtered-hybrid-skill-matching.md`, with RRF example, embedding-space compatibility, capability/negative-constraint rerank, and offline evaluation. **Diagram:** query constraints→eligible catalog→retrieval/fusion→capability/exclusion check→select or abstain; lexical/dense rank merge.

## 12. `dag-skill-registry`

**Source and method.** IPFS official documentation specifies content addressing using a CID that combines hash and codec; Merkle DAG nodes reference child blocks, so changes propagate to parent/root identifiers ([content addressing](https://docs.ipfs.tech/concepts/content-addressing/), [Merkle DAG](https://docs.ipfs.tech/concepts/merkle-dag/), official docs opened/read). Transfer this as registry artifact identity, not as a ready-made skill database: store immutable skill versions keyed by digest of canonical bytes/representation; maintain a separate mutable alias/index for name, channel, lifecycle, provenance and compatibility. A hash provides integrity detection, not author identity, trust, semantic quality, licensing, availability, or safe execution. The current body’s claimed latencies and precision percentages (e.g. exact lookup “100% precision,” capability-search ranges) require measured data and clear denominators; remove or mark them illustrative.

**Hand check.** `skill-id@v3` manifest lists body digest `h1` and reference digests `r1,r2`; changing one reference changes the manifest/root digest to `h2`. The alias `stable` may point to v3 or v4, but each run records the immutable digest actually loaded. Signature/trust metadata is verified separately from digest equality.

**Add to skill:** define immutable version identity, canonicalization, reference closure, signed provenance/trust policy, alias resolution snapshot, compatibility metadata, revocation and garbage collection; make every performance number measurement-scoped. **Reference proposal:** `references/content-addressed-skill-registry.md`, with manifest schema, digest limitations, trust/signature separation, and migration. **Diagram:** mutable discovery alias→immutable version manifest→content-addressed body/references; verification steps separating integrity, identity, authorization, and evaluation.
