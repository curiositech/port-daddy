## JADE: verified implementation mechanisms and corrections

**Per-agent behavior scheduling.** The official [JADE Programmer’s Guide](https://jade.tilab.com/doc/programmersguide.pdf), section “Agent Tasks: Behaviours” (guide text around pp. 20–23; PDF body inspected), describes one execution thread per agent and cooperative, round-robin, non-preemptive scheduling among that agent’s ready behaviors. An `action()` call yields when it returns; `block()` takes effect after return, and blocked behaviors can be restarted by message arrival, timer, or explicit restart. There is no saved Java stack: persistent computation state belongs in behavior/agent instance fields. This supports restoring `OneShotBehaviour`, `CyclicBehaviour`, `SequentialBehaviour`, `ParallelBehaviour`, and `FSMBehaviour` as explicit scheduling/composition tools. It does not support “thousands of agents,” no-lock, fairness, latency, or scaling guarantees. See also official [Behaviour API (JADE v4.6.0)](https://jade.tilab.com/doc/api/jade/core/behaviours/Behaviour.html) and [ParallelBehaviour API](https://jade.tilab.com/doc/api/jade/core/behaviours/ParallelBehaviour.html): `WHEN_ALL`/`WHEN_ANY` are termination conditions, not thread-parallel CPU execution. A concrete hand check: put a one-step state transition in `action()`, store phase in a field, return; if waiting for a message, call `block()` and return; never spin while awaiting input.

**Message matching and protocol behavior.** The official [JADE v4.6.0 MessageTemplate API](https://jade.tilab.com/doc/api/jade/lang/acl/MessageTemplate.html) supplies predicates/combinators over ACL header fields; a template routes an already received queued message to a behavior, but does not authenticate the sender, guarantee delivery/order, enforce a deadline, deduplicate, or make a conversation state machine. Pair a CFP’s `reply-with` token with the response’s `in-reply-to`, and include conversation ID/protocol/performative as appropriate. These values are correlation hints set by the application/protocol, not protected identities. `ContractNetResponder`’s official [JADE v4.6.0 API](https://jade.tilab.com/doc/api/jade/proto/ContractNetResponder.html) recommends a message template matching the protocol slot (a null template can consume every message); it provides callback/state handling for CFP, accept, reject, and out-of-sequence cases. Current API deprecates old `prepareResponse` in favor of `handleCfp`. Restore the initiator/responder callback workflow and state table, not claims that the protocol automatically chooses “best” bids or provides reliable cancellation/commitment.

**Hand-checkable Contract Net correction.** For two sellers, A has item and bids 32; B lacks item and sends REFUSE. The manager accepts A’s proposal; only A receives ACCEPT-PROPOSAL and later sends INFORM or FAILURE according to execution. B did not propose, so it cannot be the recipient of REJECT-PROPOSAL. The JADE SKILL example must change that event sequence as ROOT-HOLD.md directs. A price/deadline example is an application policy, not part of the protocol; remove the fabricated linear buyer/seller curves, production/OASIS proof, complexity claims, and universal “only proven approach” statement unless independently sourced and carefully scoped.

**DF/service discovery.** Official [DFService API (JADE v4.6.0)](https://jade.tilab.com/doc/api/jade/domain/DFService.html) explicitly says the convenience `register`, `deregister`, `modify`, and `search` calls block every activity of the caller until completion or exception. For nonblocking operation it points to `AchieveREInitiator` or `SubscriptionInitiator` plus `createRequestMessage`, `createSubscriptionMessage`, `decodeDone`, `decodeResult`, and `decodeNotification`. Restore both options and the responsiveness tradeoff. A useful recipe: register a `DFAgentDescription` with a service type/name; search a matching template; if continuous changes matter, subscribe asynchronously and process notifications. Results are service descriptions, not liveness, authorization, health, or guaranteed substitutes; revalidate before consequential use.

**Content/ontology.** Official [ContentManager API (JADE v4.6.0)](https://jade.tilab.com/doc/api/jade/content/ContentManager.html) describes filling/extracting ACL content using the declared language and ontology and registered codec/ontology objects, with validation support and codec/ontology exceptions for malformed or nonconforming content. This is a useful boundary between ACL envelope and content schema. It does not establish truth, permission, freshness, sender authority, or agreement on domain meaning. Restore a minimal sequence (register codec + ontology; fill/extract; handle `CodecException`/`OntologyException`) and label semantic checks as application policy. Delete invented BDI belief filters/“OntologicalAction” claims from JADE material unless tied to an actual cited library/API; those are not generic JADE guarantees.

**Split-container limits.** Official [JADE-LEAP User Guide](https://jade.tilab.com/doc/tutorials/LEAPUserGuide.pdf), “Execution modes” (PDF p. 7 and adjacent sections; body inspected), says a split container has a FrontEnd and BackEnd; a JADE container, not necessarily the Main Container, must already be active where the BackEnd is created, referred to as the Mediator; Main Container cannot be split; agent mobility and cloning are not supported on a split container. This is a deployment mode with specific LEAP assumptions, not a general edge/server architecture or generic durable reconnection/queue guarantee. Preserve the diagram and setup sequence only to the extent the guide documents them. Remove made-up RAM/battery/Lambda/JAR-size figures, invented connection-listener constants and persistence/buffering guarantees; do not assert disconnection survival absent an exact guide passage/version.

## Jason: verified reasoning-cycle mechanisms and corrections

**Event, option, intention.** The official author-maintained [Jason BDI Hello World tutorial](https://jason-lang.github.io/jason/tutorials/hello-bdi/readme.html), sections “Bob (the believer)” and “Bob (the vigilant)” (lines/sections on plan event, context, source annotation, and alternatives; full page inspected), gives a runnable path: initial belief/goal, event selection, matching trigger, context evaluation over current beliefs, plan instantiated as intention, then one body action. It demonstrates `tell` updates beliefs and creates `+belief` events, belief source annotations, and why a received `sincere(A)` assertion must be constrained to `[source(self)]` in a trust-sensitive example. This supports the useful event-trigger/context/plan-body model. It does not mean contexts are recomputed before every action or that running plans automatically switch when beliefs change; stale assumptions need explicit checks/failure handling in the body.

**Intention scheduling and concurrency.** Author-maintained [Jason Concurrency technical document (Zatelli, Hübner, Bordini, April 2016)](https://jason-lang.github.io/jason/tech/concurrency.html), sections Intentions, Concurrent Operators, and Conflicting Plans, says default intentions run round-robin one topmost plan-body element at a time, unless customized. `!g` is achievement subgoal executed in the current intention and suspends its caller pending completion; `!!g` starts a separate intention and caller proceeds; `|&|` is fork-join-and (both subgoals complete) while `|||` is fork-join-xor (first completion drops the other). Failure propagation differs by operator and whether a subgoal has its own failure plan. The `atomic` annotation prevents other intentions from running and can reduce reactivity. These are language/runtime rules, not wall-clock fairness or preemption guarantees; long Java actions/internal actions can still block the reasoning cycle.

**Failure and recovery.** Official author-maintained [Jason FAQ: plan failure](https://jason-lang.github.io/jason/doc/faq.html) (failure section; inspected around lines 449–489) documents that failed `+!g` creates `-!g` in the same intention; an applicable recovery plan can inspect failure annotations or `.current_intention`, clean up, and retry. Jason re-evaluates relevant/currently applicable plans rather than using only the originally captured alternatives, which adapts to changed beliefs but costs more applicability checks. The failed plan remains on the intention stack until its `-!g` handler completes; to prevent repeat attempts, track attempts in beliefs or customize option selection. Side effects already performed in the environment are not automatically undone. The FAQ explicitly notes that this mechanism is not formalized in the semantics. Restore those qualifications; delete blanket “automatic rollback,” “always tries alternatives,” bounded retry counts, or automatic recovery claims.

**Communication.** Official [Jason ACL performatives guide](https://jason-lang.github.io/jason/tech/performatives.html), full page inspected: `tell` adds a sourced belief; `achieve` adds a sourced goal; `unachieve` asks the receiver to drop the corresponding sourced goal; `askOne`/`askAll` query beliefs; `askHow`/`tellHow` transfer plans; `signal` adds an event and repeated signals can create repeated events. The page demonstrates synchronous `askOne` with a fourth variable argument suspending/resuming the sender’s intention. These are Jason’s interpreted speech-act conveniences, not authentication or a guarantee another runtime implements them. Restore syntax and effects with a two-agent example; include source annotations and timeout/failure handling where applicable. Explicitly warn that `tellHow`/plan import expands executable plan library and therefore needs an application trust policy.

**Procedural knowledge and selection policy.** The current [Jason programming patterns](https://jason-lang.github.io/jason/tech/patterns.html) document (sections on interleaving/singleton patterns; exact examples inspected) supports explicit patterns for serializing a goal using `.intend`, `.suspend`, `!!resume`, and `atomic`. It cautions that atomic execution can suppress unrelated intentions and hurt responsiveness for long work. Official [Jason API 3.3.0](https://jason-lang.github.io/api/) surfaces customizable `selectEvent`, `selectOption`, and `selectIntention` through the agent/transition system API; do not describe “first applicable plan always selected” as invariant: tutorial page gives a default ordering example, while the manual permits customized functions. Any priority, fairness, deadline, or retry policy is a customization/local design and should be demonstrated/tested.
