## windags-mutator
**Evidence.** Read full active skill and examples. Its L1-L4 mutation ladder, confidence cutoffs, 1.2x cost, Byzantine classification, and circuit-breaker thresholds are first-party heuristics, not externally calibrated results. Preserve concrete ladder/useful trace but label all thresholds as local defaults.
**Extension/example.** A transient tool timeout with an unchanged input permits bounded retry; repeated same counterexample after retry warrants feedback/redecomposition; topology redesign requires evidence of dependency/communication failure. Do not classify Byzantine solely from high confidence plus downstream failure. Keep raw failure trace, diagnosis rationale, expected cost, rollback, and independent verifier. Evaluate recovery strategy on fault-injected cases against cost/success outcomes.
**Diagrams.** Failure evidence→mutation selector with “unknown” state; mutation attempt/rollback/escalation lifecycle. Existing decision trees need review for unsupported numeric rules.
**Book candidate.** Escalation should depend on failure cause evidence rather than confidence alone; compare recovery chapter.

## windags-resilience
**Evidence.** Read active skill and 5 references. Fixed “retry same before feedback/model escalation” cost order and “no early starts before every node terminal” are local behavior policies; they can be wrong when deadlines or failure severity differ. Do not describe idempotent replay as cheaper universally.
**Extension/example.** Retry only when the operation is idempotent or protected by an effect key, the fault is plausibly transient, and retry budget/deadline permits it. E.g., read-only fetch may retry; ambiguous payment write enters reconciliation, not replay. Preserve completed outputs only if the checkpoint includes identity, inputs, version, and validated artifact. Measure successful recovery/cost/duplication over fault classes.
**Diagrams.** Node lifecycle and checkpoint/replay boundaries; error-class × recovery matrix with irreversible/ambiguous action hold. Existing state-machine diagrams likely useful; ASCII inventory still needed.
**Book candidate.** Recovery is a typed decision over effect idempotency, ambiguity, and evidence rather than retry-cost ladder.

## agentic-calendar-coordination
**Sources.** RFC 5545, *Internet Calendaring and Scheduling Core Object Specification (iCalendar)*, full body opened: https://www.rfc-editor.org/rfc/rfc5545/ . §§3.3.5, 3.3.10, 3.2.19 specify UTC/local+TZID/floating times and recurrence; a local time without TZID is floating, and ambiguous repeated DST time resolves per spec. Google Calendar Freebusy query (official API docs, full body opened) https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query supports interval-scoped busy data with narrow freebusy scopes; API errors can occur. Google does not imply free/busy is current or complete for all calendars.
**Extension/example.** Represent candidate as zoned interval, expand recurrence before overlap, query free/busy for only proposed interval, include errors/unknown calendars as unavailable/unknown, and request confirmation before booking. `America/Los_Angeles` recurring 09:00 remains local 09:00 across DST; do not add a fixed UTC offset. User can disclose busy blocks but event titles stay private. Test spring gap, fall repeated hour, travel timezone, stale/error freebusy, focus block.
**Diagrams.** Local recurrence→zoned occurrences→freebusy intersection; negotiation state machine with privacy and human confirmation. Convert ASCII failure trees.
**Book candidate.** Timezone-safe negotiation with an explicit privacy/minimum-scope data path; compare calendaring chapter.
