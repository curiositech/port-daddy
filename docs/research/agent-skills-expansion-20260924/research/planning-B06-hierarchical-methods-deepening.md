## Findings that govern all five

The word *hypertree* refers to materially different mathematical objects in the sources:

1. **Gui et al. HTP (2025)** uses a task-specific rooted acyclic generation structure. A rule maps one natural-language start node to a set of child nodes. Its “hypertree library” is `L=(G,q,R)`; a generating tree’s leaves belong to `G`, non-leaves are divisible rule-start nodes, and every parent-to-child-set branch is licensed by some rule (paper §3.2). It is a method for generating an LLM planning outline, not a hypergraph-width decomposition or a general task-network theorem.
2. **Gottlob, Leone & Scarcello (1998/2001)** use *hypertree decomposition* for a hypergraph/query: a rooted tree `T` with variable bags `χ(p)` and sets of covering hyperedges `λ(p)`, satisfying coverage, connectedness, special and descendant conditions; width is `max_p |λ(p)|` (survey §5, Definition 11). Bounded width supports tractability for specific CSP/conjunctive-query problems under the paper’s formal assumptions. It is not a natural-language task hierarchy or agent count.
3. **HTN** is hierarchical task-network planning with task/method semantics; none of these HTP claims should be attributed to HTN merely because both decompose tasks.
4. **Pilot hypertree execution** is first-party Port Daddy doctrine recorded in the skill changelog (2026-08-22). It uses “hypertree/context cluster” as an operational planning metaphor. Its `hard`/`order` edges, file ownership, worktrees, wave barriers and digest cap are policy choices, not consequences of the HTP or database hypertree definitions.

The small graph checks below are model examples, not evidence of performance. A rule connecting one parent to several children does not prove child independence; shared constraints or integration may couple them.

## `hypertree-planning`

### Primary method recovered

The relevant primary source is Gui et al., [*HyperTree Planning: Enhancing LLM Reasoning via Hierarchical Thinking*, arXiv:2505.02322v1](https://arxiv.org/abs/2505.02322), submitted 2025-05-05. The original skill and `_book_identity.json` call it a 2024 paper; correct the year. Full body read at [HTML](https://arxiv.org/html/2505.02322), especially §§3.1–3.2, 4.1–4.3, Algorithm 1, Figure 3, §5 and Appendices B–E.

The paper’s complete high-level pipeline is: (a) generate an outline `O` from query `q`, rules `R`, LLM `πθ`, reasoning depth `K`, expansion width `W`; (b) give `O` and any knowledge base `K` to the model, refine non-leaves using knowledge and iteratively expand leaves into solutions `C`; (c) generate final plan `P = πθ(Φ(C))` (§§3.1, 4.3, Figure 3). The outline alone is expressly incomplete when external knowledge is needed or leaves need deeper subtask reasoning (§4.3).

Algorithm 1, with the paper’s model-mediated choices kept visible, is:

1. Convert the rule set to divisible-node set `D`; initialize `H` to root query `q`.
2. For each depth `d=1..K`, map current `H` to candidate hyperchains `C1..Cm`.
3. If `m>W`, keep/filter to `W` hyperchains. The text names three pruning options: width-based, confidence/probability-based, or LLM-guided filtering (§4.2); do not imply one fixed scoring equation where the paper gives none.
4. For each retained hyperchain, ask the model which leaf nodes in it are divisible (`g1..gn ∈ D`), then select an expandable node `g*` in query/tree context.
5. Retrieve applicable rule(s) `r1..rP`, have the LLM instantiate each as a child set, and attach that set as one branch below `g*`.
6. Once depth expansion ends, prompt the LLM to select a final hyperchain as outline `O`. This is the outline path, not the final plan.
7. Run the separate self-guided planning and plan-generation stages above.

Construction’s four prose stages are selection, expansion, construction (repeat selection/expansion until no divisible leaves or iteration limit), and decision (§4.2). This preserves an important detail often erased by the bundle: a rule result is a *set of children attached together as a branch*; the algorithm also samples/selects among possible branches and then chooses a final path. It is not “independent parallel agents automatically solve all branches.”

### Source findings and hand-check

- The paper’s own simple formal example uses `G`, `q`, `R`, rules `g → c ⊆ G`, acyclicity, and divisible set `D`; use that definition rather than generic database hypergraph width (§3.2).
- Hand-check: let `G={Plan,Route,Lodging,Route-A,Route-B}`; root `q=Plan`; rules `r1: Plan→{Route,Lodging}`, `r2: Route→{Route-A,Route-B}`. `D={Plan,Route}`. A depth-1 expansion of `Plan` adds exactly `{Route,Lodging}` as a child-set branch; expanding `Route` adds `{Route-A,Route-B}` below Route. Every new non-leaf (Plan, Route) is a rule start; all leaves are in G; no child points back to an ancestor, so the generated structure meets the stated conditions. The graph says nothing about whether the two routes can be solved independently or reconciled with lodging.
- Results are benchmark- and setup-bound: TravelPlanner validation set has 180 queries; PlanBench Blocksworld and Mystery Blocksworld have 600 each; Natural Plan Trip Planning has 1,600 (paper §5.1, Appendix C.1). Table 1 reports 20.0% GPT-4o HTP / 36.1% Gemini-1.5-Pro HTP TravelPlanner success, versus corresponding non-HTP baselines shown there. Table 3’s GPT-4o TravelPlanner ablation reports 20.0 HTP versus 6.1 without division and 8.3 without self-guided planning; this does not establish a universal “structure is the main cause” across tasks. The paper’s 3.6× statement is Gemini-1.5-Pro HTP against o1-preview on TravelPlanner in its Table 2 setup, not a general model multiplier (abstract, §5.3). It also reports specific per-dataset comparisons in §5.2; the skill’s blanket “2.8× vs. 1.3–1.8×” phrasing needs to retain the paper’s GPT-4o, task pairings, and comparator basis (§5.2).
- The skill’s numerical per-step error illustration is elementary arithmetic, not HTP evidence: for independent per-step error ε=.02 over 60 steps, `1−(1−.02)^60 = 1−.98^60 ≈ 0.7024`. Independence and constant error are assumptions; this is not a measured cumulative error rate. `log₄(60)≈2.95` is a balanced-tree depth illustration, not a result for HTP’s rule-derived outline.

## `operad-task-decomposition`

### Primary method and scope

The entire original `SKILL.md` and its changelog, scorecard and one decision diagram were read. This recently-written bundle already states the core boundary accurately. Anchor the method in these primary texts:

- David I. Spivak, [*The operad of wiring diagrams: formalizing a graphical language for databases, recursion, and plug-and-play circuits*](https://arxiv.org/abs/1305.0297), v1 2013-05-01, especially §§2 (operads, operad functors/algebras), 4 (typed wiring diagrams), 5 (plug-and-play and recursion). It explicitly models wiring diagrams as operad morphisms and discusses a relations algebra/database queries and circuit special cases (abstract; §2 and §§4–5).
- Brendan Vagner, David I. Spivak & Eugene Lerman, [*Algebras of Open Dynamical Systems on the Operad of Wiring Diagrams*](https://arxiv.org/abs/1408.1598), v1 2014 / journal 2015, especially §§2–4 and its stated open-dynamical-system algebra. It defines a particular symmetric colored operad/multicategory and compatible semantics for composing interconnected smooth open systems; it is not a general agent-task correctness result.
- Leinster, *Higher Operads, Higher Categories*, Chapter 2, for operad/multicategory definitions; Fong & Spivak, *An Invitation to Applied Category Theory*, §§5.2.2 and 6.5.1–6.5.3, separately for acyclic port graphs and operads/algebras/SMCs. Do not collapse the acyclic port-graph definition into a universal property of operads.

### Hand-checkable composition trace

Use the skill’s declared signatures `g:(A1,A2)→B`, `h:(X)→A1`, `f:(B,C)→D`, and identity on `A2,C`. Substitution yields `f∘(g,id_C)` with inputs `(A1,A2,C)` and output D; then substituting `h` into the A1 slot of g yields `(X,A2,C)→D`. The two ways of parenthesizing these *same substitutions with same slot map* are equal by operadic associativity. At the Set algebra level choose `A1=A2=B=C=X=D=ℤ`, `h(x)=x+1`, `g(a1,a2)=a1+a2`, `f(b,c)=b×c`; with `(x,a2,c)=(2,3,4)`, both groupings compute `((2+1)+3)×4 = 24`; right grouping `g(h(2),3)=6`, then `f(6,4)=24`. Both yield 24. (The expression, slot order and actual arithmetic have been checked.) This verifies only that interpretation of this formal composite agrees under the functorial composition; it does not license changing operations/effects or prove an implementation obeys them.

The skill’s layering of formal syntax, compatible interpretation, implementation, observations is useful. Keep its explicit distinction among colors-as-artifact-sorts and colors-as-box interfaces, sharing/effects, and runtime scheduling. Operad axioms include units, associative substitution and symmetric actions/equivariance; they do not give a universal “five inputs” limit. Acyclicity is this skill’s outer workflow restriction, not a theorem that every operad/wiring system is acyclic: Spivak explicitly treats recursion, and feedback is in scope for other grammars.

## `stanton-2006-hierarchical-task-analysis`

### Primary body read; corrected method

Full author-uploaded paper text was available at [ResearchGate author full text](https://www.researchgate.net/publication/7622539_Hierarchical_task_analysis_Developments_applications_and_extensions), DOI [10.1016/j.apergo.2005.06.003](https://doi.org/10.1016/j.apergo.2005.06.003), Stanton, *Applied Ergonomics* 37(1), 2006, pp.55–79. Read sections 1–3, including Figures 3 and 5, framework heuristics and stopping criterion, plus examples/extensions. This replaces the prior baseline’s abstract/excerpt-only limit.

Stanton §2 repeats Annett et al.’s three principles (1971, p.4): (1) choose a task/operation at the highest level and define its goal in real objective terms (production, quality, or another criterion); (2) decompose into suboperations, each with subgoal and measurable contribution/performance standard; (3) operations and suboperations stand in hierarchical inclusion, while the plan gives attainment rules; sequence is common but not universal. HTA is goal-based systems analysis and applies to team/nonhuman systems too, not just documenting what a person does (§2).

Primary procedure to preserve from Stanton §3 / Figure 5: define the analysis purpose and system boundary; consult a variety of sources (observation, subject-matter experts, interviews, manuals, walkthroughs, simulation) and record sources; define the overall goal in a task statement; state subordinate goals; write plans that specify the conditions/sequence/control rule by which subgoals satisfy the parent; check whether the redescription is adequate and revise as needed; iterate over each subgoal, asking whether further redescription is warranted; terminate a goal when additional detail is not fit-for-purpose, mark lowest-level terminal subgoal (underline or `//`), and verify/revise with SMEs. Stanton presents diagram/list/table forms and notes plan rules are not restricted to fixed sequence: fixed, contingent, parallel, free order, cyclical, and selection forms appear across the paper (§3, Tables 8–9; Figure 5).

P×C: §3 explains the classic probability-of-failure `P` × cost-of-failure `C` rule as one rough stopping heuristic (the source glyph is corrupted as `P!C` in the extracted text). Stanton says analysts have trouble quantifying P and C, says stop level depends strongly on purpose, and recommends stopping before further detail ceases to be useful; team HTA can stop at the information-exchange subgoal when that serves the purpose. Do not put an invented score, “acceptable” threshold, or probability-of-inadequate-performance variant in Stanton’s mouth. Purpose-fit and explicit terminal marking are the reproducible workflow; P×C is a subordinate heuristic, not a universal quantitative cutoff. A no-solution heuristic is discussed later as Marsden & Kirby’s proposed alternative for function allocation, not Stanton’s canonical rule (paper §5).

### Miniature trace (checked against Figure 3’s method)

Goal 0: “Make nail flush with wood surface, without damaging it.” Subgoals: `1 Test nail`; `2 Hammer nail`. Plan 0: if test says flush, stop; otherwise do 2 and retest via Plan 2. Plan 2: test whether hammer is raised; if not, lift hammer (2.1); strike nail (2.2); test nail (2.3); repeat 2 while nail protrudes, exit when flush. The local skill example should present this as a source-faithful control loop, not a linear checklist. If the analysis purpose is interface requirements, further decompose the test/action subgoal and record information/input-feedback needs; if only training-level phases matter, mark the detailed action subgoals terminal. No P or C numbers can be calculated from the paper example.

## `task-analysis-of-pier-side-ship-handling`

### Correct original identity and tested method

Primary source obtained as the full original 152-page public-release [Naval Postgraduate School thesis PDF](https://upload.wikimedia.org/wikipedia/commons/c/cc/A_task_analysis_of_pier_side_ship-handling_for_virtual_environment_ship-handling_simulator_scenario_development_%28IA_taskanalysisofpi00gras%29.pdf): Charles R. Grassi, Lieutenant USN, *A Task Analysis of Pier Side Ship-Handling for Virtual Environment Ship-Handling Simulator Scenario Development*, M.S. thesis, Naval Postgraduate School, September 2000; advisors Rudolph P. Darken and Barry Peterson (title page, printed pp. i–ii). The skill’s `_book_identity.json` substantially overstates the source’s implications; keep the exact identity but replace generalization prose with source-bounded findings.

The thesis body was read, especially §§II.D–F (cognitive task analysis, GOMS, its shortfall, CDM/CCI), IV (development, scenario, validation), V (two task analyses and cue inventories), VI (limits/recommendations), Appendix B. It models exactly two pier-side evolutions: getting a ship underway from pier and mooring to pier (Ch. I; IV.B; V). The source workflow is concrete:

1. Review general ship procedures/training material, including NAVEDTRA 10776-A and two ships’ commanding-officer standing orders; form an initial GOMS-like model.
2. Have one experienced ship-driver SME review/refine it with task detail absent from written procedures.
3. Construct separate generic, bounded GOMS-like models for the underway and mooring evolutions. Each task level records goals, operators, methods, and selection rules. It shows unit-task, functional-task, detailed-task levels (Ch. V); goals may be recurring, such as maintaining a picture of ship motion/distance, not only once-through steps.
4. Map each Critical Cue Inventory to the GOMS subgoal it informs. For every cue, record what cue indicates/why it matters and the visual/audible identification path (CCI table examples in Chapter V.C, printed pp. 102–112).
5. Validate and amend the model using CDM interviews with five qualified SWOs: experienced with twin/multiple-screw ships, at least ten underway/mooring evolutions, recently returned from sea assignment; use questionnaire and physical foam-core ship/pier aid; elicit their walk-throughs and alternative viewpoints; revise the model and cue inventories (Ch. IV.C, Appendix B; five participants at printed pp. 47–50).

The source makes a precise representational point: GOMS supplies logical method/selection-rule sequence; by itself it does not reveal the perceptual information/implicit knowledge behind a choice (Ch. II.E.2, printed pp. 19–20). CCI complements it; CCI is not a general “agent sensor architecture.” The source found cues like changing ship/pier separation, swing-rate, wake/water churning, engine-stack smoke, engine sound and EOT acknowledgement in the specific model (Chapter V.C, Tables 1–15). Do not claim every decision has independent redundant sensors: the thesis catalogs particular cues and sometimes alternatives/cross-checks; it does not prove independence or a universal rule of two channels.

### Example / validation counterexample

One source-backed cue row: for goal `Determine_If_Engine_Order_Was_Executed`, CCI lists stern water churning, stack smoke plume, engine acceleration sound, and EOT acknowledgement; the table describes them as cues to check order execution (Chapter V.C, Table 6, printed p. 106; PDF scan page 121). This is a cue inventory, not a probability/fusion model; a simulation mapping may select one or more available cues but must label that as design work.

Grassi offered an optional tug in the scenario while the initial task model assumed no tug. All five selected validators chose the tug. In the final return/model-comparison interview, all five found the model inaccurate without tug procedures; Grassi revised it accordingly (Ch. IV.C, printed p. 50; PDF scan page 65). This is a useful observed assumption correction for this scenario and sample, not evidence of universal tug practice or a rule that one expert is systematically incomplete. The source distinguishes generic CDM's three passes (Ch. II.F) from this study's four enumerated steps (Ch. IV.C): scenario in advance, uninterrupted account, phase-by-phase probes, then a later appointment to compare formatted accounts with the initial model. The study paragraph calls them three phases but enumerates four; retain the actual sequence and its later model-review timing. The tug finding arose in that final comparison, not merely a hypothetical probe. The conclusion limits the model to generic, simple scenarios rather than all ship-handling methods or situations (Ch. VI, pp. 113–116). This is simulator scenario-development research, not operational ship-handling advice.

Hand-check for the method: a single task row has one goal and four candidate cues above. The CCI can be checked by asking for each cue: (a) which goal/method/selection point does it support? (b) what does the observer see/hear? (c) what does it indicate? The engine sound cue maps to order execution; it is not by itself proof that engine order was received or that the ship response was correct. Use validation to find missing, ambiguous, or scenario-inapplicable cues; do not assign unsupported numeric reliability or treat correlated smoke/sound/water cues as independent channels.
