## Primary source set and inspection depth

1. **Balegas et al., “Extending Eventually Consistent Cloud Databases for Enforcing Numeric Invariants,” SRDS 2015, arXiv:1503.09052 v1 (2015-03-31).** [Pinned arXiv record](https://arxiv.org/abs/1503.09052v1) and [full proceedings PDF](https://asc.di.fct.unl.pt/~nmp/pubs/srds-2015.pdf), read §§I–V, especially system model, bounded-counter invariant, local-rights operations and evaluation. For a lower-level transaction antecedent, **O’Neil, “The Escrow Transactional Method,” ACM TODS 11(4), 405–430 (1986), DOI 10.1145/7239.7265**, [author PDF](https://cs.umb.edu/~poneil/EscrowTM.pdf), read the abstract, transaction architecture and distributed-transaction example (pp. 405–430). Escrow treats an invariant budget as allocatable rights and reserves rights before work; pending/ambiguous work holds resources. These are transaction/counter methods, not an LLM billing implementation or guarantee about a model vendor’s final invoice. Balegas’ evaluated system is a Riak prototype with an eventual-consistency model and explicitly defined failure assumptions.
2. **Debenedetti et al., “Defeating Prompt Injections by Design,” arXiv:2503.18813 v2 (2025-06-24).** [Pinned v2 HTML](https://arxiv.org/html/2503.18813v2) (equivalent [PDF](https://arxiv.org/pdf/2503.18813v2)), read §§2–6, explicit non-goals, capability/interpreter design, evaluation, overhead and discussion. CaMeL isolates privileged planning from quarantined untrusted-data parsing, tags values with source/reader capabilities, propagates a data-flow graph, and checks policy at tool calls. Crucial limit stated in §3: it assumes trusted user query and uncompromised memory; it does not solve arbitrary text-only misinformation/phishing or remove need for clarification. On AgentDojo it reports security/utility trade-offs in that benchmark, not universal immunity.
3. **Dong et al., “Memory Injection Attacks on LLM Agents via Query-Only Interaction,” NeurIPS 2025.** [Official NeurIPS proceedings PDF](https://papers.nips.cc/paper_files/paper/2025/file/42a97bbd9844d2bf68596730af80bcdf-Paper-Conference.pdf), full 35-page paper read, especially threat model, attack construction, experiments/defenses, limitations and impact statement (pp. 1–10 plus appendices). MINJA demonstrates that query-only interactions can induce a memory-writing agent to store a poisoned demonstration using bridging reasoning and progressively shortened prompts; it evaluates several agents/tasks. It tests a defined shared-memory/retrieval architecture and attacker constraints. Its reported success rates are experimental results for those setups, not a probability that any persistent memory is poisoned. The paper recommends memory isolation, authentication, secure memory management and filtering; it does not establish any one control as sufficient.
4. **Guo et al., “Certified Data Removal from Machine Learning Models,” ICML 2020, PMLR 119, 3832–3842.** [PMLR paper page](https://proceedings.mlr.press/v119/guo20c.html) and [full paper PDF](https://proceedings.mlr.press/v119/guo20c/guo20c.pdf), read the full 11-page paper: formal definition, algorithm, assumptions, experiments/discussion. “Certified removal” is a formal indistinguishability guarantee after removal; the proposed practical mechanism applies to specified linear classifiers/settings. It is not a general-purpose deletion guarantee for conversation rows, embeddings, backups, provider logs or arbitrary foundation models. Use it to make clear that deleting an input record and removing its learned influence are different problems.
5. **Schlegel & Sattler, “Capturing End-to-End Provenance for Machine Learning Pipelines,” Information Systems 132 (2025), article 102495, DOI 10.1016/j.is.2024.102495.** [Author/institution-hosted full text](https://www.db-thueringen.de/servlets/MCRFileNodeServlet/dbt_derivate_00068998/0306-4379_132_2025_102495.pdf), searched and read the body (methods §§2–4, Git/MLflow creation/change/deletion submodels, example provenance queries and evaluation). MLflow2PROV constructs W3C-PROV-aligned lineage linking Git/MLflow entities, runs, artifacts and lifecycle operations so a derived artifact can be traced and queried. This is provenance capture for ML development pipelines; adapting the graph to episodic memory deletion is a proposed application, not a result of the paper. Capturing a deletion event is not proof every copy or derivative was erased.
6. **Xu, Dai & Yan, “Identity Disclosure and Anthropomorphism in Voice Chatbot Design: A Field Experiment,” Management Science 72(1), 223–241 (2026 issue; published online 2024-08-26), DOI 10.1287/mnsc.2022.03833.** [Publisher page](https://pubsonline.informs.org/doi/10.1287/mnsc.2022.03833), full abstract, field setting/design and citation metadata inspected; full methods and appendix were not available in the opened view. The abstract reports randomized assignment of 11,000 truck drivers in an outbound voice-chatbot logistics-dispatch setting and operational-response differences under disclosure and voice features. This narrow commercial field study is not evidence about companion dependence, clinical effects, children, older adults, or vulnerable groups. Use only to motivate a context-specific hypothesis and evaluation; no universal advice follows.

## Findings mapped to the root hold

### 1. CostGuard: reservation, settlement, concurrency and uncertain outcomes

**Source-grounded method.** Balegas et al. formalize a bounded counter by splitting spendable rights among replicas; an operation proceeds only if its replica owns sufficient rights, preserving the aggregate invariant despite concurrent updates. In a local application, the simplest equivalent is an atomic ledger transaction (not a mutable in-process counter). O’Neil’s escrow method provides the transaction intuition: reserve rights before a long-running operation, preserve recoverable intermediate state, and commit or abort later.

**Candidate illustrative admission algorithm (not a provider cap).** Define each request’s conservative application-side reserve `r` from the configured model/rate snapshot, known input token count, a hard output-token ceiling supported by the called API, and any locally known fixed charges. In one serialized/atomic transaction: reject if `settled + active_reservations + r > local_period_limit`; otherwise create a unique request record and reserve `r`. Submit with a stable idempotency key where the provider supports it. On a definitive response, reconcile against returned usage, move actual observed usage to settled, and release unused reserve. On timeout/connection loss/unclear provider status, mark `UNKNOWN`, retain the reservation, and reconcile via provider request status/usage before retry or release. A retry reuses the operation identity; it must not create a second budget reservation or silently repeat an effect. If remote execution cannot be queried, retain the hold or require operator reconciliation under a declared policy. This prevents local concurrent admissions from overspending the *local reserved ceiling* only if every relevant call uses the atomic ledger and `r` bounds actual billable usage; price changes, hidden provider charges, non-token charges, settlement delay, and provider-account activity outside this ledger remain outside the guarantee. Never label an estimated token amount a provider spend cap.

**Hand-checkable example.** Local cap $10; settled $6; two workers simultaneously seek $3.50 each. An atomic reserve admits one ($9.50 total) and rejects/defers the second. A mutable read-then-increment counter could admit both because each sees $6. If the admitted call times out after submission, preserve its $3.50 hold as unknown; releasing it on timeout would permit overshoot if the provider completed the call.

**Replace/currently retain.** Replace the sample `CostGuard` behavior claiming “prevents” spend, its WARN-per-request path, unsynchronized counters, `estimated_output` as spend ceiling, and monthly field without enforcement. Retain workload cost arithmetic, dated model/rate inputs, model-cascade/cache/context/batch/output optimization choices, and monitoring ideas, but describe controls as local policy and observed measurements. Replace YAML alert thresholds with named configured states and owner-defined thresholds; a threshold alone is not a hard bound.

**Tests / diagram.** Tests: concurrent admission at the boundary; duplicate operation key; crash between reserve/provider submit/settle; provider timeout after successful remote execution; over-reservation; usage reconciliation; price/model revision change; separate external-account spend. Diagram: reservation lifecycle (`unreserved → reserved → submitted → settled/released`, `submitted → unknown → reconciled`) plus invariant chart showing `settled + outstanding reserves ≤ local cap`.

### 2. Capture, meeting authority, and consent

**Control design, not legal conclusion.** Disclosure is not a blanket authority record. Put a capture gate before sensor/API activation: default disabled; enable only for a named channel, purpose, actor/account, data scope, retention rule, and authority/notice state established by the deploying organization’s configured process. Record a per-session/per-source receipt. If the policy does not affirmatively authorize capture, do not collect; post-capture OCR exclusions cannot undo capture. For meetings, own screen/audio can still contain participants’ content, credentials, or shared material. “Owner enabled ambient capture” cannot authorize every third-party record. Pause and collection-stop controls must stop new acquisition, not just summarization.

**Retain and sharpen.** Retain the input inventory and the insight that multi-source aggregation changes risk. Remove “always capture own speech/screen”; replace meeting YAML with channel-level default-off policy and distinct fields for authorization source, notice/check result, allowed data classes, purpose, session expiry and negative tests. Do not state what consent law requires; require current qualified review for a deployment’s jurisdiction and role.

**Tests / diagram.** Test unconfigured source denied before camera/mic/OCR starts; policy expires mid-session; screen includes another person’s speech/message; user pause stops all acquisition; service reports exact active channels. Diagram: configured authority → source-specific admission → collection → pause/stop; separate actor/source/purpose matrix from post-capture redaction pipeline.

### 3. Encryption, pgcrypto, keychain, hashing and local bind claims

**Source correction.** The current skill names SQLCipher/pgcrypto, OS keychains, localhost binding and hash-on-write as if those labels themselves prove whole-database protection, key isolation, network confinement, or integrity. The cited methods set does not validate those products. Keep no unsupported feature-level assertion: either link exact official product documentation and state scope (for example, extension-level field crypto vs volume/database encryption, key management and memory exposure), or use technology-neutral requirements.

**Concrete requirement set.** State attacker capability: offline stolen disk vs process compromise vs same-user access vs privileged host attacker vs remote network client vs backup operator. For each asset, specify confidentiality/integrity/availability control, key location/rotation/recovery, network reachability, backup handling and verification evidence. A digest stored beside mutable data detects accidental mismatch only if the expected digest is held in a separately protected trust domain; an attacker able to replace both can forge a matching pair. A local bind is a network exposure reduction under the tested host configuration, not a defense from local processes. These boundaries are engineering deductions; do not cite them as proof of a named package guarantee.

**Retain / tests / diagrams.** Retain placement choice (local/cloud/hybrid) and compromise inventory. Replace product checklist claims with asset-threat-control-evidence rows. Tests: independent key compromise scenario, process-level read, remote socket scan from declared interfaces, changed payload plus changed adjacent hash, backup restore, revocation/rotation. Diagram: attacker capability × control boundary matrix; key/data flow from capture through encrypted storage, backups and restore.

### 4. Anthropomorphism, reliance, and vulnerable-population assertions

**Evidence boundary.** Remove “don’t give a human name,” “third-person wording helps,” and categorical population-specific predictions as established protective effects. Treat interface choices as testable hypotheses. The Xu et al. field experiment shows that disclosure and anthropomorphic voice cues had different operational outcomes in one logistics calling context; it did not measure dependency, mental-health outcomes, children, or durable companion interaction. This evidence cautions against universalizing in either direction.

**Replacement method.** Keep user controls and human-centered evaluation, but specify a preregistered/context-defined research question, participant population and recruitment limits, exposure duration, comparator interaction styles, outcome measures (e.g., user understanding of AI identity/capabilities, voluntary disclosure, control comprehension, unwanted interruption, ability to pause/exit, user-reported reliance), adverse-event stop/escalation protocol, and independent ethics/research review where appropriate. Report observed outcomes with uncertainty; do not diagnose or infer that a group is inherently vulnerable. Make functional naming, first/third-person language, emotion cues and disclosure timing experimental factors, not prescriptions.

**Tests / diagrams.** Test whether participants can identify system identity and limits after use; comprehension and opt-out success; report outcomes by prespecified cohorts only when supported and safe to analyze. Diagram: user-control lifecycle (configure, inspect, pause, resume, delete); study design with intervention/comparator, measures and stop criteria. Candidate Book angle: interaction-style effects on comprehension and user control, only after a controlled study with open protocol and clear population boundary; no novelty or efficacy claim now.

### 5. Prompt injection in persistent memory

**Primary evidence.** MINJA gives a concrete attack chain: attacker queries a shared-memory agent, induces it to store bridging reasoning, progressively removes telltale prompts, then relies on retrieval to influence a later matching query. This substantiates a *possible threat under the paper’s system/attacker model*, not inevitable persistence or cascade. CaMeL gives a complementary control method: distinguish control flow (trusted plan) from untrusted data flow; parse untrusted content in a tool-less/quarantined model; propagate provenance/capability labels; check recipients and policy at every tool call. CaMeL explicitly assumes memory is not already compromised, so it cannot alone resolve MINJA’s durable-write path.

**Repair.** Change “injected instructions persist” and “poisoning cascades” from categorical outcomes to threat scenarios, then specify whether the implementation has shared memory, automatic writes, retrieval demonstrations, cross-user access, and what adversary access is assumed. Require memory writes to carry source/user/tenant/session/trust class, and to be policy-gated separately from retrieval; isolate tenants, prohibit untrusted text from authorizing durable memory or tool effects, maintain delete/correction lineage, and enforce tool capabilities independent of model instructions. No classifier or prompt wording is a containment proof.

**Example/test.** Seed a test agent with harmless shared memory and a synthetic adversarial query that tries to induce a later retrieved instruction; measure whether it is persisted, retrieved, changes output, and causes a prohibited tool effect. Run distinct checks for cross-tenant retrieval, poisoned input without durable write, durable write without execution, direct user prompt injection, and misparsed innocent data. Diagram: injection path query→candidate memory→trust/write gate→retrieval→quarantined parsing→capability check; separate memory provenance/trust-state transitions. Use MINJA’s exact evaluated assumptions when interpreting results.

### 6. Containment and stop semantics

**Method implication.** A stop request is a command sent, not evidence that every local and remote effect is fenced. CaMeL’s interpreter halts its own next tool call when a policy check fails; that boundary does not reverse a remote tool call already in flight. The staged draft’s `Detected → Contained` edge therefore overstates what a stop request alone proves.

**Replace with observable state machine.** `normal → detection_recorded → stop_requested → fencing_in_progress → contained_verified` only after independently reading back disabled local scheduler/credentials/egress/tool admission and verifying no admitted new effects. Add `partial_or_unknown` when remote in-flight calls, queued jobs, provider tasks, delayed callbacks, or side effects cannot be queried/fenced. Preserve a separate `collection_stopped` fact. Continue/restrict/stop is an explicit policy branch before the sequence: for continue, do not emit “fenced”; for restrict, record exact capability removals; for stop, attempt fence. Safe restart requires a fresh authorization/policy check, recovery of pending operations, and owner receipt; it is not implied by incident closure.

**Tests / diagrams.** Inject stop during queued, running, timed-out and remotely accepted operation; verify no new effect passes the admission boundary and classify prior operation as completed/cancelled/unknown. Exercise independent stop channel failure. Diagram: detection/request/fencing/verified-vs-unknown state machine; sequence with local agent, tool gateway, remote provider and independent readback. Report exact observation boundary.

### 7. Approval policy and existing delegation

**Method boundary.** Keep the approval gate for actions outside existing authority, high-impact actions not covered by delegation, or actions whose consequences/reversibility exceed the declared scope. Do not convert the checklist into a rule that asks permission for every operation: already-authorized, reversible actions within scope continue without repeated approval. CaMeL’s capability example illustrates policy-gated tool use; it asks approval when an email recipient is not known to have permission to read the document, not as a universal approval prompt for all tool calls.

**Add decision rule.** Before an effect: identify delegated authority/scope; classify effect and reversibility; if within explicit authority and reversible, execute with scoped logging; if outside scope, destructive/high impact, or authorization evidence is missing, block that effect and route a concise approval request. The agent may still do authorized read-only preparation. Record the exact reason and the narrow action requiring approval.

**Tests / diagrams.** Pair cases: preauthorized reversible edit vs undelegated external send; authority expired; target changed after review; approval binds to exact operation/recipient/data. Diagram: authority-scope-consequence decision table; action lifecycle from draft to exact-bound approval to effect/readback.

### 8. Audit logs: purpose, minimization, retention, and authority

**Primary methods.** Schlegel/Sattler’s provenance approach captures relationships between activities and artifacts, including creation/change/deletion, so lineage queries answer “what came from this item?” Guo et al. show that removing a model’s learned influence requires a formal model-specific procedure, not simply deleting a record. Together these support two distinctions: an audit log should prove scoped operation/lineage without being a second raw-content store, and deletion of raw data does not itself prove deletion of all descendants or learned influence.

**Repair.** Replace “log every memory operation” with a purpose-scoped minimal event ledger: event ID, actor/authority decision reference, source class (not source payload), operation type, artifact IDs/parent IDs, policy/version, time, outcome/readback, retention class and deletion state. Store raw content only when independently justified for an explicit purpose and retention window; avoid raw transcripts, screen content, secret values, and copied prompts in default logs. “ambient_capture_enabled” is a configuration bit, not proof of authority over a particular third-party record. Use separate access controls and retention for the audit plane; logs can themselves be sensitive. A content hash alone is neither provenance authentication nor deletion evidence.

**Deletion/readback workflow.** Enumerate source and descendants (transcript, summary, entity/fact, embedding/vector entry, search cache, backup snapshot, export, provider-side copy where controllable). Execute scoped deletion/tombstoning/rebuild at each store; read back by stable IDs and verify absence/blocked access after cache invalidation and restore path. Record any unqueryable or immutable copy as `deletion_pending/unknown` with owner/review route, not “deleted.” If content influenced model weights, distinguish that from storage deletion; Guo et al.’s certification is for its specified linear-classifier mechanism, not arbitrary LLM unlearning.

**Tests / diagrams.** Test delete one source item, confirm every declared derivative and cache is absent, test backup restore cannot resurrect it, and make unknown providers explicit. Test tampered audit event and adjacent digest. Diagram: provenance DAG with source→derivatives→deletion/readback states; minimal event receipt schema and separate raw-data retention plane.

## Cross-cutting source gaps, preservation, and candidate evaluation

- Preserve the skill’s five hazard categories, cost arithmetic, optimization table, scope discipline, control/opt-out ideas, privacy inventory, incident response, and claim→control→test→evidence safety-case framing. Tighten them to explicitly illustrated/local policies rather than replacing the knowledge with a generic warning list.
- Remove unsupported vulnerable-population stereotypes and blanket anthropomorphism prescriptions. Preserve the question of user reliance as an open interaction-design hypothesis with target-specific controls, not a diagnosis or clinical protocol.
- Current provider prices, endpoint semantics, keychain/pgcrypto scope, retention/deletion rights, recording/consent rules, and platform/runtime behavior need exact current primary documentation and deployment evidence before a named claim. This report did not audit those claims.
- Do not infer that CaMeL covers compromised memory; paper threat model excludes that. Do not infer that memory filtering is sufficient from MINJA. Do not infer deletion of raw records equals learned-model erasure from Guo et al. Do not treat lineage logging as proof deletion completed.
- Candidate Book example: a single end-to-end adversarial test starts with a poisoned shared-memory write, attempts an unauthorized send, triggers stop during an in-flight remote operation, and then requests deletion. Discriminating outcomes: (a) no unauthorized tool action; (b) stop state differentiates verified fence from unknown remote completion; (c) all registered derivatives are read back absent; (d) any irreducible model/provider copy is named as unresolved. Compare a prompt-only baseline, capability/data-flow gating, and memory-write isolation under a declared threat model. This is a test proposal, not evidence or a novelty claim.
