### `agentic-skill-discovery`
The body contains empirical precision/success rates (76% vs 46%; 12.50% vs 43.75%; 25% vs 46%) and gates (>45%, >75%) without identifying the underlying paper, dataset, or table in the cited passage. Do not preserve these as facts until exact source provenance is reconstructed. Version-pinned benchmark evidence offers better scoped starting points: the project-site SkillsBench PDF inspected here is dated 2026-02-13 and reports an 86-task/11-domain inventory in its abstract but 84 evaluated tasks and +16.2 percentage points in the reported cohort ([historical site PDF](https://www.skillsbench.ai/skillsbench.pdf)). These are distinct revisions/cohorts; do not combine their counts or treat the site PDF as the latest version. SkillLearnBench reports 20 verified skill-dependent tasks over 15 subdomains and finds gains are not consistent across tasks/models, with external feedback helping iterative learning while self-feedback alone can drift ([Zhong et al., arXiv:2604.20087](https://arxiv.org/abs/2604.20087), abstract/metadata inspected). ASCII candidates: 0 in body. **Book candidate:** skill utility is task-conditional; compare with/without skill and publish per-task deltas and regressions, not a single library-wide quality score. No novelty claim.

### `agentic-software-installation`
The runbook combines detection, staged install, configuration merge, and live hook verification. Several provider/version claims (CLI names, config scope, dialects, hook availability) are fragile and should be stated as verified-on date/version, not evergreen. Current official Codex hooks documentation says hooks may be configured in `hooks.json` or `config.toml` at different active config layers, matching hooks from multiple files run, matching command hooks may run concurrently, and non-managed hooks require review/trust; lifecycle includes pre/post-tool and session/subagent events ([OpenAI Codex hooks](https://developers.openai.com/codex/hooks), opened and relevant sections read). Official Claude documentation likewise says lifecycle handlers run at key points, recommends inspecting configured hooks and testing an event ([Claude hooks guide](https://code.claude.com/docs/en/hooks-guide), opened sections on setup/test/event timing). These vendor facts do not prove this repository’s paths, supported CLI versions, or local hook operation. Add a vendor/version capability matrix and fixture-based payload/exit/result tests; distinguish file staged, config trusted, event delivered, and gate effect observed. Preserve atomic merge/idempotent rollback and never clobber unrelated config. **Worked case:** merge a project-scoped hook entry into an existing user config; assert unrelated keys unchanged, then report “configured, untrusted/not tested” until an authorized interactive event is observed. **Mermaid ideas:** (1) detect → stage → merge → trust → event → observed result; (2) vendor payload fixture → adapter → normalized decision → vendor response matrix. ASCII candidates: 4; convert decision/runbook diagrams, preserve shell/config blocks as code. **Book candidate:** portable hook governance across divergent host protocols, with a compatibility conformance suite; no universal cross-vendor contract assumed.

### `windags-curator`
The body applies Beta-Bernoulli Thompson updates by adding continuous evaluator scores to alpha and `1-score` to beta, logs a near miss within 10%, crystallizes after three successes, and treats parameters as additive G-Counters. Standard Beta-Bernoulli conjugacy is grounded in binary Bernoulli outcomes; fractional updates can be a power-likelihood/heuristic but need explicit interpretation, dependence assumptions, and evaluation calibration. Correlated scores from the same evaluator/model/task family are not independent evidence. Add a per-source/task/evaluator ledger, separate candidate observation from posterior update, and include evaluator disagreement and distribution shift. Make “three successes,” near-miss margin, and PSI triggers versioned policy parameters, not validated constants. **Worked case:** three successes on near-identical easy tasks do not promote a skill; cluster/correlate the observations and require independent held-out task families plus regression tests. **Mermaid ideas:** (1) raw outcomes → evaluator calibration → evidence grouping → posterior/update → promotion; (2) skill draft/version lineage with hold, revise, promote, and rollback. ASCII candidates: 4 in body. **Book candidate:** what Thompson sampling can and cannot justify when rewards are graded, correlated, and evaluator-generated; compare binary conversion, generalized likelihood, and contextual/hierarchical alternatives empirically.
