# Fleet Retool — 2026-05-20

> The old fleet shouted into pub/sub channels nobody read. The new
> fleet writes where Erich already lives: GitHub PR comments,
> issues, and draft PRs. Channels stay — they're how ships chain to
> other ships — but they're internal plumbing now, not the operator
> surface.

## The problem this fixes

Pre-2026-05-20, every ship in `pd-fleet.yml` published findings to
pub/sub channels: `port-daddy:fleet:qa`, `notify-findings`,
`tests:gap-found`, on and on. They were durable in SQLite. They had
SSE streams. They had a dashboard panel. And the operator never
read them.

That's not a tooling problem. That's a delivery-channel problem.
Findings live where the operator already lives, or they don't live.
Erich lives in GitHub PRs. The fleet now writes to GitHub PRs.

## Headline feature — runtime backend detection via pd-tube

The pre-retool fleet had hard per-ship backend pins (Anthropic Haiku
on code-reviewer and test-author, Sonnet on red-team, Haiku on
unspider). The operator rejected that on first push and was correct
to: it was brand-reach masquerading as analysis. Hard pins ignore
that Erich has a Claude Max subscription, a ChatGPT Pro
subscription, a Cloudflare account, and OpenAI / Anthropic API
keys. Routing every PR review through a paid Anthropic API call
when the same machine has free-at-margin CLI subscriptions is the
wrong default.

The retool replaces hard pins with **runtime backend detection**.
Every LLM-powered ship now carries a `backend:` + `fallbacks:`
preference array. At spawn time the spawner walks the list and
picks the first entry that is (a) available on this machine,
(b) healthy on its last heartbeat, and (c) under its daily cap.
Ships fail loudly if no entry is serviceable — they do NOT silently
degrade to a hardcoded default.

The standard preference order, top to bottom:

1. **`cli:claude-code`** — routed through `pd-tube` (the daemon's
   CLI-backend route). Free at margin if the operator is a Claude
   Max subscriber and `claude-code` is on PATH (or
   `PD_USE_CLI_BACKEND=claude-code` is set). The sibling PR #109
   work wires this end-to-end.
2. **`cli:codex`** — also routed through `pd-tube`. Free at margin
   if the operator has a ChatGPT Pro subscription and `codex` is on
   PATH (or `PD_USE_CLI_BACKEND=codex` is set).
3. **`cloudflare`** — cheapest cloud option per ship task
   (`@cf/qwen/qwen3-30b-a3b-fp8` for general work,
   `@cf/qwen/qwen2.5-coder-32b-instruct` for code work,
   `@cf/moonshotai/kimi-k2.6` for ideation). Requires
   `CLOUDFLARE_ACCOUNT_ID` + `CLOUDFLARE_API_TOKEN`.
4. **`openai`** — `gpt-5-mini` for pattern recognition / tautology
   detection; `gpt-5` for red-team's attack-construction tier.
5. **`anthropic`** — included only for voice-sensitive ships
   (`code-reviewer`, `red-team`, `test-author`, `tenderfoot`) as a
   *soft* preference because Claude tracks operator voice well. It
   is **never** a hard requirement. If only Cloudflare is healthy,
   the ship runs on Cloudflare and accepts the quality tradeoff.

### What this means for the operator in three scenarios

| Setup                                                | Where the fleet runs           | Cost          |
|------------------------------------------------------|--------------------------------|---------------|
| Max subscriber + `claude-code` on PATH               | `cli:claude-code` via pd-tube  | $0 marginal   |
| Pro subscriber, no Max + `codex` on PATH             | `cli:codex` via pd-tube        | $0 marginal   |
| Cloudflare keys only, no CLI subscriptions, no API keys | Cloudflare qwen + cf coder  | ~$5/day cap   |
| API keys only (Anthropic + OpenAI + Cloudflare)      | Cheapest competent per ship    | ~$5.50/day cap |

The product promise: fleet works on whatever the operator already
has. If they have Max + Pro, fleet is free. If they have Cloudflare
only, fleet runs on Cloudflare and is honest about the voice
tradeoff. There is no silent Anthropic preference.

### Schema note (debt)

The existing `lib/fleet-ast.ts` AST already supports `backend:` +
`fallbacks:` (an ordered array of `{ backend, model, modelTier }`).
That carries the preference order today without a schema change.

A future cleanup may rename the pair to a single
`backend_preference:` array for clarity (it's literally what it
is). That's a YAML-schema migration plus AST extractor work, and
the live retool doesn't need it. Flagged in the operator-review
section.

## What changed, in one paragraph

- Five new ships (`code-reviewer`, `red-team`, `test-author`,
  `tautology-sniffer`, `tenderfoot`) trigger on `pull_request:*`
  events and write PR comments, issues, or draft PRs.
- Eight existing ships (`gardener`, `qa`, `test-hunter`,
  `documentarian`, `simplifier`, `cartographer`, `spark`, `spider`)
  had their backends moved to the preference-array shape and their
  outputs rewired to GitHub primitives or operator-readable repo
  files where appropriate. `spark` and `spider` keep their
  internal-only output paths because they're research input for
  other ships, not for Erich.
- A single shared primitive (`lib/fleet/github-output.ts`) implements
  `postPRComment`, `openIssue`, `openDraftPR`, `closeIssue`. Ships
  call this; they do not reinvent the API client.
- Two zombie shell scripts (`fleet/qa-adversary.sh`,
  `fleet/test-gap-hunter.sh`) hardcoded `ollama` and didn't run.
  Deleted. Their behavior is captured in the new yml-based config.

### About `tenderfoot` (and the unspider rename)

The fresh-eyes new-developer UX audit ship was named `unspider` in
this retool's first draft. That collided with **ADR-0032**, which
had already defined **unSpider** as the contradiction-finder — a
different and more ambitious role (auditing the roadmap for
internal drift, overlapping plans, stale references).

Renamed the UX ship to **`tenderfoot`** (old-western for greenhorn;
high-low cathedral collision — homely word, careful job). The
ADR-0032 unSpider retains its name and its label namespace
(`unspider:open`). Tenderfoot uses its own label namespace
(`tenderfoot:open`). The two ships share read surfaces but write
to different places; they can run side by side.

`fleet/ships/unspider.md` is now a stub that points at ADR-0032
with a TODO list for when the contradiction-finder is actually
built. This keeps the slot reserved.

### The pd-tube CLI-backend route

`cli:claude-code` and `cli:codex` are implemented in
`lib/spawner.ts:runCliTube()` (the **pd-tube** path). When the
spawner picks a `cli:*` backend, it shells the ship's prompt out to
the operator's local CLI binary (`claude-code` or `codex`) which
authenticates against the operator's existing subscription. The
daemon does not need API keys.

The sibling PR (#109 work) is wiring the pd-tube transport
end-to-end with telemetry and bond accounting. Once that lands,
the `cli:*` entries in every ship's `fallbacks:` array gain real
teeth — today they work for solo runs (`pd fleet run <ship>`) but
the full daemon-mediated event loop needs the sibling PR's
runtime.

## The shared primitive

```ts
// lib/fleet/github-output.ts
export interface GitHubOutput {
  postPRComment(prNumber, body, opts?): Promise<{ url, commentId?, edited }>;
  openIssue(title, body, labels, opts?): Promise<{ number, url, created }>;
  openDraftPR(branchName, title, body, baseBranch?): Promise<{ number, url }>;
  closeIssue(number, reason): Promise<void>;
}
```

Backed by `gh` CLI, inherits the operator's auth. When the Port
Daddy GitHub App lands, the helper flips to App credentials via the
`GH_TOKEN` env injected by the daemon. The interface does not
change.

Two sub-features matter:

1. **One-comment-per-ship-per-PR.** Every comment carries a marker
   line `<!-- pd-fleet:ship=<name> -->`. `postPRComment` with
   `editIfExists: true` (the default) finds the marker and edits in
   place. PRs stay scannable; ships don't carpet-bomb.

2. **Issue dedup by title.** `openIssue` with `dedupeByTitle: true`
   (default) searches open issues for an exact title match before
   filing. `tenderfoot` running every Monday won't refile the same
   drift complaint.

## GitHub-event channel bridge

The fleet engine doesn't natively know about GitHub events. The
`pull_request:*` channels in `pd-fleet.yml` are marked
`external_producer: github-webhook-bridge`. Today they can be fired
manually:

```bash
pd pub pull_request:opened '{
  "prNumber": 117,
  "headRef": "fix/wire-shape-bug",
  "baseRef": "main",
  "title": "fix: SDK claim wire shape",
  "author": "erichowens",
  "changedFiles": ["lib/sdk.ts", "tests/unit/sdk.test.ts"]
}'
```

That's the test harness path (see the end-to-end test below). The
persistent path is a webhook receiver or a `gh` polling watcher,
which is sibling work in flight. Until that lands, ships fire when
the channels are manually published, or when a future
`scripts/gh-event-pump.sh` cron job pumps them.

## End-to-end test (PR-opened → ship fires → comment lands)

Prerequisite: daemon running, fleet up, `gh` authenticated, a test
PR open.

```bash
# 1. Pick an open PR
PR=117

# 2. Bring fleet up
pd fleet up

# 3. Manually fire the channel
pd pub pull_request:opened "{
  \"prNumber\": $PR,
  \"headRef\": \"test/fleet-retool-smoke\",
  \"baseRef\": \"main\",
  \"title\": \"smoke: fleet retool e2e\",
  \"changedFiles\": [\"lib/sdk.ts\"]
}"

# 4. Watch fleet events
curl -N http://localhost:9876/fleet/events

# 5. Verify the comment landed
gh pr view $PR --comments | grep "pd-fleet:ship=code-reviewer"
```

Expected timeline: `code-reviewer` spawns within ~5s of the
channel pub; comment lands within 30-90s depending on PR diff size.
`tautology-sniffer` and `red-team` may or may not fire depending
on whether the diff touches tests / adversarial surface.

Re-running step 3 (or running a real `git push` against the PR
branch and publishing `pull_request:synchronize`) edits the same
comment in place. Verify the comment count on the PR did NOT
increase.

## What needs operator review before promotion to main

1. **The `pull_request:*` channel bridge.** The yml declares the
   channels with `external_producer: github-webhook-bridge`, but
   that bridge isn't built. Three options for the operator:
   - Ship the webhook receiver as a separate concern
   - Wire a `gh` polling watcher in the daemon (every 30s)
   - Keep the manual-pub test path until the GitHub App lands

2. **`cartographer-state` branch.** The retool adds a write to a new
   orphan branch. The operator should confirm this is the desired
   pattern vs. (a) writing to a `cartographer/` dir on `main` with a
   bot commit, or (b) writing to a separate repo. Default is the
   orphan-branch pattern.

3. **Budget ceiling.** `budget_usd_per_day: 8.50` is up from `9.76`
   (counterintuitive — it's lower because two ships are paused and
   we tightened the active set). Under pd-tube routing on a Max
   subscription, marginal cost drops to ~$0 and the cap is purely
   a safety net.

4. **`tenderfoot` cadence.** Monday-only is the brief's default. If
   Erich finds it valuable, bump to twice-weekly (also on Thursdays).
   If it's noisy, drop to first-Monday-of-month.

5. **YAML schema cleanup (debt).** Today the runtime expresses
   "preference order" as `backend:` (primary) + `fallbacks:`
   (rest of array). A cleaner schema would be a single
   `backend_preference:` array. That's a `lib/fleet-ast.ts`
   migration plus a yml syntax change; deferred for now to keep
   this retool small. Flagged so it's not forgotten.

## Rollback

If the new fleet misbehaves:

```bash
# Stop the new fleet
pd fleet down

# Revert the yml to the pre-retool version
git checkout HEAD~1 -- pd-fleet.yml

# Restore the deleted shell scripts (optional — they didn't work)
git checkout HEAD~1 -- fleet/qa-adversary.sh fleet/test-gap-hunter.sh

# Re-bring up
pd fleet up
```

The `lib/fleet/github-output.ts` module and the `fleet/ships/*.md`
contracts are additive — they hurt nothing if unused. Leave them in
place during rollback so the retool can be retried later without
re-writing.

## Acknowledged debt

- The GitHub-event bridge is not built. Today the `pull_request:*`
  channels are operator-manually-fired or wait on the sibling
  webhook task.
- The pd-tube CLI-backend route (sibling PR #109) is in flight but
  not landed; the `cli:*` entries in every ship's `fallbacks:`
  array work for solo runs today but need the sibling PR for the
  daemon-mediated event loop.
- `lib/fleet/github-output.ts` has no unit tests yet. The module
  shells out to `gh`; testing requires either a `gh` mock or
  integration tests against a sandbox repo. Either is fine; neither
  is done.
- `test-hunter` → `test-author` chain assumes the `coverage-gap`
  issue references the PR by number in the body. The bridge that
  cross-links them is implicit (search by title + PR number). A
  durable link via issue body would be tighter.
- The `cartographer-state` branch auto-commit pattern is
  unimplemented; cartographer needs a small shell helper for the
  orphan-branch write. Flagged in the operator-review section.
- `backend_preference:` as a single-array yml key is the cleaner
  schema; today we ride on `backend:` + `fallbacks:`. AST migration
  is deferred (see operator-review item 5).
- ADR-0032 unSpider (the contradiction-finder) is not yet
  implemented. `fleet/ships/unspider.md` is a stub pointing at
  the ADR.
