# ADR-0130: Derived JSON Must Be Generated and Hash-Gated, Never Hand-Merged

- **Status:** Proposed — a recommendation is given below; which option to
  take is the operator's call
- **Date:** 2026-08-26
- **Discovered by:** repeated operator-hit merge conflicts in files whose
  true source of truth is "the current state of many other files or a
  database" but which are hand-merged as if they were hand-authored content.
  Concrete, on this repo's own history (`git log --oneline -- <path>`):
  `docs/roadmap/roadmap.snapshot.json` alone has at least five dedicated
  conflict-repair commits — `957560fd3` ("resolve merge conflicts with main —
  sort roadmap items, update test expectations"), `87343ab5f` ("resolve merge
  conflict — count 272, main's 270 items + 2 from this branch"), `c69a41b20`
  ("correct stale snapshot.count after main-merge conflict (260→262)"),
  `2515daafc` ("restore snapshot count to match its 294 items"), `b8e6e861a`
  ("repair snapshot item count") — plus the same file appearing in two more
  generic `Merge remote-tracking branch 'origin/main'` commits. `docs/adr/adr-numbering-registry.json`
  is the same root cause and is the reason `adr-number-collision-guard.mjs`
  exists at all.
- **Siblings:** ADR-0129 (ADR identity as a content-anchored token) — same
  root cause, different implementation surface. Read together; decided
  separately.
- **Builds on:** `scripts/adr-number-collision-guard.mjs`'s existing
  regenerate-and-diff pattern (already does exactly this, for one file);
  `scripts/check-readme-freshness.mjs` (the same commit-time freshness
  discipline for a different surface); `lib/roadmap-snapshot.ts` /
  `scripts/export-roadmap-snapshot.ts` (the roadmap snapshot's actual
  generator); `docs/roadmap/AUTHORITY.md` (the doc-authority declaration
  this ADR has to reconcile with, not override).

## Context

Two files in this repo are, by their own header comments, pure projections
of another source of truth — and both have caused real, repeated merge pain
because git's line-based three-way merge does not know that.

### `docs/adr/adr-numbering-registry.json` — already generated, already gated

Its own `description` field says it plainly: *"A pure projection of
`docs/adr/`, regenerated by `scripts/adr-number-collision-guard.mjs
--write-registry`. Do not hand-edit — it is gate truth."* The guard already
does the thing this ADR is arguing for, for this one file: it rebuilds the
registry from the live `docs/adr/` tree in-process (`buildRegistry()`),
serializes it deterministically, and fails the commit
(`registryStale`, exit 1) if the committed bytes do not match what
regeneration would produce right now. There is no merge step for this file
in the intended workflow at all — a collision or a stale registry is
*regenerated*, not *resolved*, per the guard's own error message: *"Resolve
it: ... regenerate the registry: `node scripts/adr-number-collision-guard.mjs
--write-registry`."*

### `docs/roadmap/roadmap.snapshot.json` — generated, but not gated the same way

`lib/roadmap-snapshot.ts`'s header states the same shape of claim: *"CI
runners cannot reach the local daemon's SQLite, so the roadmap link gate
reads a committed mirror ... The daemon stays the single writer; the
snapshot is a read replica."* `scripts/export-roadmap-snapshot.ts` is the
generator — it fetches `GET /roadmap/items?status=all&harbor=<h>` from a
live daemon and overwrites the file wholesale. And yet this is the file with
five dedicated "fix the merge conflict" commits in this repo's history,
because nothing stops a branch from hand-editing the JSON (or letting git's
merge driver hand-edit it) instead of regenerating it, and nothing at
commit or CI time catches that the committed bytes have drifted from what
the live roadmap actually contains.

### A finding along the way: the doc-authority and the generator disagree with each other

`docs/roadmap/AUTHORITY.md` (declared 2026-07-15) states a stronger rule than
"regenerate from source": *"`roadmap.snapshot.json` is an **append-only**
projection of the table. **Never regenerate it via a full export** — that is
the fragmentation hazard that drops live upserts. Patch append-only through
the daemon code path only."* But `scripts/export-roadmap-snapshot.ts` — the
only generator for this file that exists in the repo — is a full export: it
queries every item with `status=all` and calls `writeRoadmapSnapshot`,
overwriting the committed file wholesale, every time it runs. The doc that
governs the file and the script that produces it do not agree on whether
"regenerate via full export" is the fix or the hazard. AUTHORITY.md's
own context (DB fragmentation causing every roadmap surface to report a
different item count) suggests the append-only caution predates
consolidation work that may since have closed the fragmentation gap it was
guarding against — but this ADR did not verify that consolidation landed,
and does not resolve the disagreement. It is named here as exactly the kind
of ambiguity this ADR's Option A has to design around rather than paper
over: **a hash-gate for this file cannot simply say "regenerate and diff"
without first settling whether full-export regeneration is the sanctioned
mechanism or the documented hazard.**

### The staleness check that already exists — and what it does not catch

`scripts/check-roadmap-link.ts` already reads the snapshot's `generatedAt`
field and fails loud (`verdict: 'needs-approval'`, `loud: true`, a headline
telling the author to regenerate) when the snapshot is older than
`staleAfterDays` — default **21** days in the code
(`check-roadmap-link.ts:266`), stated as **≤ 14** days in AUTHORITY.md's
reconciliation-cadence rule. That is a third, smaller instance of the same
disease this ADR is about: two artifacts that are each supposed to be
authoritative about the same number disagree with each other, in the same
two files already cited above.

More importantly, the age check is a **weak proxy**, not the check this ADR
argues for. A snapshot can be freshly regenerated and still wrong (a bad
daemon read), or staled-looking and still correct (nothing changed in 20
days). What it cannot catch is the actual failure mode observed in the five
conflict-repair commits above: a **hand-merged** file, produced by resolving
a git conflict rather than by rerunning the generator, that has a plausible
`generatedAt` timestamp (often inherited from one side of the merge) and a
subtly wrong `count`/`items` array that took a human commit to notice and
fix after the fact — every one of `87343ab5f`, `c69a41b20`, `2515daafc`, and
`b8e6e861a` is exactly that: a *follow-up* commit correcting a snapshot that
had already merged wrong.

## Why git's merge algorithm is the wrong tool here

Git's three-way merge operates line-by-line with no notion that a JSON
document is a serialization of a query result. Two branches that each add
one roadmap item produce a textual diff that *looks* like a clean,
independent insertion — new lines in the `items` array — and git will
usually auto-merge it without even flagging a conflict. But the file also
carries a `count` field that has to equal `items.length`, and nothing in
git's merge machinery updates a derived scalar when the array it derives
from changes underneath it. That is precisely the shape of `c69a41b20`
("correct stale snapshot.count after main-merge conflict") and `2515daafc`
("restore snapshot count to match its 294 items") — the merge itself
"succeeded" by git's definition and still produced a file whose own internal
invariant (`count === items.length`) was false, silently, until a human
noticed and fixed it in a follow-up commit.

This repo already has a working precedent for solving a structurally similar
problem — repeated conflicts in a shared file every PR touches — with a
**different** mechanism: `changelog.d/`. Its own README names the same
disease (*"29 of the last 200 commits touch [`CHANGELOG.md`], and effectively
all of them write those same three lines. Two branches cut from the same
base conflict on nearly every pair"*) and picks partition-by-construction —
one file per PR, assembled at release time — over either a smarter merge
driver (it explicitly rules out `.gitattributes` `merge=union`, calling out
that union-merging *"interleaves and duplicates entries without ever
conflicting — a quieter version of the same bug"*) or a generate-and-diff
gate. That is the right call for `CHANGELOG.md` specifically because a
changelog entry is **irreducibly hand-authored per PR** — there is no
underlying database a changelog fragment is a projection of, so there is
nothing to regenerate it from. `adr-numbering-registry.json` and
`roadmap.snapshot.json` are the opposite case: both are, by their own header
comments, **pure projections of something else already in this repo or
reachable from it** (the `docs/adr/` tree; the daemon's `roadmap_items`
table). For a pure projection, regenerate-and-diff is available as a
mechanism and partition is not — there is nothing to partition, only one
row of derived truth per source state. The two repo-native precedents
(`changelog.d/` and `adr-number-collision-guard.mjs`) are both correct
responses to the same symptom, aimed at two different root causes, and this
ADR's job is to extend the second pattern, not import the first.

## The options

### Option A — regenerate-and-hash-compare CI gate (recommended)

Generalize `adr-number-collision-guard.mjs`'s own `registryStale` check into
a small family of gates, one per derived file, each doing the same three
things: run the file's real generator against its real source, canonicalize
the output, diff the canonical bytes against what is committed, and fail
the build with a specific `pd regen <target>`-style instruction (mirroring
the guard's existing error text, which already names the exact command to
run) rather than presenting a diff for a human to eyeball and merge.

- **For `adr-numbering-registry.json`:** already Option A, today. No change
  needed beyond keeping it as the reference implementation the other gates
  imitate.
- **For `roadmap.snapshot.json`:** the source is a **live daemon**, which a
  hosted CI runner cannot reach (`lib/roadmap-snapshot.ts`'s own stated
  reason the snapshot is committed at all). This is a real asymmetry with
  the registry case, not a detail to gloss over: CI can regenerate-and-diff
  the ADR registry because its source (the `docs/adr/` tree) is in the same
  checkout, but it cannot do the same for the roadmap snapshot without
  either (a) a live daemon reachable from the runner — which does not exist
  today and is out of scope to stand up here — or (b) moving the
  regenerate-and-diff check to run **locally, at commit or pre-push time**,
  where a real daemon is reachable, the same place `pd guard check --staged`
  already runs today. Under (b), CI keeps only the weaker checks it can
  actually perform without daemon access: valid JSON, `count === items.length`,
  and the existing `generatedAt` staleness clock — a backstop, not the gate.
  This also resolves the AUTHORITY.md tension above by construction: a
  local, daemon-backed regenerate-and-diff naturally reads
  `status=all` from the live table (today's actual behavior) rather than
  attempting an append-only patch CI has no way to construct safely, and
  the local checker can additionally assert the append-only invariant
  AUTHORITY.md actually cares about — no previously-present slug silently
  disappears between the last committed snapshot and the freshly generated
  one — as an explicit check inside the same gate, rather than trusting
  "full export" and "append-only" to coincide by accident.
- **Costs:** two different gate implementations for two different source
  shapes (in-tree files vs. a live daemon), not one drop-in script; the
  roadmap-snapshot half of this only closes the hole for authors who run
  `pd guard check` locally before pushing, same limitation the Coordination
  Guard already has today for everything else it enforces.
- **Buys:** for the in-tree case (the ADR registry, and any future purely
  file-derived JSON), a complete fix — the merge-conflict symptom mostly
  disappears rather than getting easier to resolve, because there is no
  "conflict" once the rule is "never hand-edit, always regenerate and let
  the gate catch drift." For the daemon-backed case, a real (if
  commit-time-scoped) improvement over the current staleness-only check,
  plus a fail-closed message that tells the author the actual fix
  (regenerate) instead of leaving them to hand-reconcile a `count` field,
  which is what produced four of the five conflict-repair commits cited
  above.

### Option B — a `.gitattributes` merge driver, staleness gate as backstop

Register `docs/adr/adr-numbering-registry.json` and
`docs/roadmap/roadmap.snapshot.json` with a custom merge driver (or
`merge=ours`) so git stops attempting a line-based merge on them, and rely
on the existing staleness check (extended to the ADR registry, which has
none today beyond the collision guard) as the only freshness gate.

- **Costs:** `changelog.d/README.md` already measured and rejected exactly
  this class of fix for its own file, and its stated reason generalizes:
  `merge=ours` silently keeps one side's version and drops the other's
  changes with **no error at all** — worse than today's behavior, where a
  conflict at least stops the merge and forces a human to look. A staleness
  clock alone (this option's only proposed backstop) is the weak proxy
  already shown above to miss exactly the failure mode that produced the
  five conflict-repair commits.
- **Buys:** almost nothing beyond what exists today, and trades a visible
  failure (a merge conflict, or the current `registryStale` check) for a
  silent one. Included for completeness and rejected below, not recommended.

### Option C — stop committing the derived file; serve it live instead

For `roadmap.snapshot.json` specifically: instead of committing a mirror,
have CI (or the roadmap-link gate) query a reachable endpoint directly and
never store the projection in git at all.

- **Costs:** contradicts the file's entire reason for existing —
  `lib/roadmap-snapshot.ts`'s header is explicit that the snapshot is
  committed *because* "CI runners cannot reach the local daemon's SQLite."
  Making it queryable from CI means standing up network reachability from
  GitHub Actions to an operator's local daemon (or a hosted equivalent),
  which is a materially larger infrastructure change than this ADR is
  scoped to propose, and touches the relay/cloud-plane architecture
  decisions ADR-0122/0123/0126 already own.
- **Buys:** would eliminate the merge-conflict class entirely for this file,
  in principle, by removing the git-tracked copy — but at a cost this ADR
  is not positioned to price honestly without touching that other
  architecture. Named for completeness; not recommended without a
  dedicated ADR of its own if the operator wants it explored.

## Which files this ADR actually covers

Grounded in what this session read, not invented: `docs/adr/adr-numbering-registry.json`
(confirmed generated, already gated) and `docs/roadmap/roadmap.snapshot.json`
(confirmed generated by `scripts/export-roadmap-snapshot.ts` /
`lib/roadmap-snapshot.ts`, fed from the daemon's `roadmap_items` table,
confirmed to have caused at least five real conflict-repair commits).
`lib/model-registry-data.ts` (confirmed present on `main`, ADR-0057) is a
third, already-working precedent for this same pattern on a non-JSON
(TypeScript) surface: its own header says outright *"`scripts/refresh-model-registry.ts`
rewrites this file per version build"* and *"NEVER hardcode a model ID
anywhere else."* PR #9417 (open, unmerged) proposes widening this same
pattern — a `config/models.yaml` source feeding **two** generated,
drift-tested artifacts instead of one, `lib/model-registry-data.ts` for the
daemon and a new (not yet shipped) `apps/shared/model-registry.generated.ts`
for the Workers plane, which cannot import `lib/`. That widened form is not
merged to `main` and this ADR did not read its diff; it is cited only as
evidence that
the regenerate-and-diff pattern is already understood and being actively
extended in this repo, independent of this ADR. Deliberately **excluded**:
`features.manifest.json` — its own `_comment` field and this repo's
`port-daddy-internal-dev` skill both describe it as hand-declared per
feature ("Every feature MUST be declared here before shipping"), checked for
*parity* against the routes/CLI/MCP surface (`npm run parity`), not
generated from any of them. It is a hand-authored contract file, closer in
shape to `CHANGELOG.md` than to the roadmap snapshot, and out of scope here.

## Regressive test / verification thinking

What any implementation of Option A must be proven against, not merely
asserted to handle:

- **Two branches concurrently adding different roadmap items must both
  survive.** Construct branch X adding item `foo` and branch Y adding item
  `bar` from the same base snapshot; merge X into main, then attempt to
  land Y. The gate must fail Y's stale, pre-X snapshot loudly and instruct
  a regenerate — not silently keep Y's copy (losing `foo`) and not silently
  keep X's copy merged with Y's diff (recreating today's hand-merge, which
  is the bug). This is the actual shape of `87343ab5f`'s conflict ("count
  272, main's 270 items + 2 from this branch") and the gate is only a fix
  if it turns that into a loud, actionable failure earlier, not a quieter
  version of the same manual reconciliation.
- **A snapshot with a correct `count` but wrong `items` content must still
  fail.** The existing `check-roadmap-link.ts` staleness check only reads
  `generatedAt`; a regenerate-and-diff gate must hash or compare the actual
  `items` array, not just the scalar fields, or it inherits the same blind
  spot the age check already has.
- **The append-only invariant AUTHORITY.md cares about must be a check, not
  an assumption.** A regeneration that drops a previously-committed slug
  (the exact hazard AUTHORITY.md names — "if you delete a session on machine
  A, it still exists on machine B," generalized: an upsert race dropping a
  live item) must fail the gate even when the freshly generated file is
  otherwise self-consistent. This is the concrete design item Option A's
  write-up above defers to implementation; a test fixture with a
  monotonically-shrinking item set is the regression to write first.
- **The gate must not become a second thing that silently degrades.** Per
  the Option B critique, any fallback behavior (daemon unreachable locally,
  CI running the weaker backstop only) must fail loud with an actionable
  message — "could not verify freshness, daemon unreachable, run `pd guard
  check` before pushing" — never a quiet pass. `adr-number-collision-guard.mjs`
  already sets this bar (`die(2, ...)` on an unreadable ADR dir, not a
  silent 0) and any new gate should match it, not regress from it.
- **Re-run the existing gate as the acceptance check for this ADR's own
  files.** `node scripts/adr-number-collision-guard.mjs --write-registry`
  was run against this worktree as part of authoring this proposal (see the
  PR's Test Plan) — the registry now includes 0129 and 0130 and reports
  clean. That is the smallest possible instance of "regenerate, don't
  hand-edit" this ADR argues for, exercised on itself.

## Non-binding recommendation

**Option A**, split as designed above: full regenerate-and-diff in CI for
purely in-tree derived files (the ADR registry is already there); a
local/commit-time regenerate-and-diff plus a weaker CI-side structural
backstop for daemon-backed files like the roadmap snapshot, because CI
genuinely cannot reach the daemon and pretending otherwise would ship a gate
that cannot run. Option B is rejected for the same reason `changelog.d/`
already rejected `merge=union` for a different file — a merge driver that
silently picks a side is worse than the status quo, not better. Option C is
not rejected on the merits, only deferred: it may be the right long-run
answer once the relay/cloud-plane work (ADR-0122/0123/0126) gives CI a
legitimate way to reach roadmap truth, but proposing that architecture
change is outside what this ADR read enough to cost honestly.

## What is NOT decided here

Whether Option A, B, or C ships. The exact shape of the daemon-reachability
gap for `roadmap.snapshot.json` — whether it is closed by a CI-reachable
staging daemon, a scheduled local regeneration job, or stays a commit-time-only
check indefinitely — is a real open design question this ADR names but does
not resolve. Whether the AUTHORITY.md append-only rule should be relaxed to
match what `export-roadmap-snapshot.ts` already does, or whether the script
should be changed to match the documented rule, is also not decided here;
this ADR only establishes that the disagreement exists and that any gate
implementation has to pick one side rather than silently inheriting
whichever the export script happens to do today.

## Consequences

- Until this is decided, `roadmap.snapshot.json` stays gated only by the
  existing `generatedAt` age check, which this ADR has shown does not catch
  the actual hand-merge failure mode observed five times in this repo's
  history.
- This ADR does not change `adr-number-collision-guard.mjs`,
  `lib/roadmap-snapshot.ts`, `scripts/export-roadmap-snapshot.ts`, or
  `docs/roadmap/AUTHORITY.md`. It proposes how they would change under
  Option A, and names — without resolving — the disagreement between
  AUTHORITY.md and the actual export script's regeneration semantics.
- If Option A ships, `docs/roadmap/AUTHORITY.md` needs a revision in the
  same PR reconciling the append-only rule with whatever the gate actually
  verifies, and `check-roadmap-link.ts`'s `staleAfterDays` default (21)
  should either be reconciled with AUTHORITY.md's stated 14-day cadence or
  AUTHORITY.md corrected to match the code — leaving both live and
  disagreeing is the same class of drift this ADR exists to close.
- Any implementation PR should extend, not replace, the reference
  implementation: `adr-number-collision-guard.mjs`'s `registryStale` check
  is the existing proof that this pattern works in this repo today, for one
  file.
