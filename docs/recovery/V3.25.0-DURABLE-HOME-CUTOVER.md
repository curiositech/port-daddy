# v3.25.0 Durable-Home Cutover Runbook

Status: runbook for a pending one-time migration. Execute with the v3.25.0
release; delete or mark done after the post-cutover verification passes.

Moving the live registry from the Homebrew Cellar to
`~/.port-daddy/port-registry.db` (PRs #2067, #2083, #2109, #2122) is a live
storage migration: a deploy (the new binary), a backfill (the boot-time
`VACUUM INTO` rescue), and a contract (the old Cellar keg — and its DB — is
deleted by the next `brew cleanup`). This runbook sequences it so there is
never a moment where a running writer and the rescued registry disagree.

## Hazard model

1. **Dual-writer window (the one that loses data).** The rescue snapshots the
   Cellar DB at new-daemon boot. Any process still writing to the Cellar DB
   *after* that snapshot — a zombie 3.24.1 daemon that survived the restart,
   a stale launchd job, a long-running CLI — writes into a file nothing will
   ever read again. This machine has real history here (the 3.24.0 zombie ate
   345 respawns and split-brained :9886), so "brew restarted it" is not
   evidence. Verify process death, don't assume it.
2. **Version-skew CLI writes.** A `pd` binary from the old keg (or a shell
   with a stale PATH hash) resolves the old default and writes to the Cellar
   DB post-cutover. `brew upgrade` replaces the binary atomically, but
   long-lived shells should `hash -r`/restart.
3. **Destructive contract.** The "drop old column" step of this migration is
   `brew cleanup` deleting the old keg — it is automatic and irreversible.
   All verification must complete before the next upgrade/cleanup runs.
   The daily 03:17 backup (`~/.port-daddy/backups/`) is the safety net.
4. **Dev-plane writers.** Instance daemons (`~/.port-daddy/instances/*`) and
   checkout-launched daemons keep their own DBs by design (explicit
   `PORT_DADDY_DB`). They are out of scope for the cutover and get folded in
   by the reunification step instead.

## Cutover sequence

Each step has a check; do not proceed past a failed check.

1. **Pre-flight capture (before upgrading).**
   ```bash
   CELLAR_DB=$(lsof -p $(pgrep -f port-daddy-daemon | head -1) 2>/dev/null \
     | grep 'port-registry.db$' | awk '{print $NF}')
   sqlite3 "$CELLAR_DB" "SELECT 'roadmap', COUNT(*) FROM roadmap_items;
     SELECT 'notes', COUNT(*) FROM session_notes;
     SELECT 'sessions', COUNT(*) FROM sessions;" | tee ~/coding/tmp/precutover-counts.txt
   sqlite3 "$CELLAR_DB" "SELECT id FROM harbor_token_signing_keys" \
     | tee ~/coding/tmp/precutover-signing-keys.txt
   ```
   Record the counts, the signing-key ids, and the exact Cellar path. Also
   confirm today's backup exists: `ls ~/.port-daddy/backups/ | tail -1`
   (manifest `sourcePath` must match `$CELLAR_DB`).
2. **Stop the old daemon and verify death.**
   ```bash
   brew services stop port-daddy   # or the launchd unload the install uses
   sleep 2
   pgrep -fl 'port-daddy|pd-daemon' || echo CLEAN
   ```
   The check is the `pgrep` coming back empty. If anything survives, kill it
   and find out why before continuing (supervision-integrity check in
   `pd doctor` helps). **This is the step that closes the dual-writer window.**
3. **Snapshot the moment of death.** Note the Cellar DB mtime:
   `stat -f %Sm "$CELLAR_DB"`. After cutover this mtime must never advance
   again — an advancing mtime means a zombie writer.
4. **Upgrade and boot.** `brew upgrade port-daddy` then start the service.
   First boot of 3.25.0 performs the rescue (`migrateLegacyRegistry`: primary
   legacy path, then sibling kegs newest-first) and runs `verifyCoreSchema`
   fail-closed. Watch the log for the
   `Migrated registry from legacy location` line and the absence of a
   `failed post-apply verification` quarantine warning.
5. **Verify the backfill (counts must not shrink).**
   ```bash
   sqlite3 ~/.port-daddy/port-registry.db "SELECT 'roadmap', COUNT(*) FROM roadmap_items;
     SELECT 'notes', COUNT(*) FROM session_notes;
     SELECT 'sessions', COUNT(*) FROM sessions;"
   pd doctor   # "Database home: Registry path is durable" must be green
   ```
   Every count must be >= the pre-flight capture. A shortfall means the
   rescue picked the wrong keg — stop, check sibling kegs, restore from the
   morning backup if needed (`pd restore`).
   Also verify **signing-key continuity** — the identity minting authority
   must survive the move (historically it re-keyed on every upgrade, which
   silently invalidated all previously issued Harbor Cards):
   ```bash
   sqlite3 ~/.port-daddy/port-registry.db "SELECT id FROM harbor_token_signing_keys" \
     | diff ~/coding/tmp/precutover-signing-keys.txt -
   ```
   Empty diff = the same keys crossed over; any pre-upgrade Harbor Card still
   verifies. A changed key id means the daemon minted fresh keys instead of
   adopting the rescued ones — stop and investigate before issuing anything.
6. **Confirm no post-cutover Cellar writes.** Re-run the mtime check from
   step 3 after ~10 minutes of normal use. Unchanged mtime = the dual-writer
   window is provably closed.
7. **Reunify the scattered planes.**
   ```bash
   npx tsx scripts/registry-reunify.ts --dest ~/.port-daddy/port-registry.db \
     --shard ~/.port-daddy/instances/cloud-fleet-verify/port-daddy.db \
     --shard ~/.port-daddy/instances/pd-console-live/port-daddy.db \
     --shard ~/.port-daddy/instances/harbor-linework/port-daddy.db \
     --shard ~/.port-daddy/instances/dev-latest/port-daddy.db \
     --shard ~/.port-daddy/instances/cli-linework/port-daddy.db \
     --snapshot docs/roadmap/roadmap.snapshot.json --dry-run
   ```
   Read the plan, then re-run without `--dry-run`. The script backs up the
   destination first and is idempotent. Running against the live daemon is
   safe (WAL + busy_timeout serialize the writers; the merge transaction is
   milliseconds at this scale). Expected result: ~198+ items.
8. **Contract: export the new truth.** Run the snapshot exporter against the
   durable home and commit the union snapshot. From this point the committed
   snapshot, the live daemon, and the gate all read the same corpus — the
   acceptance gate from the 2026-07-14 focus receipt:
   `pd doctor` green AND `pd roadmap --harbor port-daddy` >= 160 AND the
   registry survives the *next* brew upgrade untouched (check after that
   upgrade lands).

## Rollback

Every step before 8 is reversible without data loss: the rescue is read-only
(the Cellar DB is never modified), reunify backs up its destination, and the
old binary can be re-pinned (`brew pin`) to run against its distribution-root
DB exactly as before. After `brew cleanup` removes the old keg, rollback
sources shift to `~/.port-daddy/backups/` (daily, 03:17).

## Known residuals

- Deletions do not propagate through union-merge — a row deleted in one
  replica resurrects from a stale one. Tracked as `roadmap-delete-tombstones`;
  do not run recurring (cron-style) reunification until that lands. The
  one-shot cutover reunify is safe: the source replicas are frozen planes.
- 70 of the reunified items carry status `now` — a curation debt for the
  roadmap-reconciler, not a migration defect.
